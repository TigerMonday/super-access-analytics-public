# テストの追加・整理

判断基準は「このテストを削除すると、どんな現実的な不具合を見逃すか」。件数やカバレッジの維持そのものを目的にしない。

## 残す保証

- 個人情報・認証情報の漏えい、HTML注入、既存文書や利用者の手書き情報の破壊を防ぐ。
- CVの集計単位、分母、期間境界、ページネーションなど、分析結果を変える誤りを防ぐ。
- 出力内容の欠落、未承認成果物の完了表示、失敗した書き出しの成功表示を防ぐ。

単純な計算でも、業務上の定義を固定していれば価値がある。モックは外部接続の境界で使い、入力・出力・禁止操作を検証する。モックが返す型だけの確認や、テスト内で組み立てた式・文字列の自己検証は避ける。

## 整理の進め方

1. 重複する保証と統合先を特定する。異なる障害条件を同一ケースとみなさない。
2. 公開入口の結果を優先し、内部関数名・呼出し回数・CSS宣言の書き方には必要以上に依存しない。
3. PDFなど重い生成は代表入力に集約する。画像・表・サイズなど必要な保証は生成済みの結果で確認する。
4. 同じ準備処理は共有してよいが、入力の境界を消さない。パラメータ化は必ずしも実行時間の短縮にはならない。
5. 変更したスイートと共通の回帰テストを実行する。単回測定から不安定率や恒常的な速度改善を断定しない。

任意ライブラリの不足はテスト中に明示的に再現する。開発環境にライブラリや認証情報があるかどうかに依存させず、実APIへ接続しない。ブラウザの完了判定は固定時間の待機ではなく状態を待つ。

## 実行

CIの対象と環境は、GitHubでは [.github/workflows/ci.yml](../.github/workflows/ci.yml)、Forgejoでは [.forgejo/workflows/ci.yml](../.forgejo/workflows/ci.yml) を参照する。ローカルでも各プロジェクトの環境で `python -m pytest` を実行する。実行時間の確認には `--durations=10` を追加する。

テスト成功は、実データの分析内容や配布版の最新性を保証しない。レポートの確認時は、元Markdown・HTML/PDF・実際の配布ファイルを区別して確認する。
