# レポート作成時の相談と分析品質

市場・顧客理解の章構成は `03_external_research/web_research/market-report-contract.md` を優先する。固定8項目は案件によって変えず、案件固有の論点は下位見出しに置く。

計測チェック、市場・顧客理解、基本分析、サイト改善のすべてに適用する。実行順序・保存先・CV定義は `standard-run-order.md`、文章は `report-writing-style.md` を正本とする。本書は、何を利用者へ相談し、分析をどこまで深めてから渡すかを定める。

計測チェックの目的は、GA4・GTMが定義どおり正しく計測できているかの監査である。監査の網羅性・判定根拠・未確認範囲を品質基準とし、事業分析の示唆の深さを求めない。以下の事業成果・顧客・施策に関する相談は、計測の正誤判断に必要な場合だけ適用する。

## 1. 相談のタイミング

### 作成前：何の判断に使うかを確認する

事業・サービスに関する質問の前に、`03_external_research/web_research/service-understanding.md` に従って対象サイトとサービスページを確認する。自社・競合ともサービス全体を把握し、一部の受注例だけで対象を狭めない。URLが既知なら再質問せず、公開情報で解決しない点だけを相談する。

既存context、会話、受領資料、過去の分析・施策を先に読む。登録済みのサイト、接続先、CV、フォーム、事業区分などを毎回聞き直さない。未登録でも会話で確認済みならその回答を使う。

結論・対象顧客・優先順位に影響する未確認情報は、分析を始める前に積極的に相談する。下記は質問候補であり、毎回すべてを埋める受付票ではない。今回の判断に効くものを原則1〜3問に絞り、なぜ必要かを短く添える。

- 増やしたい事業成果：サービス、顧客層、望ましい相談、有効リードの条件、対象外の問い合わせ。複数CVの優先度が必要なら確認する。
- 目標と判断の期限：件数・品質・売上のどれを改善したいか。数値目標や期限が未定なら創作しない。
- 顧客の実情：最近の受注・失注理由、実際の比較先、よくある質問、相談から受注までの流れ。
- 変化の背景：サイト・フォーム・タグ・同意設定・広告・記事・営業体制等の変更と時期。計画中の施策を実施済みと扱わない。
- 実行の制約：変更可能なページ、制作・開発体制、予算の目安、公開時期、変更できない要素。

個人情報や商談原文を一括で要求しない。匿名化した具体例、集計、利用者による要約で判断できるならそれを優先する。新しい外部サービスへの接続、外部AIへの送信、課金、公開・配信は、相談への回答だけで承認されたと扱わない。

### 分析途中：観察した事実を添えて聞く

#### 顧客理解は、よくある相談・要望から聞く

サービスページから課題・利用場面の仮説を準備したうえで、実情を確認する。「顧客像を教えてください」と抽象的に丸投げせず、次の順で聞く。既存回答は再利用し、毎回すべてを質問しない。

1. 傾向：「お客さんから、どんな相談や要望が多いですか？」を入口にする。複数サービスがある場合は対象サービスを明示する。
2. 具体化：回答が抽象的な場合だけ「その中で、よくある例を教えてもらえますか？」と聞く。最初から最近の1件だけを求めず、1件を顧客全体へ一般化しない。
3. 整理・確認：エージェントが課題、利用場面、依頼目的を整理し、「〇〇に困って△△を求める方が多い、という理解で合っていますか？」と確認する。誘導せず、違いや例外を訂正できる形にする。

BtoBでは相談内容に加え、必要な場合だけ担当者の仕事・社内体制・自社対応が難しい理由を聞く。BtoCでは商材と販売方法に合わせ、「購入前によく聞かれることは何ですか？」「どんな使い方を希望するお客さんが多いですか？」などへ変える。BtoB/BtoCだけで機械的に質問を固定しない。接客機会がない場合は既存のレビュー・問い合わせ・アンケートを参照し、把握していない購入理由の回答を強要しない。

回答はヒアリング上の傾向として扱い、集計による構成比とは区別する。必要なら現在多い顧客と今後増やしたい顧客を分けて確認する。無回答でもサービス由来の仮説として進め、業種・年齢・規模など根拠のない属性を足さない。会話の往復や確認宣言はレポート本文へ転記しない。

原因の候補が複数あり、社内事情がないと絞れない場合は、完成後の「要確認」に先送りせず相談する。

- 「この月だけ特定記事への流入が増えています。この時期に掲載・配信・露出の変更はありましたか」のように、観察事実・質問・回答によって変わる判断を示す。
- 回答を誘導しない。原因候補を例示するときも、それが原因だと決めつけない。
- APIの欠損、計算誤り、接続先の不一致など、こちらで確認できることを利用者へ調査させない。既存のデータ・設定を先に点検する。
- 回答がない間は、影響しない分析を進める。重要な結論は保留または条件別に示し、未確認の仮説を確定事実に変えない。CV定義など既存手順の必須確認は省略しない。
- 追加取得が必要なら、答えたい問い、必要な期間・切り口、取得範囲と費用・クォータを確認する。相談を理由に全データを取り直さない。

### 提案確定前：実行できる内容かを相談する

提供可能なサービス・相談の成果物、掲載可能な事例、変更範囲、工数、判定期間を確認する。未確認でも文案や画面案は候補として示せるが、提供できない約束を完成原稿へ紛れ込ませない。レポートの合意を本番変更や公開の承認と混同しない。

## 2. 回答を次回へ引き継ぐ

回答は確認日・出所とともに非公開contextへ保存する。既存の保存API・スキーマを使い、対応する項目がなければ `append_finding()` の履歴へ残す。回答待ち・不明・エージェントの仮説と、利用者が確認した事実を区別する。新たな回答で過去の判断を変えた場合は理由と影響先も記録する。

実クライアントの回答、URL、数値、商談情報を共通コードや公開手順へ転記しない。汎用化するのは質問の条件、分析方法、検査基準である。次回は既存回答を使い、変更の兆候や矛盾がある項目だけ確認する。

## 3. レポート別の完成基準

| レポート | 特に相談すること | 読み手へ渡す判断材料 |
|---|---|---|
| 計測チェック | 計測対象、タグ・サイトの変更履歴、確認権限。成果イベントは計測設計や別分析に必要な場合だけ確認する | 自動判定の5列表、APIで取得できない設定を集約した目視確認ブロック、具体的な異常・要確認、改善順。受信イベント一覧は出さない。機械37項目と目視19項目は内部監査で全件保持するが、正常・適用外を含む全56行は本文へ転記しない。イベント記録の存在だけで正確な計測と判定しない |
| 市場・顧客理解 | 増やしたい顧客、実際の受注・失注理由、比較先、選ばれる理由と提供限界 | 出典付きの競合比較と、自社の具体的な強み・不足。顧客の判断材料をどのページ・訴求へ反映するか。公開情報から作った顧客像を実際の顧客の声と区別する |
| 基本分析 | 事業上の優先CV・リード品質、施策や計測変更、季節性・一時的な露出 | 変化の大きさと寄与箇所、原因候補と検証結果、事業への意味。流入元・ページ・端末等を必要に応じて組み合わせ、集計表の言い換えで終えない |
| サイト改善 | 改修範囲、実際に約束できる内容、体制・期限・予算、過去の施策結果 | 優先理由、対象URLと変更位置、具体的な文案、配置が重要なら現状と変更案、必要な実装、成功・中止・再検討の判定方法。全体方針の段階では候補とし、個別施策確定時に具体化する |

4レポートを同じ構成へ揃える必要はない。計測の制約を基本分析へ、顧客の判断材料と分析結果をサイト改善へ引き継ぐ。顧客理解と数値が合わない場合は仮説を見直し、無理に関連付けない。

全レポート共通で、内部の根拠分類・確認状態・制作過程を利用者向け本文や見出しへ出さない。`会社側仮説`、`利用者未確認`、内部ID、英字の根拠分類は非公開の作業記録へ置く。判断に必要な留保は、表下の短い注記または末尾の「調査方法と限界」「分析の前提・制約」へまとめ、考察本文は事業上の意味から書き始める。

計測チェックでは `02_basic_measurement/measurement_design/standards/audit-items.md` の内部監査項目を案件ごとに削除・差し替えない。ただし公開本文へは同文書の設定確認表と、取得データから具体的に確認できた異常・要確認だけを出す。取得失敗・権限不足・未実施は正常判定に数えず、未確認理由と対応事項を書く。正常判定は確認した範囲に限り、設定を読めたことと実際の送信を検証できたことを区別する。フォーム通過率、業界平均との比較、問い合わせ減少の原因、市場仮説、サイトの訴求改善は基本分析・市場顧客理解・サイト改善で扱う。フォームの表示・開始・完了が期待どおり送信されるかは内部監査の対象に残す。

## 4. 結論を出す前の検査

3レポートの参照版・対応箇所の機械検査は `docs/report-connections.md` に従う。指示だけの接続確認で終えず、検査結果を残す。

市場・顧客理解を更新した後は、基本分析とサイト改善の「顧客課題→観測データ→施策」の対応を非公開の接続確認表に残す。対象サービス、顧客仮説、参照版、期間、CVの集計単位を照合し、旧前提に依存する本文だけを更新する。一般的な検索需要をサービスの発注意向へ読み替えず、異なる期間・分母を同じ指標として接続しない。公開本文には修正経緯を転記せず、判断に必要な根拠・制約だけを反映する。

1. **比較できるか**：期間・実取得範囲・欠損・部分月・集計対象・分子分母・取得上限を確認する。欠損をゼロとみなさない。保持期間外を含む比較はそのまま前年比と表示せず、比較可能な共通期間か比較不可を示す。
2. **計算は正しいか**：合計、寄与率、差、倍率を元の数値から再計算する。表示用に丸めた率から倍率を計算しない。ツールをまたぐ比較では検索エンジン、URL範囲、日付境界等の差も確認する。
3. **原因の説明が飛躍していないか**：端末差や前後差だけで不具合・因果を断定しない。重要な結論について別の説明と反証を検討し、確認済み・仮説・未確認を区別する。
4. **基準は適切か**：BtoB／BtoC等の利用者指定を反映し、ベンチマークの分母、母集団、調査時期、平均・中央値を確認する。比較できない値は参考に留め、その差を達成可能な改善余地と断定しない。
5. **提案は実行できるか**：根拠と対象が結び付き、変更内容が具体的か。効果の試算には仮定を示し、予測や保証と区別する。計測を追加する提案には、何の判断が可能になるかを示す。
6. **関連レポートは整合しているか**：使用したデータ・前提・版を内部に記録し、接続状態、CV定義、結論、施策の優先順位を照合する。変更の影響先だけを見直し、依頼外の全再生成はしない。未更新の関連版はその旨を利用者へ伝える。
7. **読む人が判断できるか**：重要な発見と優先事項を先に示し、根拠へ辿れるようにする。定型宣言・重複・小さすぎる図表を避ける。HTMLとPDFはそれぞれの閲覧環境で確認する。

以上は現在のエージェントが実施するレビュー基準であり、自動検査の実装済み範囲を示すものではない。既存の機械検査が成功したことだけで分析品質を保証しない。フィードバックで発見した失敗は、今回の修正に加え、適切な共通手順・プロンプト・計算処理・回帰テストへ反映する。
