# レポートの文章ルール

クライアントが読むレポート、提案書、サマリーの文章はこのファイルに従う。美文を作ることより、読み手が事実、解釈、次の行動を短時間で判断できることを優先する。

作成前・分析途中の相談、レポート別の完成基準、根拠と関連レポートの照合は [レポート作成時の相談と分析品質](./report-consultation-quality.md) に従う。利用者に確認すれば結論が変わる情報を、完成後の「要確認」へ先送りしない。

計測チェックの公開本文は、自動判定できる項目の5列表（カテゴリ／確認項目／判定／結果／対応事項）、APIで取得できない設定を集約した目視確認ブロック、具体的な異常・要確認、改善順で構成する。項目は `02_basic_measurement/measurement_design/standards/audit-items.md` を正本とし、APIで取得できない設定を推測で○にしたり、同じ理由の△行を並べたりしない。自動収集・拡張計測・推奨・カスタムの各イベント一覧は載せない。イベントの欠落、異常比率、日本語イベント名、二重送信など、具体的な問題がある場合だけ「要対応・要確認」に掲載する。確認済みのコンバージョンポイントは一覧表にせず、直近30日の全イベント件数で受信できた件数をサマリーに示し、0件・類似名受信などの異常だけ詳細に出す。全イベント件数を取得できていない場合は0件にせず未確認とする。機械37項目・目視19項目は内部監査として保持するが、正常・適用外を含む全56行は本文へ転記しない。フォーム通過率や問い合わせ減少の考察は計測チェックへ加えない。

## 書く前に決めること

1. その面で伝える結論を1つに絞る。
2. 結論を支える数値・出典・観察事実を先に選ぶ。資料にない事実や数値は作らない。
3. 「結論 → 根拠 → 解釈 → 次の行動」の順で骨組みを作る。すべての節に同じ型を強制せず、重要な話に紙幅を使う。
4. 結論へ直接関係しない予備知識、検討過程、定型的な前置きは本文から外す。
5. 利用者が会議や打ち合わせを明示していない限り、「次の打ち合わせで決めること」「MTGで握る論点」の節を作らない。未確認事項が判断に必要なら、該当する結論の直後に「要確認」として書く。
6. 利用者が求めていない付録は作らない。出典は本文の該当箇所にリンクし、全量の根拠台帳や中間成果物は社内用フォルダに残す。付録を付けるのは、本文から分離しないと理解できない明細があり、利用者が必要とする場合だけ。
7. サイト改善レポートは「このレポートで分かること」を置かず、改善方針から始める。詳細は `docs/site-improvement-report-contract.md` に従う。他のレポートでも内容を予告するだけの表紙・見出しを強制せず、対象と結論を端的に示す。

## 表と本文の順序

- 表の読み方、結論、判断、指標の定義、次の行動は表の前に置く。読み手が判断軸を理解してから根拠表を読める順にする。
- 表の前後に説明が分かれている場合は、重複を除いて表の前へまとめる。特に、優先候補や実装順を表の後で初めて示さない。
- 表の後に置くのは、出典、脚注、行単位の補足など、表を読んだ後で参照する情報に限る。データ制約が判断に影響する場合は、原則として表の前の説明または表内の留意点へ入れる。
- 1つの章に複数の表がある場合は、各表に内容が分かる小見出しを付ける。「小見出し＋説明＋表」を1つの意味単位にし、別の面へ分けない。
- HTML/PDFでは、前置きの説明と表を同じ面へ置く。原稿にやむを得ず表後の脚注がある場合も、表との間では改ページしない。

## 日本語の書き方

- 市場・顧客理解レポートの本文は、クライアントがそのまま読める「です・ます調」に統一する。表のセルは名詞句でよいが、本文・注記・カスタマージャーニーの説明文へ常体を混在させない。
- 表題と最初の一文で対象と結論を示す。「本レポートでは」のような空の前置きから始めない。
- 見出しは「分析」「考察」だけにせず、何について何が分かったかを直接書く。断定できない場合は「候補」「要確認」と区別する。
- 原因と結果、前後関係は文章でつなぐ。箇条書きは、同じ階層の項目を並べるときに限る。
- 用語を出す前に、何が起き、判断や実務にどう影響するかを普通の言葉で書く。読み手の判断に不要な用語は出さない。
- 1文はおおむね50〜60文字を目安にし、主語と述語を近づける。80文字を超えたら分けられないか確認する。
- 「以下にまとめます」「重要なのは」「このように」など、無くても意味が変わらない定型句を削る。
- 「この表ではPVだけを掲載します」「記事を一律に低CVRと評価しません」のような、作り手の掲載方針・評価方針を本文で宣言しない。代わりに、数値差、そこから分かること、判断に足りないデータ、次の確認を直接書く。
- 同じ書き出し、同じ長さ、同じ三段構成を3回以上繰り返さない。情報の重みに合わせて長さと形を変える。
- 強調の太字は結論と判断に必要な語だけに絞る。1段落の大半を太字にしない。
- 「XではなくY」を定型にしない。結論のYを先に書き、必要なときだけXとの違いを補う。

## 事実と推察の分け方

### チャットや制作工程の事情を本文へ持ち込まない（全レポート共通）

- チャットでの指摘への返答、旧版の反省、修正経緯、内部システムの都合、掲載方針の宣言は本文に書かない。必要なら非公開の履歴・引き継ぎへ保存する。
- 「AI分析だけに限定しません」「ご指摘を受けて変更しました」「指定された3社で作り直しました」のような会話への応答ではなく、対象範囲・分析結果そのものを書く。例：「対象市場は国内法人向けの計測整備・データ基盤構築・分析活用支援」。
- ヒアリングで得た事業情報は利用するが、会話の往復を再現しない。出所が重要なら「ヒアリング情報（確認日）」と簡潔に示す。
- 調査期間・対象、データ欠損、未検証の仮説、情報源の偏りなど、読者の判断に影響する制約は削らない。方法・AI利用の開示は必要な調査方法欄へまとめる。
- 内部の根拠分類・確認状態・制作過程を、利用者向け本文や見出しへ書かない。`会社側仮説`、`利用者未確認`、内部ID、英字の根拠分類は非公開の作業記録だけで使う。必要な留保は表下の `<small>※ ...</small>` または末尾の前提・制約欄へ置き、考察本文は利用者が判断できる事実と意味を先に書く。
- 最終確認で「このチャットを読んでいない人にも必要な文か」を全章に問い直す。機械チェックは候補検出であり、この意味の確認を代替しない。
- 「接続済み」「保存済みファイル」「APIから返った行」など取得・保存の内情や、「分析の根拠から外します」という処理方針を説明しない。比較できない場合は「前年同期のデータ範囲を確認できないため、前年比は算出できません」のように、読者が判断できる範囲へ言い換える。欠損の制約そのものを隠さない。

- 事実: 数値、対象期間、出典を付ける。表やグラフと本文の数値は一致させる。
- 推察: 「推察」と分かる言い方にし、根拠と別の可能性を示す。「可能性がある」を毎文に重ねない。
- 未確認: 判断に必要な情報と、誰に何を確認するかを書く。未確認のまま数値や因果を補完しない。
- 提案: 誰が、何を、どの順で行うかを書く。効果を断定する場合は比較方法も決める。

## 書いた後の確認

1. 表題、見出し、図表だけを読み、全体の論理が通るか確認する。
2. 各数値を元データと突合し、合計、単位、分子・分母、期間を確認する。
3. `uv run python tools/report_quality_check.py <report.md>` を実行し、警告の文だけを人またはAIエージェントが読み直す。機械的な一括置換はしない。
4. デザインと図表は `common/report_export/design_system/design-system.md` と `visualization-guidelines.md` に従う。
5. `report-consultation-quality.md` の「結論を出す前の検査」を実施する。文章検査の警告ゼロを、数値・因果・提案の妥当性が検証済みという意味にしない。
