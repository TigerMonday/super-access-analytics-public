# 標準実行順序と共通の決まりごと

実行順序・成果物の置き場所・命名規則・LLMの使い方の方針は、このファイルに1つでまとまっている。
各エージェントの手順書にも同じ内容が書かれている場合があるが、**食い違ったらこのファイルの記載を優先する**。

---

## 1. 利用の前提（はじめて使う人はここから）

- **サイト（会社・ブランド）ごとにこのリポジトリをクローンして使う（1サイト＝1クローン）**。複数のサイトを見たい場合は、サイトの数だけこのリポジトリを別のフォルダにcloneする。1つのcloneの中に複数サイトのデータを混在させない運用にしている。
- クローンで手に入るのは**コードとプロンプトだけ**。実データ（GA4から取得したデータ、生成したレポート、認証鍵）はクローンの外、または `.gitignore` で除外された場所に置かれる（§4・§6）。
- 同じクローンのフォルダを、複数のAIエージェントのセッションで同時に触らない。同じ出力ファイルに書き込みが競合したり、片方の作業が上書きされたりする原因になる。
- ツール本体の更新は `git pull` で行う。手順書・スクリプトを直したいときはPRを作って取り込む運用でもよいが、個人で使う分には手元で直接直しても構わない。

## 2. 実行順序（標準チェーン）

```
01 コンテキスト登録（新規サイトはまずここ。client_id の発番点）
 ↓
02 計測設計
 ↓
03 市場・顧客理解（競合・市場・Web調査→3C→ペルソナ→CJ）
 ↓
04 基本分析（GA4＋Search Consoleの事実を取得し、03の前提と統合して解釈・レポート化）
 ↓
05↔06 CVR改善チェーン（①全体施策 → ②施策〈対象ページ選定＋改善案〉。
        各段で 05=作る側 → 06=検証する側 の順に必ず通す）
 ↓
07 アドホック分析（随時。03/04の成果物を前段として読む）
```

- どのエージェントも開始時に 01 の `load_context('{client_id}')` で前提を補完し、**01にある情報は人に聞き直さない**。未登録・情報不足の扱いは §2-1（軽量受付フロー）に従う。フル登録は、利用者が「サイト情報を一通り登録して」などと明示した場合だけ実行する。
- 各エージェントは完了時に 01 の `append_finding(client_id, *, agent, summary, findings=None, outputs=None)` で作業履歴を書き戻す。例: `append_finding('sample-client', agent='04_parameter_management', summary='流入パラメータを確認', findings=['UTM表記ゆれを検出'], outputs=['outputs/sample/04_traffic/docs/report.md'])`。`agent` 名は `{テーマ番号}_{エージェント名}`（例: `04_parameter_management`）で統一する。
- 標準の一括実行では、市場・顧客理解を先に行い、その成果物を基本分析の解釈に使う。基本分析の内部では、GA4・Search Consoleの**事実取得を先に完了してから**市場・顧客前提を読み合わせる。外部仮説に合わせて数値の取得条件を変えることを防ぎつつ、事業・顧客文脈を踏まえた考察にするためである。03を実行しない軽量運用では01→02→04だけでもよいが、レポートには市場要因を断定せず検証仮説として残す。
- 03 市場・顧客理解を開始するときは、`03_external_research/web_research/service-understanding.md` の事前確認を最初に実行する。公開情報から分からない項目を1〜3問へまとめて利用者へ質問し、質問を送る前の `not_asked` と、送った後の `awaiting_reply` を区別する。未質問を「利用者未回答」と扱わない。候補探索は並行できるが、確認完了前に統合レポートを確定版として配布したり、05へ確定版として渡したりしない。
- セットアップ完了後や個別依頼で基本分析・サイト改善案を希望された場合は、既存成果物を確認し、未実施なら**「市場・顧客理解 → 基本分析 → サイト改善案」**の順を推奨として案内する。利用者が基本分析だけなど軽い進め方を明示した場合は、その希望を優先してよい。

## 2-1. 軽量受付フロー（未登録・情報不足のときに何を聞くか）

`01_context_management/prompts/context-manager.md` のフル対話登録（事業内容・ターゲット像・背景まで聞く）は重い。**計測チェックだけしたい・基本分析だけしたい**利用者に対しては、そのエージェントを動かすのに**最低限必要な項目だけ**を聞き、01に保存して次回から聞き直さない軽量フローを使う。フル登録は利用者が自然文で明示した場合だけ行う。

**共通の流れ**（各機能の正本にある「自然文で依頼されたときの受付」はこの流れを実装する。保存API は `01_context_management/src/context_store/writeback.py`）:

1. `list_clients()` と依頼文を確認する。既存の client_id が明示されている、または登録済みURLと一致する場合は、その client_id を確定して `load_context(client_id)` を読む。
2. 対象が未登録なら、**最初に対象サイトURLを聞く**。サイト名や保存用識別名を白紙の入力項目として先に聞かない。
3. URLを取得したらトップページのタイトル・OG情報・運営者表記と、取得済みならGA4プロパティ表示名を使って、サイト表示名と client_id の候補を作る。
   - client_id は `^[A-Za-z0-9_-]+$` の保存用識別子。ドメインまたは確認できたブランド名から生成し、`list_clients()` と重複しないことを確認する。
   - サイト表示名（`profile.client.name`）は成果物・レポートに表示する名前。読み取れた候補を使い、利用者へ白紙で聞き返さない。サイトを読めない、候補が複数ある、GA4表示名と矛盾する場合だけ確認する。
   - 利用者には必要に応じて「対象URLは〇〇、表示名は△△、識別名は `example` として登録します」のように候補をまとめて示す。修正が無ければ個別回答を求めない。
   - `writeback.ensure_client_registered(client_id, name)` で最小登録し、続けて `writeback.save_business_profile(client_id, site_url=site_url)` でURLを保存する。サイト名をclient_idから機械的にコピーしない。
4. 下表からそのエージェントに必要な項目を確認し、**01に無いものだけ**をまとめて1回で質問する（3つ足りなければ3つ一括。1つずつ往復しない）。
5. 聞いた内容を `writeback.save_measurement_ids()` / `writeback.save_kpi_info()` で01に保存する（次回から聞かれない）。
6. 実行する。

GA4プロパティIDは、サービスアカウントがアクセスできるプロパティ一覧から候補を出してよいが、**それは答え合わせの補助に留め、聞かずに確定しない**（利用者に確認してから保存する）。

**保存の実行例**（聞き終えた値を01に書き戻す。プレースホルダはユーザーから確認できた値に置き換える）:

```bash
cd 01_context_management
uv run python -c "
from context_store.writeback import ensure_client_registered, save_business_profile, save_measurement_ids, save_kpi_info
ensure_client_registered('{client_id}', '{サイト名}')
save_business_profile('{client_id}', site_url='{対象サイトURL}')
save_measurement_ids('{client_id}', ga4_property_id='{GA4プロパティID}')
save_kpi_info('{client_id}', key_events=['{GA4イベント名1}', '{GA4イベント名2}'])
"
```

`ensure_client_registered` は未登録のときだけ実行すればよい（既存の `profile.yaml` を壊さない設計だが、聞き直しを避けるため未登録時のみでよい）。`save_business_profile` には確認済みURLを渡す。`save_measurement_ids` / `save_kpi_info` は該当する項目を聞けたときだけ呼ぶ（値が無いキーワード引数は省略してよい。省略した項目は既存値を保持する）。
確認済みCV一覧を入れ替える場合は、追記ではなく `save_kpi_info('{client_id}', key_events=[...], replace_key_events=True)` を使う。空の一覧と `replace_key_events=True` を渡すと既存一覧をクリアする。

**「無いと動かない」と「あると精度が上がる（無くても実行はできる）」の区別**: 前者は必須質問とする。後者は一律の受付必須項目にしないが、結論・対象顧客・優先順位・実行可否を左右する未確認情報は作成前または分析途中で積極的に相談する。既存context・会話・資料で分かることは聞き直さず、判断に効く質問を原則1〜3問に絞る。回答待ちでも影響しない分析は進め、影響する結論は保留または条件付きとする。具体的な相談方法と4レポートの完成基準は [レポート作成時の相談と分析品質](./report-consultation-quality.md) に従う。計測チェックはKPI対応表を公開本文に持たないが、業務上のコンバージョンポイントは「何を取得できていてほしいか」を決める前提なので、01に無ければ一度だけ確認する。GA4イベント名が利用者にも不明な場合は、受信イベント名・GTMタグから候補を示して確認し、候補を自動確定しない。回答が不明でも実行は止めず、成果計測は未確認と明示する。確認済みのCVは内部監査・計測設計で再利用し、変更の兆候や矛盾がある場合だけ再確認する。詳細は下表の該当セル参照。

## 3. client_id 規約

- 運用はサイトごとにリポジトリをクローンして使う（1サイト＝1クローン）。01コンテキストストアはそのクローンにおける名簿で、新しいサイトは最初に01へ登録し、以後そのクローン内のすべてのエージェント・出力フォルダ・ドキュメントで同じ client_id を使う。
- `01_context_management/context/` はGit管理外なので、名簿はクローンを跨いで共有されない。別のクローン（＝別のサイト）では改めて01登録が必要になる。
- 形式は `^[A-Za-z0-9_-]+$`。client_id はそのクローン内で一貫させる（例: `example-shop`。表記が揺れそうな場合は01の `aliases` で吸収する）。
- ドキュメント上のプレースホルダ表記は `{client_id}` に統一する。
- **01の `context/` と `outputs/` はなぜ分かれているか**: 01は「そのサイトについて分かっていること」（GA4プロパティID・CVの定義・過去の施策・gotchasなど、毎回聞き直さずに全エージェントが参照する前提情報）を貯めるレジストリで、`outputs/` は「その前提を使って実行した結果」（レポート・分析ファイル）を置く場所になる。前提情報と実行結果を同じ場所にまとめる設計にはしていない（前提が成果物の中に混じると、どれが今後も参照される値でどれが単発の出力かが区別できなくなる）。

## 4. 出力規約

### 閲覧先とフォルダ構成

レポートの入口は `outputs/{client_id}/index.html`。`{client_id}` は利用者個人の名前ではなく、対象の会社・サイトに対応する登録済みの識別名を使う。初回に確認し、開発用・テスト用の名前を実案件へ流用しない。日本語のサイト表示名は `profile.client.name` に別途保存する。

```text
リポジトリ/
├─ outputs/{client_id}/
│  ├─ index.html                         閲覧用のレポート一覧
│  ├─ 02_measurement/docs/               計測チェック
│  ├─ 03_research/customer_understanding/ 市場・顧客理解
│  ├─ 04_traffic/                        基本分析
│  ├─ 05_cvr/                           サイト改善
│  └─ _data/                            取得データ（内部用）
├─ 01_context_management/context/{client_id}/ 前提情報・作業履歴
└─ 02_basic_measurement/measurement_design/{client_id}/inputs/
                                         計測設計の入力情報
```

実施した分析・指定された出力形式だけが作成される。各テーマ内の `_past/` は旧版・内部レビュー用で、最新版の閲覧先ではない。ファイル名と出力形式の詳細は以下の規約に従う。

識別名を変更するときは、出力フォルダだけでなく前提情報・計測入力の同名フォルダと現行の参照先を合わせる。移動先の不存在を確認し、既存データを上書きしない。旧版・取得データ・利用者のメモは一括置換せず保存する。変更後は一覧を再生成し、各レポートと前提情報のリンク、登録情報の読み込みを確認して、新しい閲覧先を案内する。検証記録のハッシュは名称変更を理由に無条件で更新しない。

- 最終成果物・中間成果物は **リポジトリルート直下の `outputs/{client_id}/`** に置く。ルートは `git rev-parse --show-toplevel` で求める。サブフォルダに `cd` してから実行しても出力先は変わらない（カレントディレクトリ基準にすると、実行場所によって成果物が散らばる。実際に散らばった）。
  - **出力先をユーザーに尋ねない**。実行時に出力先の明示指定があった場合のみ、そちらを優先する。
- **テーマごとの置き場所**は `outputs/{client_id}/{テーマ番号}_{略称}/`（例: `02_measurement`・`03_research`・`04_traffic`・`05_cvr`）にまとめ、他テーマの成果物と混ぜない。フォルダの内部構成（サブフォルダの有無・階層の深さ）は各テーマの手順書が決めてよい（下記の規約はどの深さでも成り立つように書いている）。
  - 02（計測設計）: `outputs/{client_id}/02_measurement/`。`docs/check-report.md`（クライアントが見る唯一の計測チェックレポート）は `review` 実行のたびに再生成される。公開本文は自動判定の5列表、APIで取得できない設定をまとめた目視確認ブロック、具体的な異常・要確認、改善順に絞り、受信イベント一覧や用途推定は載せない。イベントの欠落・異常比率など具体的な問題だけを指摘する。機械37項目・目視19項目は内部監査として全件保持するが、正常・適用外を含む全56行を本文へ転記しない。フォーム通過率や問い合わせ減少の分析は含めない。上書き前に旧版（HTML変換していれば `.html` も同様に）を `docs/_past/{YYYY-MM-DD_HHMMSS}_check-report.md` へ退避してから書き直す（規約2。03・04・05と同じ形。02はPythonコード生成のため `renderer.archive_check_report_before_overwrite` が担う）。指摘への確認・対応は `docs/check-report-notes.md`（無ければ作る。あれば絶対に上書きしないファイル。退避・上書きの対象外）に書く。詳細は `02_basic_measurement/measurement_design/README.md`
  - 03（市場・顧客理解）: `outputs/{client_id}/03_research/{テーマフォルダ}/`。テーマフォルダ名は**対象**で決める（日付・実行回数は含めない。01登録クライアント自身が対象なら`customer_understanding`固定、それ以外の対象なら対象名のスラッグ）。統合レポート`00_3c_persona_journey_report.md`は規約1・2の対象（ファイル名に日付を入れず、同じ対象を再実行するときは上書き前に`{テーマフォルダ}/_past/`へ退避）。子スキルの個別成果物は`{テーマフォルダ}/data/child_reports/`に社内用として保存する。利用者向け統合レポートに付録として転記せず、結論の判断に必要な出典だけ本文の該当箇所にリンクする（トップレベルには置かない）。詳細は`03_external_research/web_research/external-research-coordinator/SKILL.md`「出力フォルダの決め方」
  - 04（基本分析）: `outputs/{client_id}/04_traffic/basic-analysis-report.md`
  - 05↔06（CVR改善チェーン）: **確定版は `outputs/{client_id}/05_cvr/cvr-improvement-plan.md` 1本だけ**。段ごとの個別確定版（旧 `1_overall-strategy` / `2_target-pages` / `3_abtest-plan`）は作らない。確定した段だけを束ねた内容を、段が確定するたびにこの確定版へ直接反映する（作り方・タイミングは§4-5）。分析・レビュー・差し戻し前の途中成果物はすべて `05_cvr/_past/` に置く（規約2）。**チェーンの現在地判定はこの `05_cvr/_past/` 配下の固定ファイル名を基本にするが、`08-target-page-plan-final.md`は要修正時にも判定記録として作られるため、存在だけで②確定としない。総合判定が両方妥当・差し戻しなしであることも確認する**（`05_campaign_optimization/run.md` 参照）
  - 01（コンテキスト管理）は成果物を outputs に出さず、`01_context_management/context/{client_id}/` のレジストリに登録する工程
  - 取得した生データ: `outputs/{client_id}/_data/{ソース名}/`（テーマ内に持つ場合は `{テーマフォルダ}/_data/` でよい。例: `02_measurement/_data/`）。取得日プレフィックス付きで複数残す（06の検算材料になる）
- **成果物には2種類ある**。エージェントが実行のたびに作り直す**生成物**（レポート・分析ファイルなど）と、**人が書き込むファイル**（指摘の対応記録・下書きへの書き足しなど。例: 02の `check-report-notes.md`・`questions.draft.md`）。**以下の規約1・2は生成物だけに適用する。** 人が書き込むファイルは「無ければ作る。あれば絶対に上書きしない」を守る。03・04・05・06・07など他のテーマで同種のファイルを持たせるときも同じ扱いにする（テーマ固有の特別ルールにしない）。
- **規約1（生成物のファイル名に日付を入れない）**: 生成物のファイル名は、そのテーマ・その段の「今出せる最新の答え」を1つの名前で指す（例: `check-report.md`・`basic-analysis-report.md`・`cvr-improvement-plan.md`）。いつ作られたかはレポート本文のヘッダに書く。ファイル名だけで最新版を判別する必要をなくすのが狙い。
  - 例外1: 同じレポートの新旧ではなく、**対象・調査テーマそのものが異なる**ため複数が並存してよい場合（例: 03の対象ごとのテーマフォルダ。「自社」と「競合A」は別テーマとして両方残る）は、フォルダ名を対象・テーマで分けてよい。これは「版の新旧」ではなく「別の対象を区別する識別子」なので対象外とする。**実行日は入れない**（同じ対象・同じテーマの再実行は「版の新旧」なので規約1・2の対象に戻り、`_past/` への退避で扱う）。
  - 例外2: `_data/` 配下の生データは「レポートの再生成」ではなく取得の記録なので、取得日プレフィックス付きで複数残す（従来通り。上のリスト参照）。
- **規約2（上書き前に `_past/` へ退避）**: 規約1の対象ファイル（生成物）を再実行で上書きする前に、既存ファイルを `_past/{YYYY-MM-DD_HHMMSS}_{元のファイル名}` にリネームして退避してから、新しい内容を元のファイル名で書く。差し戻し・レビューの経緯（なぜこの結論になったか）は次工程・後日の判断材料になるため消さない。**テーマ固有の退避フォルダ名（旧 `_review_rounds/`・`_rework_rounds/` 等）は使わず、`_past/` に統一する。** 人が書き込むファイルは退避・上書きの対象外（そのまま触らない）。
- **規約3（`index.html` の再生成）**: `outputs/{client_id}/index.html` は、クライアントが全レポートをブラウザで横断するHTMLの閲覧入口とする。`common/report_export` で `outputs/{client_id}/` 配下へHTMLまたはPDFを書き出すと、変換成功後に自動で再生成される。HTMLを主リンクとし、同じフォルダ・同じbasenameのPDFがあれば副リンクとして表示する。再生成時には各HTMLのサイドバーも全レポート共通の目次へ更新し、レポート名ごとのアコーディオンにする。現在表示中のレポートだけを開き、ほかは閉じる。Word・Excel・Google形式だけ、またはMarkdownだけの更新では自動再生成しない。HTMLを直接作成して `report_export` を通さない場合と、入口を修復する場合は、実在するフォルダ・ファイルを走査する共通ツール `common/report_index` を手動実行する（使い方は `common/report_index/README.md`）。

  ```bash
  python common/report_index/build_index.py "outputs/{client_id}"
  ```

  特定のテーマがまだこの規約（規約1・2）に追いついていなくても、`report_index` は実在するものを拾って一覧を作る（追随を待たない）。生成された `index.html` が利用者の入口になる。各レポートが何を答えるものか・いつ作られたかが分かる一覧を出し、見た目は `common/report_export/design_system/design-system.md` のコアCSS・共通部品に揃える（HTMLを直接書くときの適用ルールは§4-3）。**このindex.htmlは1エージェント専用ではない。** 置き場所が `outputs/{client_id}/` 直下という1か所（上記の通り）であることそのものが、そのクライアントについて実行済みの全テーマ（02・03・04・05…）を1本の一覧として横断できる理由になっている。どのエージェントを実行してもこの1本を再生成するだけでよく、テーマごとに別の入口ページはできない。あわせて、成果物とは別管理の01の前提情報レジストリ（`01_context_management/context/{client_id}/`。§3「01の`context/`と`outputs/`はなぜ分かれているか」参照）の置き場所も、この一覧から案内する（中身は展開しない。「ここにある」と示すだけ）。README側の案内は「成果物はどこに出るか」節（README.md）。
- **実行完了時に、主要成果物のフルパスを必ずユーザーへ表示する**。どこに出力されたか分からなくなるのを防ぐため。
- **規約4（完了時の案内は「どれが最終か」を明示する）**: パスを並べて表示するだけでは、どれを見ればいいか伝わらない（例:「保存完了」「変換済み」のようにパスが並ぶだけで、クライアントに渡す最終成果物がどちらか分からなかった事例があった）。エージェントは完了時、その回でクライアントに渡す最終成果物（規約1の生成物のうち、いま出せる最新の答え。変換した場合は変換後のファイル）のパスを「最終成果物」等の見出しで明示し、社内用のファイル（人が書き込むファイル・生データ・`_past/` へ退避した旧版）とは区別する。**チェーン（05↔06等）で、その回にまだクライアント向けの確定版が無い場合**（`_past/` 止まりの中間成果物）は、書き出したファイルを「最終成果物」と案内せず、途中経過（社内用）であることを明示する。案内は数行に収め、実行のたびに長い説明を繰り返さない。
- **規約5（クローンの外にあるファイルを使ったら出典を書く）**: 分析の材料としてクローンの外にあるファイル（クライアントから受け取った資料など）を読んで使った場合、成果物にその出典を明記する。**読むこと自体は妨げない**（手元の資料を使えるほうが分析の精度は上がる）。**ただし黙って使わない。** 対象は「クローンの外にあるローカルファイル」だけで、GA4など既定の分析材料は対象外（毎回全部並べても意味がない）。
  - **書く内容はファイルのパス・読んだ日・そこから採った内容の3点。** 03の付録がWebの出典を「事例名へのリンク、取得日」の形でURL・取得日を書いているのと同じ考え方で、ローカルファイルは次のように対応させる。

    | Webの出典 | クローンの外にあるファイル |
    |---|---|
    | URL | ファイルのパス |
    | 取得日 | 読んだ日 |
    | 引用した内容 | そこから採った内容 |

  - **識別子は振らない。** 01配下の記録（`barrier_id`等）に識別子を振れるのは、そのファイルの構造をこちらが管理しているからであり、クローンの外にあるファイルは管理外（中身が変わる・消えることがある）で、識別子を振ると実際には無い精度があるように見えてしまう。ファイルパスと読んだ日だけで足りる。
  - **「そこから採った内容」の粒度は揃えなくてよい。** Webの引用は発言をそのまま載せることが多いが、クライアント資料は「事業構造の理解に使った」のような要約でもよい。何に使ったかが読んで分かれば足りる。
  - **書く場所はテーマごとの成果物にある出典・付録の節**（例: 03の「8. 付録（根拠資料）」）。無いテーマは成果物の作りに合わせて置き場所を決める。
- **ファイルに書いてから次工程へ進む**。ファイルに書かれていない成果物は存在しないものとみなす。
- `outputs/` は意図的にgit管理外（GA4から取得した実データや、そこから作ったレポートには機密情報が含まれるため）。人に共有したい確定成果物は、社内の共有フォルダなど自分たちの運用に合わせた場所へ個別にコピーする。

## 4-2. 成果物の書き出し形式

- 成果物はMDを正として作る。納品や共有でHTML・PDF・Word（docx）・Excel（xlsx）が要るときは、そこから変換する。
- 変換後のHTML・PDF等は、正本のMarkdownと**同じフォルダへ同じbasename（拡張子だけ違う）**で保存する。形式別の集約フォルダへ複製しない。これにより、`index.html` はHTMLと同名PDFを1件のレポートとして確実に対応付けられる。
- **変換するかどうかは「一度だけ聞いて、覚えておく」方式**（§2-1の軽量受付フローと同じ考え方）。優先順位は次のとおり:
  1. **依頼文に形式の指定があれば、それを最優先で使う**（例:「計測チェックをHTMLで出して」）。この実行だけの指定であり、01の既定は変更しない。計測の `review` / `run` では `--output-formats html` 等を渡す。「今回はMDのみ」は `--output-formats md` で自動変換を抑制する。指定がなければこの引数を省略する。
  2. 指定が無ければ、**01に保存された既定の出力形式**（`profile.yaml` の `preferences.output_formats`）を使う。空リスト（MDのみと回答済み）なら変換しない。
  3. 01にも無ければ（`ClientContext.output_formats` が `None` ＝一度も聞いていない）、§2-1の他の質問とまとめて**1回だけ**聞く（「MDのみでよいか、HTML/PDF/Word/Excelのどれかに変換するか、Googleドキュメント/スプレッドシートに書き出すか」）。**毎回聞かない。** 答えは `writeback.save_output_format_preference(client_id, output_formats=[...])` で保存し、次回からは聞き直さない。
  4. **対話で確認できない実行（`claude -p` 等のヘッドレス実行・スケジュール実行など、応答を待てない無人実行）で、01にも既定が無い場合**: 質問できないので、その回は**MDのみ**として進める（HTML/PDF等を仮の既定として自分で選ばない。「無くても動く。既定はMDのみ」という本節冒頭の原則どおりにする）。**このとき `writeback.save_output_format_preference()` は呼ばない**。無人実行中の間に合わせの判断を、対話で得た本人の回答であるかのように01へ永続化しない。次に対話可能なセッションで実行されたときに、あらためて1回だけ聞く機会を残す。完了時の表示に「出力形式は未確認のためMDのみで出力した。対話セッションで再実行すると形式を選べる」旨を一言添える。
- 変換の対象は**人が読む成果物のみ**。`outputs/{client_id}/_data/` 配下などの中間生データは変換しない。**レビュー専用の中間ファイル**（次工程のAIエージェントが読む検算・レビュー記録で、クライアント向け確定版に反映されないもの。例: 05↔06 CVR改善チェーンの `05_cvr/_past/02-analysis-review.md` や差し戻し経緯を含む `-final` 系ファイル）も変換対象外（常にMDのみ）。**変換されるのはクライアント向けの確定版・最終成果物だけ**であり、差し戻しの往復に使う内部ファイルまで変換すると、人が読まないファイルの変換に費用と待ち時間をかけることになる。
- **既定の出力形式が設定されている（空リストでない）場合**、各エージェントは完了時にMDを書き出したあと `common/report_export` で自動的に変換し、変換後のファイルの絶対パスもあわせて表示する。**設定が無い、またはMDのみの場合は従来どおりMDのパスだけを表示する**（自動変換もしないし、変換できる旨を毎回案内する必要も無い。選ぶ機会は受付時の1回で足りる）。
- **変換・書き込みに失敗しても、分析成果物のMarkdownは捨てない。** 変換ツールが落ちても分析自体は既にファイルに書けているので、その回を失敗扱いにはしない。ただし黙って無かったことにはせず、完了時の案内に「MDは出た、○○への変換／書き出しは失敗した（理由）」と一言添える。02（`run.py`）はこれを `common/report_export_bridge` の `ExportOutcome.warnings` として受け取り、そのまま案内に載せる。`run.py` を持たないエージェントは、変換コマンドの終了コード・標準エラーを自分で確認し、同じ形で案内する。
- 変換の標準手段は `common/report_export`。使い方の正本はその `README.md`。MD1ファイルを渡すと選んだ形式に変換し、生成ファイルの絶対パスを表示する。`--to` はカンマ区切りで複数指定できる（例 `html,pdf`）。単発変換は「このレポートをPDFにして」などと自然文で依頼する。
- **`gdoc`/`gsheet` は「変換」ではなく既存のGoogleドキュメント／スプレッドシートへの書き込み**で、書き込み先URL（`profile.yaml` の `preferences.google_doc_url` / `google_sheet_url`。`ClientContext.google_doc_url` / `.google_sheet_url`）が無いと成立しない（サービスアカウントは自分でファイルを作れないため）。**URLが無ければその形式だけを `--to` から外して諦め、他の形式の変換は続ける**（前項の「失敗しても捨てない」と同じ考え方）。
  - 02（`run.py`）はこの判定とコマンド組み立てを `common/report_export_bridge`（`export_if_configured()`）が担う。詳細はそのREADME。
  - `run.py` を持たない03・04・05・06・07は、AIエージェント自身が01の設定を読み、次の形でコマンドを組み立てて実行する（`common/report_export` はgdoc/gsheetをネイティブに扱えるため、`report_export_bridge` を経由しなくてもこれで完結する）:

    ```bash
    # 1. 01の設定を読む（output_formats・google_doc_url・google_sheet_url・accent_color・logo_path）
    cd 01_context_management
    uv run python -c "
    from context_store.loader import load_context
    ctx = load_context('{client_id}')
    print('output_formats:', ctx.output_formats)
    print('google_doc_url:', ctx.google_doc_url)
    print('google_sheet_url:', ctx.google_sheet_url)
    "

    # 2. 読んだ output_formats から --to を組み立てて変換する
    #    （gdoc/gsheetは対応するURLが無ければ --to から外す。accent_color/logo_pathがあれば
    #    --accent-color/--logo も追加で渡す。詳細は下記のブランド設定の項）
    cd ../common/report_export
    uv run python -m report_export {MDの絶対パス} --to html,gdoc \
      --output-dir {MDのあるフォルダの絶対パス} \
      --gdoc "{google_doc_urlの値}"
    ```
- HTMLとPDFはデザインシステムに沿って見た目が揃う。Excelは表を中心に展開する（文章は概要シートにまとめる割り切り）。文章の正本は `docs/report-writing-style.md`、デザインの正本は `common/report_export/design_system/design-system.md`。表・グラフ・図解の選び方は `common/report_export/design_system/visualization-guidelines.md` を正本とし、レポート作成前に3ファイルを読む。数がない定性情報を棒・円・レーダーへ変換せず、比較表・平らな比較ブロック・フロー図を使う。
- **利用者が自社ブランドカラー・ロゴに変えている場合**は、01の `profile.yaml` の `preferences.accent_color` / `preferences.logo_path`（`ClientContext.accent_color` / `.logo_path`）を読み、値があれば `common/report_export` の呼び出しに `--accent-color` / `--logo` として渡す（無ければ何も付けない＝既定のゴールド・ロゴのまま）。保存は `writeback.save_brand_preferences()`。§2-1の軽量受付フローと同様、**一度設定されていれば聞き直さない**。`common/report_export` は特定のエージェント専用ではない汎用ツールのため01に依存しない設計なので、値をここ（呼び出し側）で橋渡しする。
- **PDFへの変換は初回のみ準備が要る**。PlaywrightのChromiumが未取得だと変換できない（`cd common/report_export && uv run playwright install chromium`。数百MBのダウンロード）。未取得のまま変換しようとした場合は `report_export` 側が原因の分かるメッセージ（取得コマンド付き）で止まる。既定の出力形式にPDFを選んだ利用者には、保存時にこの初回準備が要ることを伝える。

## 4-3. HTMLをClaudeが直接書くとき（report_exportを経由しない場合）

§4-2は「MD→`common/report_export`で変換」する流れの話。**それとは別に、Claudeが対話の中でHTMLを直接書く**（1枚もののレポートをその場で組む、チャットに図解を出す、`common/report_export`を通さずHTML成果物を作る、など）場面が別にある。この場合も見た目を揃える義務は同じなのに、`common/report_export`のコード（house_style.py等）を経由しないため自動では揃わない。**過去に一度、この存在に気づかずデザインシステムを無視してHTMLを自己流で組んだ事例があった**（角丸・囲み枠・独自の差し色を使うなど、design-system.mdが禁じていることをほぼ全部やった）。

**HTMLの成果物を1行でも書く前に、必ず次を行う**:

1. `common/report_export/design_system/design-system.md` を読む（存在を知らないと発生しない工程なので、読んだかどうかを自己チェックする）。
2. 同ファイルの「コアCSS」節を `<style>` の先頭に**丸ごと**埋め込む（抜粋・要約・自己流での再現はしない）。
3. デザインの原則（角丸なし／囲み枠を多用しない／カードの上辺・左辺の装飾線なし／白黒グレー主体／強調はゴールド／良い結果は緑／悪い結果・要対応は赤）を守る。表・カード・コールアウト等は同ファイルの共通部品クラスをそのまま使い、新しく似た見た目を作らない。

この規則は `CLAUDE.md` の「共通の決まりごと」にも置いてある（重複だが、読み飛ばし対策として意図的に二重化している）。**「HTMLを書く」という作業が発生した時点で、この節の存在を思い出せなかった＝読み飛ばしなので、以後は「HTMLを書く前にdesign-system.mdを開く」をチェックリストの先頭に置く。**

## 4-4. CVR改善チェーンの確定版：簡潔さの基準

05↔06 CVR改善チェーンの確定版（`05_cvr/cvr-improvement-plan.md`）は方針・決定を伝える文書であり、
04の基本分析レポートのようなデータ報告ではない。**長さの上限を文字数で機械的に決めない**（根拠を
削って文字数だけ合わせると本末転倒になる）。代わりに、次の基準で「同じ情報を二度書かない」ことを
徹底する。**05（作成）が下書きを書く時点、06（レビュー）が確定版に反映する時点の両方で守る。**

- **数値は1箇所にだけ置く**：表で示した数値を、直後の地の文でもう一度書き下さない。文章で数値の
  意味を説明したら、後続の見出しで同じ数値を再掲しない（参照するときは「（上記の通り）」で足りる）
- **検討して採らなかった選択肢は、結論より薄く書く**：「なぜ外したか」を一行添えれば足りる。比較
  した候補や迷った過程を、結論と同じ分量で再現しない
- **前提・背景は結論より短くする**：前提の分量が結論・優先順位の分量を超えたら書きすぎのサイン。
  前提の詳細を書きたくなったら、参照した資料への言及に置き換えられないか考える
- **「次工程への申し送り」は新情報だけにする**：本文ですでに述べた対象範囲・数値をそこでまとめ
  直さない。次工程が実際に困る制約（未確定事項・確認してほしいこと）だけを書く
- **見出しは新しい情報を追加するときだけ立てる**：前の見出しの結論を別の角度から言い直すだけの
  見出しは、統合するか削る

これらは、実際にある確定版が長くなった原因（表で示した数値を地の文で繰り返す／各タイプの説明と
「次工程へ渡す要点」がほぼ同じ内容を2回書く／検討過程を結論と同じ密度で書く）から起こしている。

## 4-5. CVR改善チェーン：確定版は1本だけ

05↔06 CVR改善チェーンの**確定版は `outputs/{client_id}/05_cvr/cvr-improvement-plan.md`
（HTML化する場合は同名の `.html`）1本だけ**。段ごとの個別確定版（旧
`1_overall-strategy.md` / `2_target-pages.md` / `3_abtest-plan.md`）は作らない。①だけ確定
していれば①の内容だけ、①②なら①②とも束ねた内容を書く。段が1つ増えるたびに作り直す。

**チェーンは①全体施策 → ②施策（対象ページ選定＋改善案）の2段。** 旧構成では②「個別施策
（対象ページ選定）」と③「ABテスト（改善案）」が別の段だったが統合した（経緯・理由は
`05_campaign_optimization/README.md`）。②の確定版レビューは、対象ページ選定と改善案を
**別々に**「妥当／要修正」判定し、**両方が妥当のときだけ**確定版へ反映する（片方だけ妥当な
状態では確定版を更新しない。詳細は `06_effect_verification/2_target_page_plan/creation_review/prompts/review.md`）。

①の全体方針が確定したら、そこで一度止まり、**チャットで**方針の要約・主な根拠または留意点・
次に行うことを示して、対象ページ選定とページ別改善案まで進めてよいかを明示的に聞く。確認待ちの
章をクライアント向けレポートへ置いて代用しない。利用者が了承したら `page_profile` から再開し、
②の確定まで同じ段の処理を自動で続ける。利用者向けチャットには工程番号・内部ファイル名を出さない。

**経緯**: 以前は段ごとの確定版3本と、それらを束ねた1本の確定版を両方出していた。実データで作った
ところ、束ねた1本（2,309字）が個別確定版3本（合計5,145字）と同じ内容を伝えるだけの重複になって
いた。「レポートが多すぎてどれを見ればいいか分からない」という以前の指摘に逆行するため、確定版は
1本に一本化した。

- **作るタイミングと担当**: 各段の確定版レビュー（06/creation_review、①②共通）が「妥当」と
  判定した直後に、その段の内容を**直接この確定版へ反映**する。段ごとの完成ファイルを個別に作って
  から、それらを束ねて確定版を作る、という2段構えはしない（詳細は各06レビューの入口ファイル
  `06_effect_verification/*/creation_review/prompts/review.md`）。
- **入力**: そのときまでに存在する `05_cvr/_past/` の各段の是正反映済みファイル
  （`04-strategy-final.md` / `08-target-page-plan-final.md`）のうち
  実在するものすべてを読む。確定版は毎回全体を作り直す（差分だけ追記しない）。
- **単純な連結にしない。** 段分をそのまま繋ぐと、対象サイト・確定日・参照資料のような前提が
  段の数だけ繰り返され、通しで読んだときに同じ話が何度も出てくる。確定版では次の形に組み替える:
  - 対象と成果定義は表紙に簡潔に置き、管理IDは出さない。参照資料と調査範囲は末尾に1回だけまとめる
  - 各段の内容は「結論→根拠→次工程への引き継ぎ」の骨格を保ったまま、前の段ですでに書いた文脈
    （対象サイトの説明・分析の前提など）を再掲しない
  - 段と段のつながりが分かるように、前の段の結論が次の段にどうつながったかを橋渡しの一文で補う
    （例:「①で最優先にしたサイト改善のうち、②でこのページを対象に選んだ」）
  - 「参照した資料」のような共通の末尾節は段ごとに繰り返さず、確定版の末尾に1回だけまとめる
  - 最初の「結論」または「改善方針」の直下に、`<!-- pictograms: issue,target,growth -->` と「改善課題／優先施策／期待する変化」の1行3列表を置く。HTML/PDFではピクトグラム要約へ変換する。定量比較が成立する場合だけ追加の数値グラフを使い、根拠のないスコアや疑似グラフは作らない
  - **簡潔さの基準（§4-4）は確定版にも適用する。** 特に「数値は1箇所にだけ置く」は複数段を
    束ねるときに崩れやすい（同じ数値が①と②の両方に出てくる場合は、出典を保ちながら重複を削る）
- **上書き前の退避**: 既存の `05_cvr/cvr-improvement-plan.md`（`.html` があれば同様に）は、上書き前に
  `05_cvr/_past/{YYYY-MM-DD_HHMMSS}_cvr-improvement-plan.md` へ退避してから書き直す（規約2と同じ扱い）
- **HTML/PDF変換の対象に含める**: この確定版も他のテーマの確定版と同じ扱いで、01に既定の出力
  形式があれば `common/report_export` で変換する（§4-2）。変換前に `tools/validate_cvr_artifact.py` と `tools/report_quality_check.py` を通し、HTML/PDF生成時は共通変換側でもピクトグラムの描画結果を必須検査する
- **index.htmlでの見せ方**: `common/report_index` のテーマ登録は確定版1件だけを見る（段ごとの
  個別確定版は探さない）。表示の仕組みは `common/report_index/README.md` が正本（このファイルは
  CVR改善チェーン固有の「何を作るか」を扱い、`report_index` 側はテーマ横断の「どう見せるか」の
  仕組みを扱う。役割を分けている）。
- **現在地判定への影響は無い**: チェーンの現在地判定（`05_campaign_optimization/run.md`）は
  `05_cvr/_past/` 配下の固定ファイル名を基本にする。`08-target-page-plan-final.md`だけは要修正時にも
  判定記録として作られるため、ファイル内の総合判定が「選定・改善案とも妥当」「差し戻しなし」かを
  追加確認する。段ごとの個別確定版は現在地判定に使わない。

### CVR改善チェーンの判断・成果物契約

- **04基本分析のCV数は、利用者が確認した完了イベントの `eventCount` とする。基本分析のCVRは `CVイベント数 ÷ 同じ切り口のセッション数`。** 同一セッションで複数回発火すれば100%を超え得る。「CVしたセッションの割合」ではないことを表内または考察で明記する。これは月次・チャネル・ランディングページ・デバイス等の現状把握に使う定義であり、次項の05↔06 CVR改善チェーンの定義とは混ぜない。
- **CVR改善チェーンではエンゲージ率を取得・判断・成果物に使用しない。** セッション、ユーザー確認済みのCVイベント、そのCVが発生したセッション、定義済みの導線イベント、同一LP×流入元、ページ目的で判断する。離脱率を別指標から代用せず、定義済みのページ離脱指標が無ければ「計測不能」と書く。計測チェックで機械的アクセスの疑いを判定する場合に限り、国だけで断定せず、異常な地域集中・平均エンゲージメント時間・確認できる成果・直帰率等の複数信号の補助として使用できる。
- **CVRは「ユーザー確認済みのCVイベントが1回以上発生したセッション数 ÷ 同じ期間・切り口の全セッション数」とする。** キーイベント発生回数やイベント発生回数を分子にしない。CVの業務上の意味と完了イベント名が未確認なら質問して止め、イベント名から推測しない。
- **05↔06の成果物で単に「CV件数」と示す値は、原則として上記の「CVイベントが1回以上発生したセッション数」に統一し、列名は「CVセッション」とする。** 04基本分析だけは前項のイベント数基準を使う。両者を同じ表・同じ列で混在させない。
- **大規模ページ群を一括で低CVRと判定しない。** 全体方針の段階で着地セッション上位を累積80%まで・最大50ページを既定として軽量に目的確認する。正式なpage_profileでも同じ既定を使い、CVが1件以上あるページ、CV直結ページ、有料流入の着地ページを追加する。全件一覧は生データへ保存し、個別確認したカバー率・件数・未確認範囲を明記する。
- **CVRの内部成果物（`05_cvr/_past/`）は最初のH2を「使った前提」とし、計測チェック・基本分析・市場・顧客理解の3行を書く。** 顧客理解がある場合は`barrier_id` / `stimulus_id`を記載し、対応しない場合は「対応する障壁は見当たらない」「対応する刺激は見当たらない」と書く。工程間の接続と無理な対応付けを検証するためである。**クライアント向け確定版 `05_cvr/cvr-improvement-plan.md` は結論から始め、「使った前提」や内部IDを表示しない。** 根拠は普通の言葉で本文へ織り込み、調査範囲は末尾に簡潔に置く。`tools/validate_cvr_artifact.py`を通らない成果物は次工程・確定版へ渡さない。
- **A/Bテスト案はパターン作成前に検出力を判定する。** `tools/ab_test_power.py`でベースライン、最低検出効果、必要サンプル、想定日数、許容日数を確認する。ベースラインCVが少ない場合は計測先行、必要期間が許容日数を超える場合は計測付き単一案リリースへ分岐し、A/Bテストを強行しない。比較数補正の設計が無い3群以上のテストは行わない。
- **実ページの根拠を残す。** page_profileで読んだページのURL・確認日時・HTTP状態・タイトル・主要見出し・CTA等を`outputs/{client_id}/_data/page_profile/`へ保存する。モバイルFVはURL識別子と取得時刻ごとのフォルダへ保存し、複数ページ・再撮影で上書きしない。

### 但し書きの置き場（個別確定版を無くしたことで生じる論点）

個別の確定版を無くすと、根拠や但し書きの置き場が `05_cvr/_past/` のレビュー結果だけになる。
`_past/` は次工程のAIエージェントが読む社内用の記録で、クライアントは見ない。**読み手
（クライアント）の判断や行動が変わる但し書きは、確定版の本文に残す。** 検算の内訳や検討過程の
ような、読み手の行動が変わらない記録は `_past/` に置いたままでよい（確定版に持ち込まない）。

判断基準の例:

| 但し書き | 確定版に要るか |
|---|---|
| 前提条件が変わると結論も変わる事実（例:「GA4と広告が未連携。この判断はその前提の上にある」） | 要る |
| 複数施策の実行順序を誤ると成果が変わる事実（例:「施策Aと施策Bは直列に進めない。改善余地の規模が大きく違う」） | 要る |
| 着手前に直すべき計測上の制約（例:「ページ分類が未設定」「URL計測が割れている」） | 要る |
| 検算のための分母整合の内訳 | 要らない（`_past/` にとどめる） |
| どの案をなぜ採らなかったかという検討過程 | 要らない（`_past/` にとどめる） |

**§4-4の簡潔さの基準と矛盾しない**: §4-4は「同じ情報を二度書かない」「検討して採らなかった
選択肢は結論より薄く書く」という書き方の基準であり、行動が変わる但し書きを削れとは言っていない。
簡潔にするのは重複の排除・分量配分であって、行動に影響する事実の有無ではない。上記の基準に
該当する但し書きは、簡潔に1文で書けばよく、簡潔さを理由に削ってはいけない。

## 7. 従量課金・APIクォータの原則

BigQuery分析では [BigQueryの費用確認](./bigquery-cost-guardrails.md) を必ず読む。実行前dry run、5GiB超の見積もり・上限変更に対する明示同意、実行時の課金バイト上限を必須にする。一連のクエリの合計・再試行も承認範囲に含める。同意なしに上限を上げない。

- 従量課金や月間枠のある外部API（GA4等）を大量に叩く処理は、**実行前に消費量の見積もりと上限ガードを置く**。既定値のまま無自覚に全量取得しない。
- 自然文からGA4の取得条件を作る場合は、`common/ga4_fetch` の取得計画JSONを使う。実行前に対象プロパティの `getMetadata` と `checkCompatibility` で、ディメンション・指標・フィルタ・組み合わせを検証する。AIが生成したAPI名を未検証のまま `runReport` へ渡さない。
- 非互換時に項目を黙って削除・置換しない。「アクセス数」など複数の定義がある語は、問いへの影響が変わる場合に利用者へ確認する。検証済み取得計画を生データと同じ場所へ保存し、実際の取得条件を追跡できるようにする。

## 8. 生成する文章の書き方（自分の会社が読む成果物）

市場・顧客理解は `03_external_research/web_research/market-report-contract.md` と同階層の `market-report-template.md` の固定8項目を使用する。完成後・変換前に `python tools/validate_market_report.py <report.md>` を実行し、失敗したまま配布しない。内容の正しさは別途出典と照合する。

クライアントが読む文章の構成、日本語、事実と推察の書き分けは `docs/report-writing-style.md` を正本とする。レポートのHTML/PDF変換前に `uv run python tools/report_quality_check.py <report.md>` を実行し、出た警告を読んで個別に判断する。警告は候補検出であり、機械的な一括置換はしない。

計測チェックは配布前に、リポジトリルートで `python tools/validate_measurement_report.py <report.md>` も必ず実行する。検査は、内部監査の正本が機械37項目・目視19項目を保っていることと、公開本文に5列の設定確認表・具体的な異常・改善順があることを別々に確認する。受信イベント一覧と全56項目の本文掲載は要求しない。失敗したまま配布せず、通過後も元データとの突合と表示確認を行う。

- レポート・方針・チェックリストなど、**自分やチームが読む本文**では、このツール内部のテーマ番号やエージェント識別子（`01`、`05`、`06`、`02 基本計測` のような表記）をそのまま書かない。読み手にとって、ツール内部の実行フロー名を書いても何を指すか伝わらない。
- 人が読んでわかる日本語の呼称に置き換える。目安は以下のとおり。

  | 内部識別子 | 置き換える呼称の例 |
  |---|---|
  | 02 基本計測 | 計測設計、計測チェック |
  | 03 市場・顧客理解 | 外部リサーチ、3C分析、ペルソナ、カスタマージャーニー |
  | 04 基本分析／パラメータ管理 | 基本分析 |
  | 05/1 全体施策 | 全体施策の分析・方針 |
  | 05/2 施策（対象ページ選定＋改善案） | 個別ページ施策 |
  | 06 各レビュー | 内部チェック（本文で触れる必要がある場合のみ） |
  | 01 コンテキストストア | サイトの前提情報 |

- この禁止は**本文（レポートとして人が読む文章）だけ**に適用する。エージェント間の受け渡しに使う実行手順・入出力ファイルパス・`append_finding()` の `agent=` 引数など、エージェント同士の内部連携の記述は従来どおり番号のままでよい（誤って書き換えない）。

## 8-1. 会話でユーザーに直接伝えるときの言葉づかい

§8はレポート本文の話だが、**チャットでユーザーに直接話しかける確認・報告・案内も同じ考え方で番号を避ける**。実演で「01に保存しました」とユーザーに言ってしまい、何のことか伝わらなかった事例があった。番号（`01`〜`07`）はClaudeがどの手順書・フォルダを読むかを示す内部の目印であり、利用者にとっては手がかりにならない。

- 対象は「Claudeが利用者に向かって話す文言」。会話での確認・保存の報告・次に何をするかの案内など。
- 対象外（番号のままでよい）:
  - コマンド定義・手順書がClaude自身に向けて書く指示文（例:「01に保存する」という手順の記述そのもの。これはClaudeが読むための文で、利用者に読ませる文ではない）
  - 識別子として必要な箇所（`01_context_management/` のようなフォルダ名、ファイルパス、`docs/standard-run-order.md §2-1` のような文書参照、`append_finding()` の `agent=` 引数）
- 言い換えの例:

  | 内部の言い方（NG） | ユーザーに伝わる言い方（OK） |
  |---|---|
  | 01に保存しました | この内容は覚えておくので、次回からは聞きません |
  | 01を実行します | 計測の設定をチェックします |
  | 01に登録済みか確認します | 以前の登録内容があるか確認します |

- 迷ったら、その一文が「利用者が読む/聞く文か」「Claudeが読む指示文か」で判断する。一緒くたに番号を消すと、フォルダ名やファイルパスの参照まで壊れるので、1件ずつ判断する。

### 短く・平易に

文章は短く、言い換えや前置きを削って書く。難しい言葉やAIっぽい定型表現を避け、ふだんの言葉で書く。ただし一文ずつの箇条書きにはせず、短くても自然に流れる文にする。マーケティング用語は読み手の共通言語なので、そのまま使ってよい。専門的なエンジニア用語や社内の呼び名を出すときだけ、ひとことで平易に言い換える。

## 8-2. 文書内の相互参照の書き方

利用者が上から読んで手を動かす手順書・チェックリスト（例: `docs/setup-ga4.md`）では、離れた場所にある手順・節を指すときに**番号だけで済ませない**。「3の配置場所」のような書き方は、読み手がいちいち3番を探しに戻る負担になる（試用フィードバックで「3ってどこだよ」という指摘を受けた）。

- 参照は**識別子＋見出しタイトル**の形で書く。例:「手順3（鍵ファイルを置く）の配置場所」「手順6-1（GTM側でサービスアカウントに権限を与える）」
- 見出しの文言をそのまま使う（言い換えない）。見出し側の文言を変更したら、参照している箇所も揃えて直す
- 直前の文脈で既にその手順・節の話をしていて、番号だけでも迷わない場合（同じ文・同じ段落内で言及した直後など）は簡略化してよい。段落を跨ぐ参照・別の節への参照は必ずフルで書く
- 対象は利用者向けの本文。エージェント同士の内部連携用の記述（`agent=` 引数、ファイルパスなど）は対象外（§8-1の切り分けと同じ）
