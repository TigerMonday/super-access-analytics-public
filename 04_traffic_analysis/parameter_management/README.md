# パラメータ管理エージェント

集客トラッキングの監査と**基本分析**（GA4・Search Consoleの推移、チャネル、入口ページ、
ページ、デバイス、新規/リピーター、フォーム通過率、実CVパス）を行い、
**1つの Markdown レポート**を生成するエージェント。

本ツールの **基本分析テーマ** 構成エージェント。

> Markdownを正本とし、HTML指定時は共通の `report_export` で、目次・考察ボックス・グラフを備えたHTMLへ変換します。

Search Console連携の準備は [`docs/setup-search-console.md`](../../docs/setup-search-console.md) を参照。

---

## このエージェントでできること

レポートは **冒頭にサマリ、そのあと項目別の詳細** という1ファイル構成。

### 📊 サマリ
結論・主因・次の判断を文章で示し、主要指標は期間を列名へ明記した当期・前期の実数、差、増減率で示す。
基本分析のCV数は確認済み完了イベントの発生回数、CVRはCVイベント数÷セッション数。

### 📈 基本分析（固定項目1〜7＋任意項目8〜9）
1. 月次推移（週次はクライアント向け本文へ出さない。セッションは単独、同じKPIのCV数とCVRは左右2軸で重ねたグラフ）
2. チャネル別パフォーマンス（当期・前期、CV数、CVRのセル内バー付き表）
3. ランディングページ別（セッション上位とCV上位を分け、`(not set)` は除外）
4. ページ別（PVのみ。閲覧開始数・閲覧開始率は出さない）
5. デバイス別（mobile / desktop / tablet の3カテゴリ。地域・OS・年齢性別は対象外）
6. 新規/リピーター別
7. リードサイトは完了イベント数÷フォームページPVのフォーム通過率。ECサイトは推奨eコマースイベントの取得有無を確認して購入プロセスを表示
8. Search Console連携時は自然検索（Search Console）を表示
9. BigQuery連携時は成果に至るページ遷移とページ閲覧後CV率を表示。定義は `docs/basic-analysis-search-and-paths.md` に従う

クライアント向けH2見出しは、分析サマリー、上記1〜9、必要な場合の「分析の前提・制約」、
クローン外資料を使った場合の付録に固定する。「優先して取り組む課題」「次に行うこと」などの
施策提案は05で扱い、基本分析へ追加しない。保存後の品質検査は、一覧外のH2、固定順の逆転、
分析サマリーまたは固定項目1〜7の欠落、数値項目の `> **考察:**` 欠落、当期・前期列の期間表記欠落をエラーにする。`> **考察:**` はMarkdown上の関連付け記号で、HTML/PDFではラベルを表示せず本文だけを見せる。

かつて存在した「CVパス簡易近似」（着地ページ×閲覧ページのクロス集計による近似）は削除済み。着地ページでしか絞り込めずCVしたセッションに絞り込めていなかったため、実質「その着地ページに来た人がよく見るページ」を表示するだけで、「CVに至る経路」としては読めなかった（詳細はランディングページ別（3）やページ別（4）参照）。

対象外（意図的に扱わない。他エージェントの領域）: 地域別、OS別、年齢性別、他社サイト分析、ヒートマップ、改善提案

**キーイベントの表示名**: レポートのヘッダとフォーム通過率（7）の見出しは、01の `kpis.yaml` に業務上の名前（`kpis[].name`）が登録されていれば「名前（`event_name`）」の形式で業務名を出す。

**複数CV（キーイベント）がある場合**: 合算CVだけでは打ち手が決まらないため、月次・チャネル・ランディングページ・デバイス等はKPIごとのCV数とCVRに分けて表示する。

**優先KPI**: 01の `kpis.yaml` で `priority: 1` が一意に決まっていれば各表の先頭へ置く。他のKPIは消さない。優先度が未設定なら全KPIを対等に扱う。

### 内部のパラメータチェック

以下は非公開の作業記録へ保存する。基本分析の本文へ監査指摘を列挙しない。
- ホスト名棚卸し（計測対象ホスト名の一覧。自社/想定外の切り分け。自己参照があれば発生ページも）
- utm の設定有無
- 命名規則違反（表記ゆれ・予約語・重複・文字数）
- 欠損流入（`(not set)` / `(direct)`）
- 媒体目的と計測項目の整合
- 命名規則（`standards/naming-conventions.md` へのリンク＋要点）

「流入パラメータの状態」「流入元の表記ゆれ」「計測対象のホスト名」は、いずれも上記の
内部監査に含まれる。基本分析の独立した章・目次項目としては出力しない。

※ カスタムディメンションの点検は計測設計の確認範囲（本エージェントの監査項目外）。

## 監査時に強める観点

GA4のチャネル分類だけを見ると、`Unassigned` や `(direct) / (none)` の背景が見えにくい。実務レポートでは、**GA4で分類された結果**と**実際に運用されているUTMルール**を分けて確認する。

- `Unassigned` は件数だけでなく、該当する `source / medium` の生値を明記する
- 自己参照・内部流入は、指摘する前にホスト名棚卸しで実データを確認し、発生ページ（landingPage）を添える。棚卸し抜きで参照元除外を勧めない
- QR、店頭掲示、チラシ、SNSプロフィールなど、広告管理画面に出ない流入もUTM対象に含める
- `utm_medium` はチャネル分類に直結するため、`cpc`、`paid_social`、`qr`、`email` などの推奨値を提示する
- 店舗別・プラン別・媒体別の比較が必要な場合は、`campaign` だけに詰め込まず、命名ルールとして分解できる形にする
- 表と補足説明は近づける。`Unassigned` の中身などは、該当表の右余白または直下に置く

例: [`samples/utm-audit-commentary.example.md`](./samples/utm-audit-commentary.example.md)

## 使い方

リポジトリをAIエージェントで開き、「基本分析レポートを作って」と自然文で依頼する。受付と実行の正本は [run.md](./run.md)。

エージェントが順番に:

1. **クライアント名 / GA4プロパティID / 期間 / キーイベント** を質問。サイトURLが01に未登録なら続けてURLも質問し、答えるとトップページを実際に読みに行ってサイトの役割・toB/toC・事業内容を根拠つきで推測、1回の確認で解釈の前提として01に保存する（任意。飛ばしても分析は続く）
2. GA4データと、設定があればSearch Consoleデータを自動取得（この時点では事実だけを確定）
3. 観察結果（欠損流入・表記ゆれ・キーイベント発火状況・ホスト名棚卸し・ランディングページとページ別の顔ぶれの違い等）を提示
4. **CVごとのフォームページ / 媒体・施策一覧 / 命名規則** を確認（フォームページが決まれば通過率を追加取得）
5. 03市場・顧客理解の成果物を読み込み、その文脈を使って基本分析を解釈する
6. **Markdown レポート**を `<リポジトリルート>/outputs/{client_id}/04_traffic/basic-analysis-report.md` に保存（`<リポジトリルート>` は `git rev-parse --show-toplevel` で求める。ファイル名に日付は入れない。既存ファイルは `_past/` へ書き込み時刻付きで退避してから上書きする。docs/standard-run-order.md §4）。出力先はユーザーに尋ねず、明示指定があった場合のみ従う。完了時は保存先のフルパスを**最終成果物**として表示する（docs/standard-run-order.md §4 規約4。成果物は指定した形式（既定はMarkdown）でも受け取れる。詳細は §4-2）
7. `python common/report_index/build_index.py "outputs/{client_id}"` で `index.html` を再生成
8. サマリと優先対応 Top3 + 基本分析ハイライトを表示

詳細フロー例は [samples/interaction.example.md](./samples/interaction.example.md) を参照。
