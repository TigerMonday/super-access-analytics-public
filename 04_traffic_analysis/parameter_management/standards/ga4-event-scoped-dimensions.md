# GA4: ディメンションと指標はイベント行で結合される

GA4 Data API のクエリ設計で踏み外しやすい前提を1つに絞ってまとめる。実際にこれで
1本クエリ分の設計を作り直すことになった不具合があった（後述）。

---

## 2つの原則

1. **GA4はディメンションと指標をイベント行で結合する。** `eventName` でフィルタすると、
   返るのは「そのイベントが起きた行」だけで、「そのイベントが起きたセッションの全体像」
   にはならない。`sessions` を指標にしても、ページのディメンション（例:
   `pagePathPlusQueryString`）を並べた時点で、行の単位はイベントのまま。
   `pagePathPlusQueryString` は「そのイベントが発火した瞬間に見ていたページ」を返す
   だけで、同じセッション内の他のページには一切触れない。

2. **セッション単位に広げたいときは、セッションスコープのディメンションを軸にする。**
   `landingPagePlusQueryString`（セッションの入口ページ）のように、値がセッション全体で
   固定されるディメンションであれば、`eventName` で絞っても正しく「そのセッションの
   属性」を返す。

---

## 実例: 中間ページ候補クエリの不具合

CVファネルの中間ページ候補を出す目的で、「キーイベントが発火したセッションでよく見られて
いるページ」を取るつもりで次のクエリを書いた:

- ディメンション: `pagePathPlusQueryString`
- 指標: `sessions`
- フィルタ: `eventName` = 対象のキーイベント

意図は「発火セッション内でよく閲覧されているページ」だったが、返ってきたのは**そのイベント
自身が発火したページ**だけだった。原因は上記の原則1。このサイトのキーイベントは
「完了ページ（例: `/contact/service/thanks/`）の `page_view`」として発火する設計だった
ため、このクエリは常に完了ページ自身を1位で返す。GA4で最もありふれた計測方式であり、
他のサイトでも同じ設計であれば同じ結果になる。ボタンクリックでイベントが発火する型
（発火ページ＝入力前ページ）ではこの問題は起きない。

**同じ `fetch_ga4_analytics.py` の中に、正しい例と間違った例が両方ある:**

- **正しい例**（旧実装のCVパス簡易近似。着地ページでしか絞り込めずCVしたセッションに
  絞り込めていなかったため機能自体は削除済みだが、クエリ設計としては正しい例として残す）:
  `landingPagePlusQueryString` × `pagePathPlusQueryString` のクロス集計。軸がセッション
  スコープの `landingPagePlusQueryString` なので、同一セッション内で閲覧された他のページ
  （`pagePathPlusQueryString` 側）を正しく拾える。
- **間違った例**（今回の中間ページ候補クエリ）: `pagePathPlusQueryString` を軸に
  `eventName` で絞った。軸自体がイベントスコープなので、原則1により「そのイベントが
  起きた行」以外は返らない。

この不具合の対処（`is_event_self_page()` による除外、完了ページの親パスをランディング
ページ一覧と突き合わせる `with_parent_path_guess()`）は `scripts/analysis_calc.py` を参照。
根本原因はクエリ設計そのものであり、除外ロジックだけでは直らない。
