# GTM タグ量産の診断と集約ガイド

GTM コンテナでタグが数十〜数百本に増えているとき、その多くは「同じ種類のタグを手作業で複製した」結果である。
このガイドは、量産の原因を突き止め、タグを変数（ルックアップテーブル）でまとめる道筋を立てるための手順をまとめる。

- 客観的な棚卸し（事実の並べ替え）は `review`（diagnoser）の GTM 機械検出が出す。
- このガイドは、その検出結果を解釈し、原因を推定し、集約案を立てるための考え方をまとめたもの。

機械検出（diagnoser の `gtm_mechanical_checks`）は次を候補として出す。本ガイドはその候補を入力に使う。

- 量産: 同じ種別が 10 本以上ある（軸の特定が必要）
- 残骸候補: 名前に `old` / `旧` / `test` / `コピー` 等を含むタグ（有効状態なら停止漏れの疑い）
- 二重計測候補: 同一トリガーから同種タグ（カスタムHTMLを除く）が複数発火している箇所
- 値の使い回し候補: タグごとに固有であるべき値（CV ラベル等）が複数タグで共有されている箇所

**二重計測候補にカスタムHTML（`html`）は入らない。** ヒートマップ・チャット・A/Bテストなど
外部SaaSのスニペットは、そもそも全ページ（同一トリガー）で複数本発火するのが仕様として
正常な状態であり（[`third-party-tools.md`](./third-party-tools.md)）、実際の案件でも
「計測ツール系はオールページで発火することが多いので指摘に入れなくていい」という判断が出た。
カスタムHTMLの中身（宛先）はGTMエクスポートに現れないため、機械では
「本当にGA4へ二重送信しているか」を判定できず、判定できないものを候補に混ぜると
この誤検知が常態化する。したがって候補生成そのものから外している。
**代わりに残るリスク**（カスタムHTMLの中にGA4送信コード・`gtag()` を直書きしていて
本当に二重計測になっているケース）は機械化していない。
[`audit-items.md`](./audit-items.md) の目視項目「独自HTMLの直書きGA4送信」で扱う。

## 0. 検出を読む前提 — 名前と実体は一致しない

機械検出はすべて**名前**を手がかりにしている。集約・停止の判断に使う前に、次の3点を押さえる。

- **タグ名は実装の保証にならない。** `【AllAds】Clarityタグ_ヒートマップ用` という名前のタグが
  実際には別のツール（Ptengine等）を読み込んでいた例がある。「重複タグN組」は名前ベースの候補であって、
  停止・削除の根拠ではない。中身（読み込み先・送信パラメータ）を見てから判断する。
- **コンテナは1つとは限らない。** カスタムHTMLタグから別の GTM コンテナを読み込んでいることがある。
  その中身は本体コンテナのエクスポートに入らないので、監査範囲の外にあることを明記する。
  A/Bテストツールのように**コンテナが増えるのが仕様**のものもある（[`third-party-tools.md`](./third-party-tools.md)）。
- **量産の一部は外部SaaS の導入痕跡。** 同じツールを複数の担当者・時期で入れた結果の二重設置は、
  「軸で複製した量産」とは原因も打ち手も違う。先に SaaS 由来を仕分けてから Q1 に入る。

## 1. 診断の問いの順序

GTM の問題の多くは「同じ種類のタグを手作業で量産した」ことの副産物である。
量産は不具合の温床であると同時に、診断の入口になる。次の順で問いを立てる。
固有業種に依存しない一般形で書いてあるので、案件ごとに当てはめる。

### Q1. 量産の発見 —「なぜこの種別はこんなに多いのか」
機械検出の「量産」フラグで 10 本以上の種別を見る。同種タグが大量にあるなら、
「ある軸 × ある行動」のマトリクスを、タグの複製で表現している可能性が高い。
例: 媒体 × 行動（登録 / 予約 / 購入）× ある軸（店舗 / 商品 / 地域 / 言語…）。
本数が `軸の数 × 行動の数 × 媒体数` の掛け算に一致しないか概算する。

### Q2. 軸の特定 —「複製は何で分岐しているのか」
量産タグの名前・発火トリガーを読み、複製の軸が何かを突き止める。
軸の正体は案件ごとに違う（店舗・商品カテゴリ・地域・言語・キャンペーン・LP 別…）。
固有名を決め打ちせず、データから読む。軸が分かったら、それに一言で名前を付ける
（例: 「これは“店舗”という軸でタグを複製している」）。

### Q3. 分岐キーの特定 —「機械はどうやって軸を見分けているか」
その軸を GTM が判定している手がかりを、トリガー条件から探す。よくある手がかり:

- URL のクエリパラメータ（例: `?xxx_id=数字`）
- URL のパス / サブドメイン
- dataLayer の変数（最も望ましい）
- イベント名・カスタムイベントのパターン

この分岐キーが、後でルックアップテーブルの「キー列」になる。
複数方式が混在していないかも確認する（一部だけ別方式 = 例外処理が必要）。

### Q4. 値の異同検査 —「分岐値は全部固有か、使い回しか」
パラメータごとに、全タグ共通の固定値か、タグごとに違う分岐値かを見分ける。

- 固定値（全タグ共通の ID 等）→ タグをまとめられる根拠。
- 分岐値（タグごとに違う）→ ルックアップのテーブル行として残す。
- 分岐値のはずが一部共有されている → 「意図的な共通化か、設定漏れか」を質問候補にする。
  例: 本来店舗別に測りたいのに、複数店が同じ CV ラベルを共有していると合算になる。

### Q5. 重複・残骸検査 —「二重計上・テスト混入・旧版残置はないか」
機械検出の「二重計測候補」「残骸候補」を見る。

- 二重計測候補 → 同一トリガーで同種タグ（カスタムHTMLを除く）が複数 = 二重計上の候補。
  ただし断定の前に、各タグのブロックトリガー・発火条件の差を確認する（差があれば重複しない）。
- カスタムHTMLは機械検出の対象外。**タグ名から直書きのGA4送信が疑われる場合
  （`GA_Event_Code_...` のように命名でGA4計測を示唆しているもの等）は目視で確認する**
  （[`audit-items.md`](./audit-items.md) 目視項目「独自HTMLの直書きGA4送信」）。
- 残骸候補（old / test / コピー等）で「有効」のもの → 停止漏れ・本番混入の疑い。

これらは集約プロジェクトを待たず今すぐ単独で直せることが多く、即時修正リストに回す。

### Q6. 送信内容の検査 —「各媒体は何を送っているか」
媒体ごとに送信パラメータを点検する。一般的な観点:

- 標準イベントを使っているか、独自（カスタム）イベントか（最適化の効きに影響）
- 必須データの欠落（CV の値・取引 ID、ユーザーデータ等）が業態上妥当か、漏れか
- 同じ目的のデータの送信経路が媒体内で揃っているか（経路の不整合がないか）
- プラットフォーム側の制約（媒体の仕様変更など）に抵触しないか

不確実なプラットフォーム仕様は推測で書かず、必要なら最新仕様を確認する。

## 2. 検出を「設定意図を問う質問」に変換する

機械検出やサイト確認で見つかった不審点は、断定でなく質問リストにする。
「間違っている」と決めつけず「この設定の意図は何か」を問う形にすると、
クライアントとの確認がスムーズで、こちらの誤認も避けられる。質問化すべき典型:

- 分岐値の使い回し（共通化は意図的か / 手間で共通になっているか）
- 設定が片側だけ欠けている要素（不要なのか / 設定漏れか）
- テスト・旧版タグ（役目を終えたなら削除してよいか）
- 分岐キーの将来挙動（キーが再利用されないか 等、外部システム仕様に依存する点）
- 出稿状況（使っていない媒体タグの要否）
- 実サイトとの突合で見えた齟齬（閉店・統廃合・URL 変更など、断定できないもの）

スライドレポートに載せるときは、修正が必要なページに `! 修正推奨`、確認が必要なページに `? 要確認` の注記を置く運用（[`README`](../README.md) のレポート化運用メモを参照）と揃える。

## 3. 成果物の組み立て（推奨例）

レポートに載せる場合の推奨構成。案件に応じて組み替えてよい。
多店舗チェーンの広告計測コンテナで有効だった構成を雛形として示す。

### 現状整理
- タグ種別の内訳（本数・正体・うち停止）
- なぜ量産されているか（軸の特定結果を平易な言葉で）
- 媒体ごとに何を送っているか（固定値 = まとめられる根拠 / 分岐値 = テーブル行）
- 問題点・課題点（媒体別にグルーピングし、各項目に重大度 = 高 / 中 / 低を併記）

### 改善プラン
1. 即時修正（タグ整理を待たず単独で直せるもの。誤データ停止を最優先）
2. 集約プラン（量産タグを「分岐キーで見分ける変数」＋「ルックアップテーブル」でまとめる手順）。
   順序は ①分岐キーの変数化 → ②各媒体の集約 → ③標準化・拡張設定の適用。順番を逆にすると個別改善が空振りする。
3. 改善後のタグ本数イメージ（種別ごと 現状 → 改善後。分岐値はテーブル行として残るので「本数削減 ≠ 値の削減」を明記）
4. 日々の運用がどう変わるか（軸の要素が増減する場面 = 出店 / 閉店 / 商品追加 等で、
   今の手作業 vs 改善後のテーブル 1 行操作を対比。本数削減より作業とミスの減少が本質）

### マスタ（分岐軸の管理表）
- 1 行 = 軸の 1 要素（店舗・商品・地域…）。
- 列: 分岐キー（= ルックアップのキー）/ 表示名 / 状態（active / closed 等）/ 媒体ごとの分岐値 / 備考。
- キーは分岐キー（Q3）の実値をそのまま使うと変換が不要で素直（独自連番を振らない）。
- このマスタを正本とし、GTM のルックアップ変数はこの写しにする運用。
- 異同検査・残骸検査で見つかった注意点は備考列に書き、一覧で気づけるようにする。

## 4. 考え方の核

> 同種タグの量産は、ある軸（店舗・商品・地域・言語…）を「変数に降ろさず、タグ実体の複製で表現した」結果である。
> 診断とは、その軸を見つけて名前を付け（Q1–Q3）、値の異同と複製ミスを検査し（Q4–Q5）、
> 軸を変数化（ルックアップ）してタグをまとめる道筋を示すこと。
> 二重計上・テスト混入・値の使い回し・送信経路のズレは、別々の不具合に見えて、
> 多くは「手作業で複製する運用」という単一の原因の異なる現れである。
> だから本質的な打ち手は「個別の不具合を 1 つずつ直す」ことではなく、
> 「複製をやめて、軸を 1 か所（テーブル）で管理する状態に変える」こと。

整理の価値はタグ本数の削減そのものではなく、次の 3 点にある。

- 人の目では見つからないミスを検出できる状態にする
- 軸の増減（出退店・商品改廃）への作業とミスを減らす
- 改善を 1 か所で全要素に効かせられる

この原理は GTM に限らず、「個別実体の複製」で増えてしまった構成全般に当てはまる。

---

## 5. 進め方のまとめ

1. `review`（diagnoser）の GTM 機械検出で、量産・残骸・二重計測・値の使い回しの候補を得る。
2. Q1 → Q6 の順に問いを立て、検出結果とトリガー条件・実サイトを材料に解釈する。
3. 断定できない点は §2 の質問リストに変換する。
4. §3 の構成で成果物を組み立てる（推奨構成は雛形。案件で組み替え可）。
5. 不確実なプラットフォーム仕様（媒体の最新仕様等）は裏取りし、推測で断定しない。
