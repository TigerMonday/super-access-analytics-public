# GA4 設定チェックの監査項目

**「内部でどこまで見るか」の正本。** 機械37項目と目視19項目は内部監査として全件実行し、
案件ごとに削除・差し替えない。一方、`check-report.md` は内部表の転記ではなく、利用者の判断に
必要な設定確認表、異常が見つかった項目、改善順だけを掲載する。受信イベント一覧は掲載しない。内部監査の
網羅性とクライアント本文の読みやすさは別の契約として検証する。

判定根拠と確認範囲は内部データに残す。本文に出さない項目も未実行にはしない。
フォーム通過率・業界平均・問い合わせ減少の原因分析は計測監査の対象外とする。

判定は **○確認範囲で問題なし／△要確認／×不備を確認** とし、適用外は理由付きで別に示す。

△にはデータ未取得・権限不足・目視未実施や条件付きの懸念を含むため、状態欄で理由を区別する。
適用外の項目も行を残して理由を示し、正常に検証できた項目とは分けて数える。
イベントの存在・設定の登録・異常未検出だけで、実際の送信まで正常と断定しない。

| どこで判定するか | 数 | 実体 |
|---|---|---|
| **機械**（`_data/` から自動） | 37 | `src/measurement_design/review/audit_matrix.py` |
| **目視**（下の表） | 19 | この文書 |

機械側は `run.py review` を実行すると自動で走る。全37行と目視19行を
`check-report.md` へそのまま埋め込むことはしない。

cd 02_basic_measurement/measurement_design && uv run python run.py review --client {クライアント名}

設定確認表と目視確認ブロックの後は、次だけを本文へ出す。

1. 内部監査で×・△となり、利用者の判断または対応が必要な具体的な異常
2. 前段の確認が終わらないと着手できない依存関係を含む改善順

自動収集・拡張計測・推奨・カスタムの各イベント一覧は公開本文へ出さない。主要イベントの欠落、
異常比率、日本語イベント名、二重送信など、改善判断につながる具体的な異常だけを上記1へ出す。
予約・決済・オンラインサービス等の外部ドメインは利用者への事前質問項目にせず、受信した主要
`hostName`（全セッションの1%以上、検証環境を除外）から候補を作る。複数の主要ホストがあり、
そのホストが `source / medium` で `referral` になっていれば、クロスドメインの確認候補として△を出す。
この2つは別集計であり実際のホスト間遷移を直接示さないため、分断や設定不備とは断定しない。
対象間の導線、同じWebストリーム・タグID、実ブラウザ遷移時のセッション継続を確認し、分断を
再現できた場合だけ設定変更を提案する。
確認済みコンバージョンイベントは、上位100件ではなく直近30日の全イベント名・件数と突合し、
全件取得が成功した場合だけ未掲載を0件と判定する。旧データ・取得不足は未確認とし、0件または
類似名で受信している場合だけ「成果計測」の指摘を出す。単なるKPIとイベントの対応表には戻さない。

KPIとイベントの対応表、イベントパラメータの独立章、カスタム計測の独立章、その他推奨設定の
独立章は本文に設けない。GTMタグの本数だけを根拠に「一本化する」とは提案しない。GTMで重複を
指摘する場合は、同じイベント名、同一または重なる発火条件、変数でイベント名を決める設定を区別する。

### 判定を作るときの落とし穴（実測）

- **`テレビ電話相談予約` を電話タップと読んだ。** 「電話」だけで拾うと、
  オンライン相談のフォームが混ざる。**クリック・タップまで揃って初めて電話タップ**
- **`--sanitized--` `(data not available)` を「未知の medium」と数えた。**
  あれは GA4 が伏せた値で、UTM の付け方の問題ではない
- **海外アクセスや低成果率だけでBot扱いしない。** 海外流入は通常発生しうる。特定国への異常な集中を入口に、平均エンゲージメント時間が極端に短い、直帰率が非常に高い、成果がない/極端に少ない等の複数信号が重なる場合だけ「機械的アクセスの疑い」とする
- **環境（ブラウザ×OS）の偏りは補助根拠に留める。** 国名や環境だけで除外せず、サーバーログやCDN/WAFログで確認できた範囲だけ除外する
- **無いキーを見て、常に ok を返していた**（`counts.ad_conversion_tags`）。
  データセットの実物でキーの有無を確かめる。**存在しないキーは黙って None になる**
- **直した先も別スキーマだった。** タグの種別は GTM API 形式では `type`
  （`"awct"`）、公開 gtm.js 形式では `function`（`"__awct"`）に入る。
  `function` 側しか見ていなかったため、API経由で取得したデータでは
  相変わらず広告タグが常に0本だった。`_tag_kind()` で両形式を1箇所に寄せる
- **測定IDはトップレベルに無い。** 公開 GTM JSON では各タグの `destination` に入っている。
  「送信先が1種類だから ok」と読んでいたが、実データでは10種類あった
- **`mybusiness` `ai-assistant` は GA4 が分類できる。** 語彙に無い値を
  「未分類」として数えると、チャネルの実測（3,963）と食い違う（実装は5,102を出していた）。
  **セッション数は `channel_performance` を正にし、語彙の話は種類の数で言う**
- **欠損データで ok を返さない。** データが無いのは「問題なし」ではない。`warn` にする。
  個別に塞ぐと漏れる（codex レビューで3巡続けて同じ型を指摘された）ので、
  **`ITEMS` に「要るデータセット」を宣言し、`audit_matrix` が先に止める**。
  「データが無いときに ○ を返す項目が1つもないこと」をテストで固定している
- **改行を `
` で決め打ちしない。** テンプレートは作業環境で CRLF になり、
  節を落とす正規表現が空振りして `{{audit_matrix}}` が残った
- **クロスドメインは「ドメインが2つ以上」が前提。** 開発環境やbotの単発アクセスまで
  1ドメインに数えると、単一ドメインの案件で存在しない自己参照の論点を作ってしまう。
  セッション比1%未満のホストは数えない（`check_non_production_hosts` と同じ考え方）。
  **GTM側のクロスドメイン対象ドメインリストは機械では読まない。** `googtag` タグの
  内部パラメータのキー名がGTM API v2の仕様に公式に載っておらず、実データにも
  該当パラメータが無いため、読めたつもりのキー名で「設定なし」と言い切ると
  キー名の不一致だけの誤判定になる（GA4管理画面で直接設定した場合はGTM側に
  そもそも何も現れない）。目視項目「クロスドメインのGTM側設定」に送っている

| 領域 | 項目 | 何を見るか | なぜ機械化していないか |
|---|---|---|---|
| 広告連携 | 広告コンバージョンの最適化対象 | 広告管理画面で、各コンバージョンアクションが入札の最適化対象（プライマリ）か、確認用（セカンダリ）か | GTMから分かるのはタグの発火条件までで、広告管理画面側の最適化設定は取得できない。クリックやスクロールで広告コンバージョンタグが発火すること自体は誤りとは限らないため、機械判定しない |
| 基本計測 | 不要なURLパラメータの除外 | 完了ページに `?c=` のような値が残るか | `_data` のページはクエリを落として集計している。別途クエリ付きで取る必要がある |
| 基本計測 | クロスドメインのGTM側設定 | GTMのGoogleタグ（`googtag`）の詳細設定「クロスドメインリンク」に対象ドメインが正しく入っているか。GA4管理画面（データストリームの「Googleタグの設定」）で直接設定している場合はGTM側には何も現れない | GTM API v2は `googtag` タグの内部パラメータのキー名を公式に文書化していない。実データにも該当パラメータの実例が無く、キー名を確定できない。仮に何らかのキー名を推測して読みにいくと、キー名を外しただけで「未設定」と誤判定しうる（GA4管理画面側の設定は原理的にGTMのデータへ出てこない）。誤って断定するほうが実害が大きいため機械化を見送る。判定表側の「クロスドメイン計測」は自己参照の実害（ドメイン間の遷移が参照扱いになっているか）だけを見ており、GTM側の設定の有無そのものは見ていない |
| イベント計測 | フォームの表示計測の網羅 | 対象サイトの各フォームに定義どおりの表示計測があるか | フォームの数はサイト固有。イベント名から機械的に数えられない |
| イベント計測 | 成果の定義の置き場所 | GA4 管理画面とタグマネージャーのどちらで作っているか | GTM の閲覧権限が無いと片側しか見えない |
| 流入計測 | UTMの付け方の決まり | 同じ媒体が複数の表記に分裂していないか | 「同じ媒体か」は媒体名の知識が要る（`ig` `fb` `th` が同じ Meta か） |
| 流入計測 | 内容（content）の値 | 広告名・クリエイティブ名が入っているか | 値が意味を持つかは人が見る（数値IDでも社内で読めることがある） |
| 流入計測 | 振り忘れ・欄の入れ違い | source と medium が逆・空 | 空の理由（未設定か自動分類か）は媒体側の設定を知らないと決まらない |
| 流入計測 | キャンペーンID（utm_id） | 費用データと突合できるIDが届いているか | `_data` に `sessionCampaignId` を取っていない（取得項目を増やせば機械化できる） |
| 流入計測 | 検索広告の自動連携 | 広告のキャンペーン名がそのまま入っているか | 自動連携かUTM手動かは、値の形だけでは決められない |
| ページ計測 | 旧構造の併存 | 新旧のURL構造が同時に生きているか | 「旧」の定義はサイト固有 |
| ページ計測 | 検索結果・詳細のURL規則 | 条件や物件IDがURLに出るか | URLの意味づけはサイト固有 |
| カスタム計測 | イベントのパラメータの割合 | パラメータを持つタグの数 | GTM の閲覧権限が要る（公開ファイルからは数えられるが名前が読めない） |
| カスタム計測 | 値の受け渡しの仕組み | dataLayer・変数の設計があるか | 現物を見ないと判断できない |
| カスタム計測 | 独自HTMLの直書きGA4送信 | 同一トリガーで発火する独自HTML（カスタムHTML）の中身が、GA4へ直接送信するコード（`gtag()` 等）を持っていないか。タグ名がGA4計測を示唆する場合（`GA_Event_Code_...` 等）は特に確認する | 独自HTMLの中身（スクリプト本文）を取得していないため機械では宛先が判定できない。ヒートマップ・チャット・A/Bテストのような外部SaaSは同一トリガーで複数本発火するのが仕様（`third-party-tools.md`）なため、機械検出（二重計測候補）からはカスタムHTMLを除外している |
| その他 | Search Console 連携 | GA4管理画面で対象プロパティとリンクしているか。分析ツールからSearch Console APIを読めることとは区別する | Admin API のリンク一覧を取得していない |
| その他 | 未使用のプロパティ | アカウント配下に記録の無いプロパティがあるか | 案件フォルダは1プロパティ分。アカウント全体は `list_properties.py` で別に見る |
| その他 | 権限をいただいていないタグ | 想定外の測定IDが動いていないか | 実機のリクエストを見る（Playwright）。設定データには出ない |
| その他 | 確認の運用 | 月次で見る仕組みがあるか | 運用の話。データに出ない |

## 項目を足すとき

1. `audit_matrix.py` の `ITEMS` に `(領域, 項目, 判定関数)` を足す
2. 判定関数は `(judgement, state)` を返す。`judgement` は `ok` / `warn` / `ng`
3. `tests/unit/test_audit_matrix.py` に**○になる例と×になる例の両方**を足す
4. 機械化できないものは、この文書の「目視」の表に理由つきで足す

**判定を空（`—`）にしない。** 見たのか見ていないのかが分からなくなる。
データが無いなら `warn` にして「取れていない」と書く。
