# 外部ツールの痕跡カタログ — SaaS が GA4/GTM に何を残すか

診断で「用途不明のイベント」「命名規則違反」「意味の分からないコンテナ」に見えるものの一部は、
**導入済みの外部SaaS が仕様どおりに動いている痕跡**である。

正体が分かれば、指摘ではなく説明になる（クライアントに聞く必要がなくなる）。
逆に、正体を知らないまま「不要」「異常」と判定して止めると事故る。

このカタログは、案件で実際に遭遇して実物で確認できた分だけを書く。
**推測で「たぶんこのツール」と書かない。** 根拠（どのデータで確認したか）を必ず添える。

- 機械検出（`review` の diagnoser）はツールを知らない。SaaS 由来のイベントも違反候補として並べる。
- このカタログは、その候補から「仕様どおりのもの」を外し、残りを本当の指摘にするために使う。

---

## 1. 正体の突き止め方（一般手順）

ツール名を先に当てにいかない。**痕跡から逆算する。**

### 手順1. パラメータの接頭辞を見る

用途不明イベントの「イベント × パラメータの実測」（`_data/03-custom-definitions.json`）を見る。
**あるイベントの発火全件に、同じ接頭辞のパラメータが付いている**なら、単一のツールが送っている強い証拠。

| 痕跡 | 意味 |
|---|---|
| `optx_*` / `exp_variant_string` | ツール固有の名前空間。ドキュメントを引けば特定できる |
| `ai_*` / `bot_*` | AI接客・チャットボット系 |
| ドット区切りのイベント名（`b4a.booking`） | dataLayer に外部システムが直接プッシュしている |

「一部のイベントにだけ付く」なら実装由来、「全件に付く」ならツール由来と考える。

### 手順2. GTM のカスタムHTMLタグの読み込み先ドメインを見る

タグ名ではなく **`<script src>` のホスト名**でツールを特定する（`js.ptengine.jp` → Ptengine、
`www.clarity.ms` → Microsoft Clarity）。ホスト一覧は `_data/09-gtm.json` を `src=` で検索する。

### 手順3. GA4 のイベント作成ルールを見る

GTM を全部見ても発火元が見つからないイベントは、たいてい **GA4 管理画面のイベント作成ルール**にある
（`_data/01-property.json`）。ここは GTM のエクスポートには一切現れない。

### 手順4. それでも分からなければ実ページで確認する

該当ページを開き、DevTools の Network で `collect?` のリクエストを見る。ここまでやって不明なものだけを
`questions.md` に回す。**手元で判別できるものを質問に回さない。**

## 2. ツール別カタログ

### Optimize Next（A/Bテスト・LPO）

確認: 実際の案件（2026-07・GTM取得データで実測）

**GTM コンテナを配信の器として使う仕様。** テストごとに別コンテナを作り、それを既存コンテナの
カスタムHTMLタグから読み込ませる。したがって**コンテナが増えること自体は異常ではない。**
「コンテナが2つ余分にある」を不備として指摘しない。

```javascript
<!-- Optimize Next -->
<script>(function(p,r,o,j,e,c,t,g){
p['_'+t]={};g=r.createElement('script');g.src='https://www.googletagmanager.com/gtm.js?id=GTM-'+t;r[o].prepend(g);
r[o][j].add(e+t);setTimeout(function(){if(r[o][j].contains(e+t)){r[o][j].remove(e+t);p['_'+t]=0}},c)
})(window,document,'documentElement','classList','loading',2000,'5LNM9RQC')</script>
```

このスニペットから読み取れることが3つある。

| 事実 | 診断上の意味 |
|---|---|
| コンテナIDが `'GTM-'+t` の**文字列連結**で組み立てられている | **`GTM-XXXXXXX` で検索しても見つからない。** 探すときは `gtm.js?id=GTM-` か `Optimize Next` で検索する |
| `documentElement` に `loading<ID>` クラスを付け、**2000ms 後に外す** | アンチフリッカー処理。表示の遅延（LCP）に影響しうる。パフォーマンスの論点になる |
| 読み込むのは GTM コンテナそのもの | **中身は本体コンテナのエクスポートに入らない。** テスト内容まで見るなら別途エクスポートが要る |

GA4 側の痕跡:

| 痕跡 | 内容 |
|---|---|
| イベント `experience_impression` | どのテストのどのパターンを表示したかの記録。**発火数は上位に食い込む**（実際の案件で30日24,037件・全イベント11位） |
| パラメータ `optx_experience` | テスト名（日本語が入る。命名規則の対象外） |
| パラメータ `optx_variant` | パターン名（`オリジナル` / `パターン1` など） |
| パラメータ `exp_variant_string` | パターンID（`OPTX-…` 形式） |

**発火数が多くても計測不良ではない。** ただし次の2点は棚卸しの対象になる。

- カスタムディメンション枠を3つ消費する（上限50）。テスト終了後も登録が残りがち
- 別途 `variant_id` のような自前のABテスト用ディメンションが登録されていることがある（値は入らない。`optx_*` 側で取れているため）

**別コンテナのエクスポートを依頼するかどうか**: 設定監査の必須項目ではない。
「どのページで何を出し分けているか」まで見る必要がある場合だけ、優先度低として質問表に載せる。

### BOTCHAN（AI接客・チャットボット・EFO）

確認: 実際の案件（2026-07）

| 項目 | 内容 |
|---|---|
| 読み込み先 | `botchan-scripts.botchan-apps.com` / `api.ada-cloud.com` / `app2.blob.core.windows.net` |
| タグ数の目安 | 用途（AI接客 / EFO / 出し分け）ごとにカスタムHTMLが分かれ、10本以上になることがある |
| イベント | `chat_open` / `ai_session_start` / `ai_com_start` / `BOT_clicklog` など |
| 注意 | カスタムHTML内にスクリプトURL＋`api_token=…` が**平文で書かれる**。クライアントサイドで公開される類のトークンなので実害は低いが、GTM エクスポートをリポジトリに置く運用では扱いを決めておく |

`ai_*` / `BOT_*` のイベントが **GTM からは送信されているのに GA4 で受信数0** になっていることがある。
タグの停止・トリガー条件・送信先測定IDのどれかを疑う（実装の問題であってツールの仕様ではない）。

### B4A（予約・電子カルテ）

確認: 実際の案件（2026-07）

| 項目 | 内容 |
|---|---|
| 連携方式 | 外部システムが **dataLayer に直接プッシュ**する |
| dataLayer イベント名 | `b4a.booking` / `b4a.counselingRequest`（ドット区切りの名前空間） |
| GTM 側 | これをカスタムイベントトリガーで受け、`purchase` などの GA4 イベントに変換する |

**二重計上の温床。** 予約完了後にサンクスページへ遷移する動線だと、
「dataLayer 由来の `purchase`」と「サンクスページ到達由来の `cv_reserve`」が両方発火する。
発火数の大小だけで包含・排他を決めず、**発火パスとチャネル分布を突き合わせて確定させる**。

### ヒートマップ系（Microsoft Clarity / Ptengine）

確認: 実際の案件（2026-07）

| ツール | 読み込み先 |
|---|---|
| Microsoft Clarity | `www.clarity.ms` |
| Ptengine | `js.ptengine.jp` |

同一ツールが複数タグで二重設置されていることが多い（代理店ごとに入れた結果）。
Clarity が4タグ、といった状態は珍しくない。GA4 のデータには直接影響しないが、
ページ表示の負荷と管理の見通しの論点として挙げる。

## 3. タグ名を信頼しない

**タグ名と実装は食い違う。** 実際の案件では `【AllAds】Clarityタグ_ヒートマップ用` という名前のタグが、
実際には **Ptengine** を読み込んでいた。

| やってはいけない判定 | 正しい手順 |
|---|---|
| 名前が同じだから重複タグ。片方を止める | 中身（読み込み先・送信パラメータ）を見てから判断する |
| 名前に `test` / `旧` が入っているから不要 | 有効状態で発火実績があるなら、まず何を送っているか確認する |
| 名前が `【GH】…` だから代理店GHの管轄 | プレフィックスは運用の慣習であって、正しさの保証ではない |

`review` の「重複タグN組」は**名前ベースの機械検出**である。停止・削除の提案に使う前に必ず中身を見る。
考え方は [`gtm-tag-consolidation.md`](./gtm-tag-consolidation.md) を参照。

**カスタムHTMLは「二重計測候補」の機械検出から外れている。** ヒートマップ・チャット・A/Bテストの
ようなツールは、同一トリガー（オールページ等）から複数のカスタムHTMLタグが発火するのが
仕様として正常な状態であり、実際の案件でも「計測ツール系はオールページで発火することが多いので
指摘に入れなくていい」という判断が出ている。中身（宛先）が分からないカスタムHTML同士を
機械的に「二重計測」と決めつけると、この誤検知が案件ごとに再発する。
一方で、カスタムHTMLの中にGA4送信コード・`gtag()` を直書きしている場合は本当の二重計測になり得る
（タグ名が `GA_Event_Code_...` のようにGA4計測を示唆しているケースなど）。これは機械化しておらず、
[`audit-items.md`](./audit-items.md) の目視項目「独自HTMLの直書きGA4送信」で確認する。

## 4. 「仕様どおり」と「問題」を分ける

外部ツールが絡む論点は、次の3つに仕分けてから書く。混ぜると全部が不備に見える。

| 区分 | 例 | 成果物での扱い |
|---|---|---|
| **仕様どおり** | Optimize Next でコンテナが増える／`experience_impression` の発火数が多い | 現状09・現状02 に「仕様である」と1文で書く。指摘にしない |
| **仕様の副作用（判断が要る）** | `optx_*` 3つがカスタムディメンション枠を消費／アンチフリッカーの2秒 | 推奨側で「残す／外す」の判断材料として書く |
| **実装の問題** | GTM から送っているのに GA4 で受信0／同一ツールの二重設置／タグ名と実装の不一致 | 通常どおり指摘する |

## 5. カタログへの追加ルール

新しいツールに遭遇したら、次が揃った時点でここに追記する。

1. **ツール名**と、それを特定した根拠（読み込み先ドメイン / パラメータ接頭辞 / 公式ドキュメント）
2. **GA4 側の痕跡**（イベント名・パラメータ名・発火数の目安）
3. **GTM 側の痕跡**（タグの型・読み込み先・特徴的なスニペット）
4. **診断上の扱い**（仕様どおり / 副作用 / 問題 のどれか）
5. **確認した案件と時期**（仕様は変わる。いつ時点の話かを残す）

確認できていない項目は書かず、`questions.md` に回す。
**このカタログは「調べた結果」の置き場であって、推測の置き場ではない。**
