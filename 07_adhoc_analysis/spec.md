# spec: アドホック分析エージェント

| 項目 | 内容 |
|---|---|
| **概要** | 分析依頼から問い構造化→データ取得→結果解釈→追加検証を4フェーズで段階実行。各フェーズで承認ゲート。**基本分析・市場・顧客理解の後段**として、起動時に前段成果物を読み込む（Step 0） |
| **データソース** | **GA4 Data API（自動取得）**。Phase 2 で Search Console 拡張予定 |
| **前段インプット（Step 0・あれば必読）** | ・01 コンテキストストア（GA4 ID / キーイベント / gotchas / findings）<br>・03 3C・ペルソナ・カスタマージャーニーレポート（`outputs/{client_id}/03_research/`）<br>・04 基本分析レポート（`outputs/{client_id}/04_traffic/`） |
| **インプット** | ・分析依頼（自由記述）<br>・クライアント名 / GA4 プロパティID / 期間（Step 0 で補完できたものは再質問しない）<br>・比較期間（任意） |
| **アウトプット** | Markdown レポート（4フェーズ統合版）→ `<実行フォルダ>/outputs/{client_id}/07_adhoc/`（実行フォルダ＝セッション開始時のカレントディレクトリ。通常はリポジトリルート。docs/standard-run-order.md §4）<br>出力先はユーザーに尋ねず、明示指定があった場合のみ上書き。完了時に主要成果物のフルパスを表示する<br>・サマリ<br>・参照した前段成果物<br>・Phase 1: 問い構造化<br>・Phase 2: データ取得結果<br>・Phase 3: 結果解釈<br>・Phase 4: 追加検証アイデア<br>・適用した前提<br>※ HTML 版は Phase 2 拡張。当面 Markdown を正とする |
| **トリガ** | 分析依頼が来たとき / 定例で深掘りしたい論点が出たとき（原則 02・03 完了後） |
| **人レビュー観点** | **各フェーズで承認ゲート**（問い設計 / データ十分性 / 解釈妥当性 / 追加検証必要性） |
| **成果物** | アドホック分析レポート |

---

## レポート種別

| 種別 | 用途 | 進め方 | 主な出力 |
|---|---|---|---|
| 深掘り分析 | 特定の問いに答える | 4フェーズ承認ゲートを厳密に適用 | Markdown/HTML |
| 簡易分析スライド | 監査・設計資料の補助資料として全体像を示す | 対象期間と主要切り口を先に固定し、通しで作成 | スライド用Markdown/PDF |

簡易分析スライドでは、細かい仮説検証よりも、クライアントが次に確認・改善すべき論点を短時間で理解できることを優先する。

## 4フェーズの詳細

### Phase 0: 前段読み込み（Step 0）
- 01 コンテキストストアの `summary_markdown()` で前提を補完（gotchas は必ず遵守）
- 03 外部リサーチ（競合・市場・ユーザーの声）を仮説形成の材料にする
- 04 基本分析レポートを読み、既知の基本指標（チャネル・デバイス・月次推移等）を把握。**再取得せず引用し、深掘り差分に集中する**
- 前段成果物が無い場合はその旨を明示し、通常フローで進める

### Phase 1: 問い構造化
- 目的（答えたい本質的な問い）
- 主要指標（GA4 メトリクス）
- 切り口（ディメンション）
- 想定される仮説（複数。03/04 の findings を出発点にする）
- 参照した前段成果物の一覧

### Phase 2: データ取得
- `scripts/fetch_ga4.py` を必要回数実行
- メインクエリ + 詳細クエリ + 比較期間クエリ
- 結果を Markdown 表で整理

### Phase 3: 結果解釈
- 仮説との照合
- 要因分解
- 前提と限界の明示

### Phase 4: 追加検証アイデア
- 優先度別の次の分析候補
- 確認すべきポイント

## エラー・補完ルール

- 分析依頼が曖昧な場合は質問で具体化
- 03/04 の前段成果物が見つからない場合は「前段未実施」と明示して進める（黙って省略しない）。02 と重複する基本集計を依頼された場合は、02 の実施を先に提案する
- データ取得失敗時はエラーメッセージごとに対処を案内
- サンプル少（30セッション未満等）の場合は信頼性の限界を明記
- 各フェーズで承認なく次へ進まない
- 簡易分析スライドでは、成果イベントの定義変更や過剰発火が疑われる場合、成果数を事業成果として断定しない
- `gtm.*` など実装由来のイベントが多い場合、イベント数をユーザー行動量として扱わない
- `hostName` で複数ドメインが出る場合、クロスドメイン設定や参照元欠損の可能性を注記する
- 予約・申込ドメインがある場合、`landingPagePlusQueryString` 全件で `/store/`、`/reserve/`、`/booking/` などから始まるセッションを確認し、店頭・QR・直接申込の利用を媒体評価から分ける
- ページ関連は `ドメイン → サイト構造 → ページ` の順に整理する。サイト構造は `pagePath` 全件をURL構造でグループ化し、ページ別表ではCV列を無理に入れない
