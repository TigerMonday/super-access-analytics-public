# 競合デスクリサーチ

開始前に `../research-quality-standard.md` と `../research-methodology-basis.md` を全文読み、
調査設計・根拠台帳・成果物へ適用する。

公開情報のみで直接競合・代替手段から意思決定に必要な対象を選び、サイト・コーポレート・IR資料を
読み込んで比較マトリクスと仮説別所見を出力する。4〜6社は読みやすさの目安であり、主要競合の定義ではない。

## いつ使うか

- 案件キックオフ直後、競合分析ツール契約前に初期仮説を肉付けしたい
- ツール契約済みでも、定量データで見えないUX・コンテンツ・戦略意図を補完したい
- 提案資料の「業界・競合」章の素材を作る
- クライアントが立てている仮説を、競合の実装と照合して裏取りする

## アウトプット

`research/YYYYMMDD_competitor_desk/desk_research.md` に以下を出力:

1. **比較マトリクス**（10〜15観点 × 4〜6社の表）
2. **自社サービスメニュー×想定顧客マップ**（外部リサーチ統括スキルの想定顧客仮説の出発点。対象クライアントの案件で、ペルソナ・態度変容ジャーニーを作る場合のみ）
3. **仮説別所見**（クライアントが持つボトルネック仮説ごとの一次所見）
4. **IR・中計サマリ**（上場企業がある場合）
5. **次ステップへの申し送り**（定量検証で見るべき観点、要ヒアリング項目）

## 手順

### Phase 0: スコープ確定（5分）

ユーザーに以下を確認してから始める:

- ユーザーがすでに想定している対象企業・代替手段（出発点であり、確定リストではない）
- 分かる範囲の各社URL（不足分は公式ページを発見して確認し、ユーザーにURL一覧の作成を要求しない）
- 上場の有無（IR対象を判定）
- クライアントが既に持っているボトルネック仮説（議事録があれば読み込む）
- 重点観点（価格戦略 / UX / コンテンツ / AI機能 / 業種特化 / その他）

### Phase 0.5: 比較対象を選ぶ

`market-landscape-research` の成果物があれば、そこで定義した市場境界と候補集合を読む。無い場合は、
最低限、顧客課題、商品・サービス、対象顧客、地域を明記し、次の3群から候補を発見する。

1. 同じ顧客へ近い提供方法で同じ課題を解く直接競合
2. 内製、手作業、隣接カテゴリ等、別の方法で同じ課題を解く代替手段
3. 販路・能力・顧客基盤を転用して参入し得る候補

比較表に載せる4〜6対象は、知名度や検索上位だけでなく、顧客の比較候補、規模、提供方法、地域、
代替性の違いが意思決定に役立つように選ぶ。除外した主要候補と理由も残す。

### Phase 1: Webサイト表層スキャン

WebFetchで各社サイトを巡回。1社あたりトップ＋主要2〜3ページを取得。

**確認する観点（候補セット）**。先に顧客の選定基準と今回の意思決定を確認し、関係する行だけを使う。
下表を業種に関係なく機械的に埋めない。

| カテゴリ | 観点 |
|---|---|
| 業態・ターゲット | 業態、主ターゲット業種、地域 |
| 商品 | カテゴリ数、SKU規模感、PB有無 |
| **価格戦略** | 価格表示の有無、ログイン要否、見せ方 |
| **登録・審査** | 申請プロセス、所要日数、与信方法 |
| 決済 | 対応決済手段、掛け払い対応 |
| 配送 | 配送エリア、最低注文金額、送料 |
| **AI機能** | レコメンド、レシピ提案、チャット、検索AI |
| コンテンツ | 業種特化LP、オウンドメディア、特集の更新頻度 |
| UX機能 | クイックオーダー、サンプル制度、再注文、ポイント・ランク |
| サポート | 電話/チャット、営業時間、FAQ充実度 |

比較軸は全社で同じ定義・確認条件に揃える。自社だけが強く見える軸を後から追加しない。比較不能な項目は
空欄を推測で埋めず「未確認」または「非公開」とする。企業の公式ページは、その企業の提供内容を示す
根拠にはなるが、顧客が重視していることや市場での優位性を示す根拠にはならない。

取得は利用環境で許可されたブラウザ／Web取得機能を使い、元ページを目視できた項目だけを記録する。
任意URLを汎用コードで直接取得したり、Bot対策・ログイン・アクセス制限を迂回したりしない。
JS必須等で本文を確認できないページは検索スニペットで補完せず「未確認」とする。

### Phase 1.5: 自社サービスメニュー×想定顧客マップ（想定顧客仮説の出発点）

**対象クライアントの案件で、外部リサーチ統括スキル（`external-research-coordinator`）がペルソナ・
態度変容ジャーニーを作る場合に実施する**（3C・比較マトリクスだけが目的の依頼ならスキップしてよい）。

自社（分析対象クライアント）のサービスページ・料金ページ・事例分類を、**サービスメニュー単位**で
読み、メニューごとに「誰の、どんな状態に向けて売っているか」を抽出する。

**粒度の注意（最重要）**：「デジタルマーケティング全般の支援」のような事業ドメイン単位でまとめると
想定顧客が曖昧になり、そこからペルソナを逆算できない。サービスページの見出し・料金プラン単位
（例：「SEO支援」「広告運用」「データ分析」「組織開発」）まで分解する。

**取得元（優先順）**:

1. 料金ページ（プラン別に対象を明記していることが多い）
2. サービスメニューページ（各メニューの「こんな方に」「対象」「課題」の記載）
3. 事例ページの分類（業種・規模・課題別の事例カテゴリ）
4. 採用ページ・IR資料（顧客セグメントへの言及があれば補助的に使う）

**出力形式**:

```markdown
| サービスメニュー | 想定顧客像（会社側の記載） | 出典（ページ・引用） |
|---|---|---|
| SEO支援 | 自然検索流入が伸び悩む中堅BtoB企業の担当者 | services/seo ページ「こんな課題に」 |
| 広告運用 | 広告費を投下しているがCPAが合わない担当者 | services/ads ページ料金表下部の対象記載 |
| ... | | |
```

各行が `customer-understanding.yaml` の `personas[].persona_basis: service_derived` の直接の
材料になる（該当する障壁・刺激の `evidence_type: service_derived` の `evidence` にこの表の出典を
そのまま使う）。会社側の記載が「対象」を明示していない場合は、料金プラン名・機能説明から素直に
読み取れる範囲に留め、憶測で補わない（読み取れなければその行は空欄にし、`unresolved` に回す）。

### Phase 2: IR・中期経営計画リサーチ（上場企業のみ）

上場企業の場合、以下の優先順で読む:

| 資料 | 入手元 | 見るポイント |
|---|---|---|
| **中期経営計画** | 各社IRサイト > 経営計画/中計 | EC・DX投資、M&A方針、KPI、3〜5年戦略 |
| **決算説明資料**（直近） | IRサイト > 決算情報 | EC売上比率、新規/既存売上、課題認識 |
| **有価証券報告書**（最新） | EDINET or IRサイト | セグメント別収益、設備投資、研究開発、リスク |
| 統合報告書 | IRサイト > IRライブラリ | サステナビリティ、人的資本、長期ビジョン |
| 適時開示（直近1年） | TDnet | M&A、業務提携、組織変更 |

**EDINET API活用**（有報の機械取得）:

```bash
# EDINETで企業の有報書類一覧を取得
curl "https://disclosure.edinet-fsa.go.jp/api/v2/documents.json?date=YYYY-MM-DD&type=2&Subscription-Key=<KEY>"
# 書類IDから本文ZIP（XBRL+PDF）をダウンロード
curl "https://disclosure.edinet-fsa.go.jp/api/v2/documents/<docID>?type=1&Subscription-Key=<KEY>" -o ir.zip
```

APIキー未取得の場合は、各社IRサイトを WebFetch で直接巡回。

**まとめる観点**:
- 経営トップが言及する **EC・DXのキーワード頻度**（「EC強化」「DX投資」「AI活用」が何回出るか）
- 公開された **EC事業の数値目標**（売上、GMV、新規顧客数）
- **競合への言及**（M&A・業務提携相手、自社が「競合」と認識している企業群）
- **重点投資領域**（設備投資の内訳から物流・IT投資比率）

非上場企業の場合は: コーポレートサイトの「会社概要」「事業案内」「採用情報」「ニュースリリース」、業界紙の取材記事（日経MJ・業界専門紙等）、求人票（採用ポジションから組織体制を推定）を代替ソースに。

### Phase 3: 比較マトリクスの作成

10〜15行 × 4〜6列の表に集約。**読み手が3秒で差分を掴める粒度**にする。

```markdown
| 観点 | **自社** | 競合A | 競合B | 競合C |
|---|---|---|---|---|
| URL | [...] | [...] | [...] | [...] |
| 業態 | ... | ... | ... | ... |
| 主ターゲット | ... | ... | ... | ... |
| **価格表示** | **ログイン必須** | 配送先選択で絞込 | **税込価格を公開** | **税込価格を公開＋掛け払い** |
| **審査プロセス** | **3営業日** | 即時 | 即時 | 即時 |
| 支払い方法 | ... | ... | ... | ... |
| **AI機能** | **なし** | なし | なし | なし |
| 業種特化LP | 弱い | カテゴリ階層のみ | 子ども園・介護等独立 | 業種別ソリューション |
| ... | | | | |
```

**強調ルール**:
- 自社と差がある観点は `**bold**` で見出しと値を強調
- 行をカテゴリ順（業態 → 商品 → 価格 → 機能 → コンテンツ → サポート）に並べる
- 「（推定）」「（要確認）」を率直に表記。憶測を断定で書かない

### Phase 4: 仮説別の一次所見

クライアントが持つボトルネック仮説ごとに、競合との比較から見えた所見を書く。

**型**:

```markdown
### 仮説X: <仮説の文>

- **自社**: 競合との差分（具体）
- **競合A**: 実装状況
- **競合B**: 実装状況

**示唆**: <競合トレンドと自社のギャップ>
**検証軸**: <次に定量データで確認すべきこと>
```

**書き方の鉄則**:
- 「示唆」は **言い切らない**。「〜の可能性」「〜から距離がある可能性」など、検証前であることを表現
- 「検証軸」で **次のステップに渡せる形** にする（GA4のどの指標で確認するか等）
- 議事録の仮説と整合しないファインディングは率直に書く（否定でも肯定でも）
- 「競合にある」だけで自社も実装すべきと結論しない。顧客の重要課題、自社の提供方針、実装コストの
  いずれかと接続できなければ観測事実にとどめる
- 競合の組織能力、原価、社内プロセスは、公開された活動から推測できる範囲を超えて断定しない

### Phase 5: 次ステップへの申し送り

レポート末尾に必ず2つのセクション:

```markdown
## 競合分析ツールで見るべき定量観点

| 指標 | 想定される仮説の検証ポイント |
|---|---|
| セッション数推移（月次） | 自社の頭打ちは業界共通か / 相対的に遅れているか |
| 流入チャネル構成 | 広告依存度・オーガニック比率の比較 |
| トップLPと滞在時間 | 価格公開サイトの方が商品詳細到達率が高いか |
| 検索キーワード | 業種別クエリでの競合優位性 |
| ... | ... |

## ギャップ・要確認事項

- [ ] <未確定の競合URL> — クライアント指定待ち
- [ ] <自社GA4で深掘りすべき項目>
- [ ] <ヒアリングで確認すべき項目>
- [ ] <次回MTGの論点>
```

## ディレクトリ構成

```
research/YYYYMMDD_competitor_desk/
├── desk_research.md       # メイン成果物
├── data/                  # 取得したHTML、IR PDFのスナップショット
│   ├── <company>_top.html
│   ├── <company>_ir_chukei.pdf
│   └── ...
└── scripts/               # メタ抽出スクリプト等
    └── fetch_meta.py
```

## やってはいけないこと

- 競合の **定量データ（セッション数等）を表層スキャンで推測しない**。それは `competitor-traffic-analysis` スキルの仕事
- 価格を見せていない競合の価格を推測しない。「ログイン要のため不可視」と明記
- IR資料の数字を **抜粋元（決算説明資料 P.12 等）なしで引用しない**
- 競合のスクリーンショットを成果物に貼らない（著作権配慮）。比較は文章＋表で表現
- 「示唆」を断定形で書かない。定量検証前は仮説のまま
- Phase 1.5「自社サービスメニュー×想定顧客マップ」を**事業ドメイン単位の粗い粒度**でまとめない（「デジタルマーケティング支援」だけでは想定顧客が逆算できない。サービスメニュー単位まで分解する）
- Phase 1.5で会社側の記載に無い想定顧客を憶測で埋めない（読み取れなければ空欄にし `unresolved` へ）
