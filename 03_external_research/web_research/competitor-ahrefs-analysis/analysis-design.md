# Ahrefs 分析設計（直接API版）

作成: 2026-07-12 / 対象: `03_external_research/web_research/competitor-ahrefs-analysis`

> **この文書の位置づけ**: Ahrefs を直接 API で叩けるようになったことを受けて、「何のために・何を取り・どう判断し・どこに出すか」を定めた設計書。実行手順の詳細は [SKILL.md](./SKILL.md)、取得スクリプトは `scripts/fetch_ahrefs.py` を参照。実行エージェント（Sonnet 等）はこの文書の判断ルールに従うこと。**このスキル自体、Ahrefs の契約（API トークン）が無いと使えない任意機能である**（詳細は SKILL.md 冒頭）。

---

## 1. 03テーマの中での Ahrefs の役割

市場・顧客理解テーマのデータ源には性格の異なるものがあり、答えられる問いが違う。

| データ源 | 分かること | 分からないこと |
|---|---|---|
| **Ahrefs（本設計）** | **検索順位・検索ボリューム・KD（難易度）・被リンクの一次データ** | サイト内行動・CV（それは GA4＝01/02/06 の領分） |
| Web検索（desk research） | 競合のコンテンツ・訴求・価格などの定性情報 | 定量データ全般 |

Ahrefs が答えるのは要するに **「検索経由の集客で、競合に対してどこで負けていて、どの打ち手から取り組むと勝てるか」**。

## 2. 実行基盤（前提）

- **認証**: API トークンは、公開版の他の鍵と同じ置き場所の方式に揃える。環境変数
  `AHREFS_API_TOKEN` → `~/.saa/credentials/ahrefs/token.txt` の順で解決する
  （`fetch_ahrefs.py` の `resolve_token()`）。トークンをリポジトリ・レポート・ログに書かない
- **ユニット予算**: Ahrefs は従量課金（行数 × 選択列数）の API のため、**取得量には必ず上限を置く**
  （プラン名・月間割当ユニット数は契約によって異なるため、このスキルの手順・既定値はプラン非依存で書く。
  各自の契約内容は `limits` サブコマンドで確認する）。
  **⚠️ 課金は「行数 × 選択列数」**（2026-07-12 の実案件実行で実測確定。当初の「1行≒1ユニット強」は誤り）。
  **2026-07-14 列削減**: `gap` が内部で使う organic-keywords / refdomains の `select` は、build_keyword_gap /
  build_backlink_gap / gap のレポート出力のどこからも参照されていない列（競合側の `sum_traffic` ・
  `best_position_url`、refdomains の `first_seen`）を確認の上で外し、**競合側 organic-keywords 6列→4列**・
  **自社側 organic-keywords 6列→5列**（`best_position_url` はリライト/内部リンク強化の対象ページ特定用に残し、ギャップ結果行へ `own_best_position_url` として伝搬させる）・
  **refdomains 4列→3列** に削減した（単体の `organic-keywords` サブコマンドは人間が表を見るための
  独立実行のため、従来通りフル6列を既定にし `--select` で上書き可能）。
  gap のフル実行（自社＋競合4社・既定limit）の最悪ケースは **旧約46,000 units → 新約33,550 units（約27%減）**
  （内訳: 自社DR 50 + 自社kw 2,000行×5列=10,000 + 競合kw 4社×1,000行×4列=16,000 + refdomains 5サイト×500行×3列=7,500）。
  併せて、自社側 organic-keywords 取得にも競合側と同じ `--min-volume`（既定100）の絞り込みを適用する
  （ギャップ判定は競合側で volume≧しきい値に絞った候補語だけを見るため、自社の低ボリューム語を取得しても
  判定には使われず、判定品質を落とさず行数=課金だけ減らせる）。
  `gap` には事前見積りガードが入っており、最悪ケースが「残量−10,000」を超えると実行を止める
  （キャッシュ命中や実行結果の行数が少なければ実消費は大きく下がるので、確信がある場合のみ
  `--force-units` で上書き可）。**実行前に必ず `limits` で残量を確認**し、残量 10,000 未満では取得系を実行しない
- **キャッシュ**: 取得データは `outputs/{client_id}/_data/ahrefs/` に `fetched_at` 付きで保存される。
  **2026-07-14〜 有効日数はエンドポイント別既定値**（overview系[domain-rating/backlinks-stats/metrics]・
  refdomains = 30日、organic-keywords = 14日、serp-overview = 7日で現状維持）を使う。根拠: 検索順位は
  日次で動くが打ち手の優先度判断に日次精度は不要、被リンク・DRは月単位でしか動かないため長めでよい。
  `--cache-days` を明示指定した場合は常にそちらが優先される（従来互換）。`--refresh` で強制再取得

## 3. ユースケース別の分析設計

### UC-1: 競合SEOポジション診断（初回診断・提案資料用）

- **目的**: 「自社と競合の SEO 上の体格差」を1枚で示す。提案の現状把握章・新規クライアントの初回診断で最初に回す
- **入力**: 自社ドメイン＋競合3〜5社、国コード（日本案件は `jp`）
- **取得**: `overview` サブコマンド（domain-rating / backlinks-stats / metrics を統合取得）
- **アウトプット**: 横並び表＋所見3行

| サイト | DR | 参照ドメイン数 | オーガニックKW数 | 流入推計(月) |
|---|---:|---:|---:|---:|

- **判断ルール**:
  - DR 差が 15 以上ある相手の「勝ちキーワード」は KD の高い領域では追わない（UC-2 の KD 閾値に反映）
  - 流入推計は絶対値でなく**相対比較のみ**に使う（Ahrefs の Traffic は推計。断定表現をしない — SKILL.md の禁止事項）
- **ユニット目安**: 実測 150/ドメイン（domain-rating＋backlinks-stats＋metrics の3呼び出し）

### UC-2: キーワードギャップ → コンテンツ打ち手（本命。06/1 全体施策のインプット）

- **目的**: 「競合は1ページ目にいるのに自社が取れていないキーワード」を洗い出し、現実的に取れるものだけに絞って打ち手にする
- **入力**: UC-1 と同じドメインセット。**ブランド語除外リスト**（社名・サービス名・URL片。必ず最初に作る）
- **取得と計算**: `fetch_ahrefs.py gap` サブコマンドで実行（2026-07-12〜）。取得（organic-keywords を自社＋各競合）から突合・KD閾値判定・推奨アクション判定までコードに固定されている。**実行エージェントはこの計算を手で再実装してはならない**（毎回LLMが計算を書き直すと結果が揺れ、レポートの数値が再現できなくなるため）。条件の変更はフラグ（`--min-volume` 等）で行う
- **ギャップ抽出条件**（gap の既定値。フラグで調整可）:
  - 検索ボリューム ≥ 100/月
  - 競合順位 ≤ 10（1ページ目）
  - 自社順位 > 20 または未取得
  - ブランド語除外後（`--exclude` で指定）
- **KD 閾値ルール**（自社 DR に応じて「現実的に取れる」ラインを変える）:

| 自社DR | 狙うKD上限 |
|---|---|
| 〜39 | KD < 30 |
| 40〜59 | KD < 45 |
| 60〜 | KD < 60 |

> **KD の取得元に関する注意（2026-07-12 実測）**: KD は `organic-keywords` の `keyword_difficulty` 列から取る（正常動作）。個別キーワードの KD/CPC をまとめて引く `keywords-explorer/overview` 系エンドポイントは、現在 Ahrefs 側の障害でアカウント問わず 500 エラーになるため、`kw-overview` サブコマンドは volume のみのフォールバック動作になっている（`volume-history` 経由）。ギャップ抽出は organic-keywords ベースで完結するので UC-2 の実行に支障はない。KD/CPC の単発取得が必要になったら Ahrefs サポートに問い合わせる

- **アウトプット**: KD×ボリュームのマトリクスで優先度をつけたキーワードリスト **5〜10個**。各行に推奨アクションを1つ付ける（新規記事 / 既存リライト / 内部リンク強化 のいずれか。判定は自社の**順位（`best_position`）の数値**で機械的に行う: 未取得または51位以下→新規、21〜50位→リライト、それ以上（かつ `--own-min-position` より下位）→内部リンク強化。`best_position_url` は判定には使わず、リライト・内部リンク強化の行に**打ち手の対象ページ特定用**として付す — 結果JSONの `own_best_position_url` フィールドとレポート表の「自社URL」列。自社未取得の行は空欄）
- **06連携**: 結果ファイルを 06/1 全体施策分析が「外部要因・集客の伸びしろ」として読む（成果物の置き場は §5）
- **ユニット目安**（2026-07-14 列削減後）: **競合側 4,000/ドメイン**（1,000行×4列。行×列課金のため limit がそのまま効く）。
  自社側は own-limit 既定2,000×5列＝最大10,000（自社側にも `--min-volume` の絞り込みが入るため、実際の行数は
  上限より少なくなることが多い）。競合4社の最悪合計 約26,000（4,000×4社＋自社10,000＝26,000）
  — gap の事前見積りガードに従い、残量が薄い月は競合数か limit を絞る

### UC-3: 被リンクギャップ → 獲得チャネル候補

- **目的**: 競合が持っていて自社に無い被リンク元（メディア・団体）を抽出し、PR・寄稿・掲載依頼の候補リストにする
- **取得と計算**: UC-2 と同じ `gap` サブコマンドが被リンクギャップも同時に出す（refdomains を自社＋競合で取得し、競合側にのみ存在する参照ドメインを抽出。DR≥50・上限500行/ドメインが既定）
- **アウトプット**:
  - 獲得候補メディアリスト（DR 降順、複数競合にリンクしているものを上位に）
  - 競合の新規参照ドメイン獲得トレンド（急増していれば「PR 投資が走っている」シグナルとして所見に書く）
- **判断ルール**: ディレクトリ型・スパム様のドメインはリストから除外（DR が高くても anchor が不自然なものは候補にしない） <!-- leak-ok: 「スパムのような」の意味の一般語（様＝〜のような）で、人名・社名の敬称ではない -->
- **ユニット目安**（2026-07-14 列削減後）: **1,500/ドメイン**（500行×3列。`first_seen` は未使用と確認の上で削除） × ドメイン数

### UC-4: SERP 実勢確認（UC-2 の補助・スポット）

- **目的**: UC-2 で上位に来たキーワードについて、実際の SERP の顔ぶれを確認し「想定外の強豪（メディア・公的機関）がいて実は取れない」を打ち手決定前に潰す
- **取得**: `serp` サブコマンドを**優先キーワード上位 5〜10 個だけ**に実行（乱発しない）
- **判断ルール**: 上位3位以内が DR80 超のドメインで占められているキーワードは、KD が低くても優先度を1段下げる
- **ユニット目安**: **300〜500/キーワード**（実測450。日本のSERPはAI Overview・PAA等の特集枠が同じ順位番号で複数行返り、行数課金が膨らむ。スクリプト側でオーガニック行のみに絞って保存している）。乱発禁止の理由はこれ

## 4. 標準の実行順序

1. `limits` で残ユニット確認（10,000 未満なら中止して報告）
2. スコープ確定（自社・競合・国・ブランド語除外リスト）— SKILL.md Phase 0 の様式 <!-- leak-ok: 「様式（フォーマット）」の一般語で、人名・社名の敬称ではない -->
3. UC-1 → UC-2 →（必要に応じ UC-3 / UC-4）
4. レポート作成（§5 の場所へ）。**必ずデータ取得日を明記**（キャッシュ利用時は元の取得日）
5. 消費ユニットをレポート末尾に記録

## 5. 成果物の置き場と形式

02 テーマ共通の置き場ルール（`outputs/{client_id}/03_research/` 配下、生データとレポートを分ける）に従う:

- **生データ**: `outputs/{client_id}/_data/ahrefs/*.json`（スクリプトが自動保存。`fetched_at`・`units_consumed` 入りエンベロープ）
- **分析レポート**: `outputs/{client_id}/03_research/{YYYYMMDD}_competitor_ahrefs/ahrefs_analysis.md`
  - 構成: ①ポジション横並び表 ②キーワードギャップ優先リスト ③被リンク獲得候補 ④（実施時）SERP確認結果 ⑤所見と推奨アクション ⑥データ取得日・消費ユニット
- client_id は 01 コンテキストストアの登録名を使う（未登録なら先に登録。表記の揺れを作らない）

## 6. やってはいけないこと（SKILL.md から継承＋API版で追加）

- Traffic 推計値を絶対値として断定しない
- ブランド語と一般語を混ぜたランキングを出さない
- KD だけで打ち手を決めない（DR・トピカル権威を加味）
- データ取得日を書き忘れない
- **`--refresh` を習慣的に付けない**（エンドポイント別既定キャッシュ日数で十分。ユニットの無駄）
- **`limit` を外して全行取得しない**（organic-keywords・refdomains は上限必須）
- トークンをレポート・ログ・コミットに含めない
