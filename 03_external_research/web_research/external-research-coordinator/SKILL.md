# external-research-coordinator スキル

開始前に `../research-quality-standard.md` と `../research-methodology-basis.md` を全文読み、
すべての子スキルと統合成果物へ適用する。

「市場・顧客理解エージェント」の単一エントリーポイント。子スキル群を束ねて
**3C分析 → ペルソナ → 態度変容カスタマージャーニー** を作る。

## 配下の子スキル一覧

```
external-research-coordinator（本スキル）
│
├─ Market（市場）
│   └─ market-landscape-research           市場境界・公的統計・代替手段・競争構造
│
├─ Competitor（競合）
│   ├─ competitor-desk-research            公式Web + IR/中計の比較マトリクス
│   ├─ competitor-case-study-research      公式導入事例 + 業種×規模マップ
│   └─ competitor-company-deep-dive        競合1社の企業ベース深掘り
│
├─ Customer（顧客）─ 顧客の声による仮説検証（無くても未確認の仮説は作れる）
│   ├─ competitor-review-research          レビューサイト横断（B2B SaaS / B2C / コスメ / 飲食 等）
│   ├─ competitor-qa-research              Yahoo!知恵袋 / OKWAVE 等の Q&A
│   ├─ competitor-social-research          X / Reddit / 5ch 等の SNS
│   └─ competitor-case-study-research      （Competitor欄と兼用）競合の公式導入事例。自社の事例が
│                                           無い会社でも、競合事例に登場する顧客層の実在確認に使える
│                                           （「自社を選ぶか」までは確認できない点に注意）
│
├─ Company（自社）─ 想定顧客仮説の出発点（サービスから逆算）
│   ├─ competitor-desk-research の Phase 1.5「自社サービスメニュー×想定顧客マップ」
│   └─ 01の登録情報（profile.yaml）＋ 公式サイト
│
└─ 検索順位・被リンク（任意・Ahrefsの契約が必要。3Cの直接の材料ではない）
    └─ competitor-ahrefs-analysis          検索順位・KD・被リンクの一次データ（契約が無ければ丸ごとスキップ）
```

## 役割

| 項目 | 内容 |
|---|---|
| キャッチー名 | 市場理解係 |
| 正式名 | 市場・顧客理解エージェント |
| 概要 | Web 上の公開情報をリサーチして 3C分析を作り、そこから態度変容フローが異なる単位でペルソナを分け、ペルソナごとに態度変容カスタマージャーニー（何が起きたら次の段階に進むか）を組み立てる |
| データソース | Web（公開情報）。GA4データは使わない（実際の流入経路・ページ遷移は扱えない） |
| インプット | 調べたいテーマ、対象（競合 / 市場 / 商材）、期間、欲しい形式（表 / 箇条書き）、出典必須条件 |
| 人レビュー観点 | 情報の信頼性、出典の妥当性、一次情報の有無、結論の飛躍がないか、根拠のないペルソナ・刺激仮説を人数/項目合わせで作っていないか |
| 成果物 | 3C分析 → ペルソナ → 態度変容カスタマージャーニー統合レポート（+ 01への保存） |

## 標準フロー

市場の範囲・競合・顧客像を確定する前に `../service-understanding.md` を必ず実行する。既存contextから対象URLを確認した後、自社・競合のサービス一覧と各ページを読み、サービス一覧を保存する。Step 1の質問で公開サイトから分かる事業説明を利用者に求めない。

ユーザーから「市場と顧客を調べて」「競合を比較して」などと自然文で依頼されたら、このスキルを入口にする。クライアントに紐づく調査では、依頼文の client_id または `list_clients()` の一覧から対象を確定する。成果物形式は依頼文→01の既定→利用者への確認の順で決め、既定が未登録なら他の不足質問とまとめて一度だけ聞く。無人実行で未設定ならMDだけで進め、仮の既定値は保存しない。汎用調査では client_id と成果物形式の既定保存は不要。

### Step 0. 01コンテキストストア読み込み（共通）
- 実行: `cd 01_context_management && uv run python -c "from context_store.loader import load_context; print(load_context('{client_id}').summary_markdown())"`
- 出力された「クライアント前提」（クライアント名・業種・ターゲット・gotchas・過去findings）を Step 1 のインプット整理に取り込み、**ユーザーには聞き直さない**。無い項目だけ質問する。
- gotchas（⚠ 分析時の注意）は必ず遵守する。
- client_id が01に未登録（出力が空）の場合は、`docs/standard-run-order.md` §2-1 のURL先行受付を使う。最初に対象サイトURLを確認し、サイト表示名と client_id はURL・サイト・GA4情報から候補を作る。曖昧・矛盾・重複がある場合だけ利用者へ確認し、`writeback.ensure_client_registered()` と `writeback.save_business_profile(site_url=...)` で最小登録して続行する。事業内容等のフル登録には進まない。クライアントに紐づかない汎用調査の場合はこのステップをスキップしてよい。
- ここで得られたクライアント名・サイト（`profile.client.name` / `client.site_url`）は、Step 1「対象」の既定値になる。決め方の優先順位は Step 1「対象の決め方」を見る（**リポジトリの文書から対象を推測することは禁止**。理由もそこに書く）。

### Step 1. インプットを構造化する

ユーザーの依頼から、以下 5 項目を埋める。不足は質問して埋める。
**ただし、すべて聞き終えてから動くのではなく、見えている範囲で着手しつつ並行で埋めていく**。

```markdown
| 項目 | 内容 |
|---|---|
| テーマ | （何を明らかにしたいか。例：競合との集客差 / レビュー上のポジション / 業界 KOL の動き） |
| 対象 | （対象製品名 / 競合社名リスト / カテゴリー） |
| 期間 | （取得対象期間。例：直近 12 ヶ月、過去 3 年） |
| 欲しい形式 | （表 / 箇条書き / マップ / バブルチャート / レポート全体） |
| 出典必須条件 | （一次情報のみ / 公式のみ / レビュー本文の引用要 等） |
| 案件タイプ | （B2B SaaS / B2C 商品 / EC / 飲食 / 業種混在 等） |
| 入手済みデータ | （議事録 / 過去の調査 / 競合の公開データ 等） |
| Ahrefs契約の有無 | （契約ありなら `competitor-ahrefs-analysis` を追加。無ければ聞かずに省く） |
| 利用者の一次情報（任意） | 問い合わせ・商談で顧客からよく言われることがあるか。次項「利用者ヒアリングの聞き方」参照 |
```

この表に加えて、**何を決めるための調査か**を一文で固定する。「市場を知りたい」のように
意思決定へつながらないテーマは、優先セグメント、提供価値、競合対策など判断対象へ分解する。

#### 完成を止める事前確認（必須）

対話可能な実行では、公開情報から分からず結論に影響する項目を1〜3問に絞って聞く。複数の抽象項目を1問へ列挙せず、利用者が回答できる具体的な問いにする。最低限、次を確認する。

- 比較したい競合の会社名・公式URL。選定を任された場合は、候補・URL・候補理由を示して確認する
- 今後増やしたい相談・案件。サービス名や実際の相談例で答えられるように聞く
- 顧客や営業から実際に聞いた選定理由・失注理由。把握していなければ「不明」でよい
- 引き受けない案件・約束しない成果・難しい条件と、既存の競合資料・商談資料の有無

回答が「分からない」「資料なし」でも確認完了としてよい。公開サイトからの推測を回答として補完しない。
調査期間・情報源は利用者に特別な指定がなければ標準値を適用し、質問枠を使わない。期間は直近24か月を優先し、情報源は公式サイト・公的機関・原典を優先する。必要な過去資料や第三者情報は補足として出所を明示する。
結果は `../research-intake.template.json` を基にテーマフォルダの `data/research-intake.json` へ保存する。
`not_asked` は未質問、`awaiting_reply` は質問済みの回答待ちとして区別する。調査開始時に未質問項目を1〜3問へまとめて聞き、質問を実際に送った後だけ対象項目を `awaiting_reply` へ変える。未完了項目が残る間も市場調査・自社理解・候補探索は進められるが、統合レポートの完成・配布・後工程への確定版連携は行わない。未質問項目を「利用者未回答」と報告しない。
完成前に `tools/validate_market_report.py` をレポートパス付きで実行し、事前確認記録も含めて合格させる。

#### 利用者ヒアリングの聞き方（顧客の声の材料が無い会社向け）

**自社サイトに事例インタビュー等のオウンドメディアが無い会社は多数派。** そういう会社でも、
利用者（サービス提供側）自身が営業・問い合わせ対応で顧客の生の声を持っていることが多い。
レビューサイトより確度が高いこともあるので、対話可能なら必ず聞く。

- **聞き方**：「ペルソナを教えてください」のような抽象的な聞き方はしない。相手が具体的に
  思い出して答えられる聞き方にする。例：「問い合わせや商談で、よく言われることはありますか」
  「導入を決めた人が、決め手として口にすることは何ですか」「逆に、検討をやめた人がよく挙げる
  理由はありますか」
- **答えが得られたら**：発言内容を根拠として使い、`evidence_type: customer_voice`
  （自社の顧客の声。レビュー・Q&A・SNSと同じ強さ）とし、`evidence` に「利用者ヒアリング
  （聞き取り日・概要）」の形で出典を残す。個人が特定される情報（社名・氏名等）はそのまま
  書かない。
- **答えられなくても止まらない。** 「特に無い / 分からない」であれば、①サービスから逆算する
  経路のみで進める。無回答を理由に質問を重ねたり、ペルソナ作成そのものを止めない。
- 無人実行（`claude -p` 等、対話を待てない実行）では、このヒアリング自体を省略してよい
  （聞けないことが分かっているものを聞こうとしない）。

#### 対象の決め方（最重要。誤ると成果物全体がクライアントに無関係なものになる）

「対象」（対象製品名 / 競合社名リスト / カテゴリー）は、次の優先順位で決める。**上から順に確認し、当たったところで確定する**。

1. **ユーザーが依頼文で対象を明示している場合**：それを最優先で使う。01の登録情報より常にこちらが勝つ（「競合を調べたい」「業界全体を見たい」など、自社以外を対象にする依頼は正当にあるため）。
2. **ユーザーの明示が無く、client_id が01に登録済みの場合**：Step 0 で読み込んだクライアント名・サイト（`profile.client.name` / `client.site_url`）を対象の既定値として使う。01の値をそのまま採用してよく、あらためて聞き直す必要はない（Step 0 の「ユーザーには聞き直さない」原則のとおり）。
3. **ユーザーの明示も01の登録も無い場合**（クライアントに紐づかない汎用調査）：対話可能なら、テーマと対象をユーザーに質問して確定する（従来どおり）。
4. **対話で確認できない無人実行**（`claude -p` 等のヘッドレス実行・スケジュール実行など、応答を待てない実行）で、上記1・2のどちらも無い場合：**対象を確定できないので、レポート作成に着手せず中断する**。docs/standard-run-order.md §4-2 の無人実行時の考え方（「質問できないので仮の既定を自分で選ばない」）と同じ扱いで、対象について「推測して進む」ことはしない。中断時は「対象が未確定のため中断した。対話セッションで対象を指定するか、01にクライアント登録した上で再実行してほしい」旨を出力に残す。

**禁止：対象が決まらないときに、リポジトリ内の文書（`README.md`、`CLAUDE.md`、`docs/` 配下等）から発行元・運営会社名を読み取って対象に使うこと。** 理由：これらの文書はこのツール自体（キットの配布元）についての記述であり、実際に分析しているクライアントとは無関係。特に公開版では配布元の企業名が必ずREADMEに書かれているため、この経路を許すと「自社の分析をしたい」という依頼が配布元企業の調査結果に化けてしまう（2026-08-23、無人実行でこの事故が実際に発生した）。対象の根拠は、常に「ユーザーの明示指定」または「01の登録情報」のいずれかだけにする。

#### 出力フォルダの決め方（同じ対象の再実行を積み上げない）

以前は実行するたびに `YYYYMMDD_<案件ID>_external_research/` のような日付付きフォルダを新規に作っていたため、
同じ対象（例: 自社）を何度も回し直すと `_v2`・`_再構築版` のようなフォルダが積み上がり、
「どれが最新か分からない」状態になっていた（実際に発生した）。**docs/standard-run-order.md §4 の
規約1・2（生成物のファイル名に日付を入れず、上書き前に `_past/` へ退避する）を03にも適用する。**

- **フォルダ名（テーマ識別子）は「対象」で決める。日付・実行回数は含めない。**
  - 対象が「01登録クライアント自身」（既定ケース）のとき：`outputs/{client_id}/03_research/customer_understanding/`
    固定。01の `customer-understanding.yaml` 自体がクライアントごとに1つ（1回の実行で丸ごと作り直す）前提の
    ファイルであることに揃えている。
  - 対象が「ユーザー指定の別対象」（競合・他社・自社以外の市場等）のとき：対象名を正規化した短いスラッグ
    （英数字・アンダースコア。例: `competitor_a`）を使う。**対象が違えば別フォルダ**（同じクライアントの
    中でも「自社」と「競合A」は別テーマとして両方残す）。
- **同じフォルダ名が既に存在する＝同じ対象の再実行。** 新しい統合レポートを書く前に、既存の
  `00_3c_persona_journey_report.md`（`.html` があれば同様に）を
  `{テーマフォルダ}/_past/{YYYY-MM-DD_HHMMSS}_00_3c_persona_journey_report.md` へ退避してから書き直す
  （規約2と同じ扱い）。**フォルダ名が違えば新規フォルダを作るだけで、退避は発生しない**（対象が違う調査は
  正当に並存する）。
- `data/child_reports/`（次項「出力する成果物の整理」参照）は生成物ではなく作業用の中間ファイルなので、
  `_data/` と同じ考え方で扱う（取得日プレフィックス付きで複数残してよい。上書きで前回分を消さない）。
- 出力先の決定にユーザーへの追加質問は発生しない（「対象の決め方」で確定した対象から機械的に決める。
  出力先を尋ねない原則のとおり）。

### Step 1.5. 市場境界と競合候補を作る

3Cまたは市場調査を含む依頼では、最初に `market-landscape-research` を実行する。顧客が解決したい課題、
商品・サービス、対象顧客、地域、期間で市場境界を定義し、直接競合・代替手段・参入候補のロングリストを
作る。ユーザー指定の競合は重要な候補だが、それだけを市場全体とはみなさない。

単一企業の公式情報だけを確認する依頼や、個別のレビュー・SNS調査では省略してよい。

### Step 2. 子スキル選択ロジック

入力に基づき、実行する子スキルを決める。**全部呼ぶことを目的にしない**（不要な呼び出しは作業を増やすだけ）。

#### 案件タイプ別の標準セット

| 案件タイプ | 必ず使う | 任意で追加 |
|---|---|---|
| **B2B SaaS / ツール** | market-landscape-research、competitor-desk-research、competitor-review-research、competitor-case-study-research | competitor-company-deep-dive（注目競合のみ）、competitor-qa-research（疑問の型を取りたい場合） |
| **B2C 商品 / 家電 / ガジェット** | market-landscape-research、competitor-desk-research、competitor-review-research（B2C 系サイト）、competitor-social-research | competitor-qa-research（選定軸を取りたい場合） |
| **EC（食材・アパレル等）** | market-landscape-research、competitor-desk-research | competitor-review-research（楽天・Amazon レビュー）、competitor-social-research |
| **コスメ・美容** | market-landscape-research、competitor-review-research（@cosme / LIPS）、competitor-social-research（Instagram / TikTok） | competitor-qa-research、competitor-desk-research |
| **飲食店 / 施設** | market-landscape-research、competitor-review-research（食べログ / Google マップ）、competitor-social-research（X / Instagram） | competitor-desk-research（店舗チェーンなら IR も） |

**Ahrefs の契約がある場合**：案件タイプによらず「任意で追加」に `competitor-ahrefs-analysis` を足してよい（検索順位・KD・被リンクの一次データが欲しいとき）。**契約が無い場合はこの子スキルの実行自体を提案しない**（提案しても使えないだけで、他の子スキルの実行を妨げない）。

**ペルソナ・態度変容ジャーニーを含む成果物のとき**：`competitor-desk-research` は上表で「任意」の
案件タイプ（コスメ・美容／飲食店等）でも、Phase 1.5「自社サービスメニュー×想定顧客マップ」だけは
実施する。これが想定顧客仮説の出発点（サービスから逆算）になるため。3C分析・比較マトリクスだけが
目的で、ペルソナを作らない依頼なら省いてよい。

#### 上場・非上場による分岐

```
上場企業対象 → competitor-desk-research の IR フェーズを厚めに
非上場対象 → competitor-desk-research の Web 表層中心 + 業界紙
```

#### 順序の原則

1. **市場境界と候補集合**：market-landscape-research で、何を同じ市場として比べるかを決める
2. **競合仮説づくり**：competitor-desk-research で、直接競合・代替手段から比較対象を絞る
3. **検索順位の裏付け（Ahrefs 契約がある場合のみ）**：competitor-ahrefs-analysis — 検索順位・キーワードボリューム・被リンクの一次データで、desk-research の仮説キーワードを裏付ける。契約が無ければこのステップごと飛ばして次に進む
4. **第三者の声**：competitor-review-research → competitor-qa-research → competitor-social-research（マクロ → 疑問 → リアルタイムの順）
5. **事例**：competitor-case-study-research（業種×規模マップ）→ competitor-company-deep-dive（注目競合のみ）
6. **統合**：本スキルで束ねる

ただし**緊急性の高い問い**（「『競合』の最近の動きを 1 時間でまとめて」等）には、上記の順序を崩して
competitor-company-deep-dive 単独 or competitor-social-research + competitor-review-research の 2 本立てだけで返すこともある。

### Step 3. 子スキルを呼び出して順次実行

選んだ子スキルを順に呼ぶ。それぞれの出力（Markdown）はそのまま保持し、次の子スキルへの
インプットに必要な部分を抽出して渡す。**保存先はテーマフォルダ配下の
`data/child_reports/01_desk_research.md` のような番号付きファイル**（「出力する成果物の整理」参照）。
利用者が最初に開くのは統合レポート（`00_3c_persona_journey_report.md`）1本だけなので、
子スキルの個別成果物をトップレベルには置かない。

引き継ぎの典型例：
- competitor-desk-research の Phase 5「次ステップ」→ competitor-review-research のスコープ確定
- competitor-case-study-research の Step 5「業種×規模マップ」→ competitor-company-deep-dive の Step 1「調査動機」

### Step 4. 3C → ペルソナ → 態度変容カスタマージャーニーを組み立てる

子スキルが出した個別 Markdown から、**この順で**3段階を組み立てる。**GA4データは使わない**
（市場統計を含む外部公開情報を材料にするが、実際の流入経路・ページ遷移は書けない）。

**3Cはここで初めて使う。** 調査前に3つの欄を作って情報を当てはめない。市場境界、収集方法、
根拠台帳が先で、3Cは統合結果である。3Cの各要素を並べた後、顧客の重要課題、競合・代替の空白、
自社が実証できる能力の交点を示す。一つのCだけに根拠がある案は機会ではなく仮説に落とす。

**根拠を必ず示す。** 3Cの各要素、ペルソナの分岐理由、カスタマージャーニーの各段階が、どの調査結果から導かれたかを内部成果物で追えるようにする。子スキル成果物名と該当箇所は `data/child_reports/` の中間成果物と根拠台帳に残す。一次情報で確認できなかった項目は埋めず、`unresolved` に集約する。

**利用者向け統合レポートに付録は付けない。** 数値や判断を支える重要な公開出典は、本文の該当箇所に資料名つきで直接リンクする。全量の比較表、引用集、採用・除外理由、子スキル一覧、ローカルファイルのパスは社内用の `data/` にだけ保存する。同じ内容を本文と社内用資料の両方に長文で転記しない。

#### Step 4a. 3C分析

| 3Cの要素 | 材料（子スキル） |
|---|---|
| Competitor（競合） | market-landscape-research（直接競合・代替手段・参入候補）/ competitor-desk-research / competitor-company-deep-dive / competitor-case-study-research |
| Customer（顧客） | market-landscape-research（母集団・セグメント）/ competitor-review-research / competitor-qa-research / competitor-social-research / competitor-case-study-research（競合事例。顧客層の実在確認のみ）/ 利用者ヒアリング（Step1「利用者の一次情報」） |
| Company（自社） | 01の登録情報（`profile.yaml` の業種・事業内容・toB/toC）＋ 公式サイト ＋ competitor-desk-research の「自社サービスメニュー×想定顧客マップ」（Phase 1.5） |

各要素は要約1〜3文＋根拠（子スキル成果物名＋該当箇所、Companyは「01登録情報」または「公式サイト」）。
続けて「3Cの交点」を置き、顧客課題・競合または代替の空白・自社の実証可能な能力を1行ずつ対応させる。

#### Step 4b. ペルソナ

**属性の羅列は作らない。** 年齢・職業・家族構成・趣味のような、態度変容の説明に効かない属性は
書かない。書くのは **態度変容の説明に必要な属性だけ**（例：決裁権の有無、予算の承認フロー）。

##### ペルソナ構築の3経路（サービスからの逆算は仮説の出発点）

ペルソナは次の3経路のいずれか（または複数）で構築する。サービスからの逆算は、顧客調査が無い場合にも
作れる**会社側の想定顧客仮説**であり、実在や需要を確認した顧客像ではない。レビュー・Q&Aに顧客の声が
集まらない会社でも止まらないための出発点として使い、自社の実利用者・見込み利用者の声が得られたら
検証・修正する。①だけでも仮説成果物は作れるが、確認済みペルソナとは呼ばない。

| 経路 | 材料 | 09での記録 |
|---|---|---|
| **① サービスから逆算（仮説の出発点）** | competitor-desk-research の Phase 1.5「自社サービスメニュー×想定顧客マップ」。自社が**サービスメニュー単位**で「誰の、どんな状態に向けて売っているか」を決めている事実が根拠。これは会社側の想定の根拠であり、顧客需要の確認ではない。**粒度が重要**：「デジタルマーケティング全般の支援」のような事業ドメイン単位では想定顧客が曖昧で逆算できない。「SEO支援」「広告運用」「データ分析」「組織開発」のようにサービスメニュー単位まで分解する | `persona_basis: service_derived` / 該当項目 `evidence_type: service_derived`。統合レポートには「会社側の想定。実利用者には未確認」と表示する |
| **② 自社の顧客の声で検証** | Customer側の子スキル（review / qa / social）。**または**利用者が問い合わせ・商談で直接聞いている顧客の声（Step1「利用者の一次情報」でヒアリング済みなら使う）。「どんな課題を持った人が、どんな言葉で語っているか」が根拠になる。可能なら実利用者・見込み利用者への直接調査を優先する | 裏付けが取れた項目・ペルソナは `persona_basis: customer_voice_confirmed` に格上げ、該当項目を `evidence_type: customer_voice` |
| **③ 競合事例で裏付け（上積み。実在確認のみ）** | competitor-case-study-research / competitor-company-deep-dive の**競合の**公式導入事例。同業・競合の顧客として**実在すること**は確認できるが、**「その人が自社を選ぶか」までは確認できない**（②より一段弱い根拠）。自社にオウンドメディア・事例インタビューが無い会社ほど使う機会が多い | `persona_basis: competitor_customer_voice_confirmed`、該当項目を `evidence_type: competitor_customer_voice`。障壁（相手側の内部状態）の裏付けに使うのは可。刺激（自社の訴求）の裏付けにする場合は、会社を問わない一般的な機序（例：他社事例に触れること自体が動機になる）であることを確認してから使う |

**①だけで構築したペルソナも仮説成果物として出してよい。** 「顧客の声で裏付けが無いから作れない」と諦めない。
ただし「実際の顧客像を確認した」とは書かない。②③の材料が無ければ①のまま `service_derived` で残す。
根拠の無い思いつきだけは `hypothesis` のままにする
（他の3値に格上げしない）。②と③がどちらも取れた場合は、より強い根拠である②の
`customer_voice_confirmed` を優先して記録する。

###### 探し先が無いとき

| 材料 | 無いときの扱い |
|---|---|
| 自社のオウンドメディア・事例インタビュー（②） | 無ければ次の材料へ。**多数派の会社はここが無い** |
| 第三者のレビュー・Q&A・SNS（②） | 無ければ次の材料へ |
| 同業・競合の事例（③） | 無ければ次の材料へ。あっても`competitor_customer_voice`（実在確認のみ）扱いで、②と同じ強さにはしない |
| 利用者自身が知っていること（②、Step1でヒアリング） | 答えが無ければ①のみで進める。無回答を理由に止めない |
| **すべて無い** | **①（サービスからの逆算）だけで仮説として出す。** `persona_basis: service_derived` と「実利用者には未確認」の注記を付け、この後の施策検討側が根拠の強さを判断できるようにする |

- **人数は2〜3人が目安。材料が足りなければ減らしてよい**（根拠の無いペルソナを人数合わせで作らない）。
  サービスメニューが複数の想定顧客に分かれる場合（例：「SEO支援」と「広告運用」で想定顧客が違う）は、
  そのメニュー単位の違いがペルソナを分ける根拠になる。
- **上限は5人。** サービスメニューが多い会社ほど機械的に増えやすいが、5人を超えたら**単純に
  切り捨てない**。態度変容フロー（障壁・刺激）が近いペルソナ同士を1人に統合する
  （ペルソナを分ける基準自体が「フローが違うこと」なので、フローが近いものはそもそも
  分ける根拠が弱い）。統合した場合は `distinguishing_factor` を統合後の分岐点に書き直す。
  09側の `validate_customer_understanding()` も5人超過時に警告する（`schema.PERSONA_MAX`）。
- **ペルソナを分ける基準は「態度変容フローが人によって違うこと」**。属性が違うから分けるのでは
  なく、Step 4c で作る各段階の「障壁」「刺激」が違うから分ける。フローが同じなら1人にまとめる。
- **何が違うから分けたのか**（`distinguishing_factor`）を必ず書く。ペルソナが1人のときは不要。
- ペルソナごとに `persona_basis`（`service_derived` / `competitor_customer_voice_confirmed` /
  `customer_voice_confirmed`）を必ず設定する。

#### Step 4c. 態度変容カスタマージャーニー（ペルソナごと）

固定の5段階で作る：**日常業務 → 課題の発生 → 調査 → 検討 → 購入**（最終段階の表示名「購入」は
既定値。次項「最終段階の表示名を決める」の手順で01の `kpis.yaml` から導いた名称に差し替える）。
各段階について、次の4点を書く。**4が成果物の中心**（ここが書けていなければ成果物として用をなさない）。

1. **状況・行動**：その段階で何が起きているか
2. **認識状態**：何を認識していて、何をまだ認識していないか
3. **障壁**：何が引っかかって次に進まないか
4. **刺激仮説**：どういう刺激を与えたら次の段階へ動くか

利用者向け統合レポートでは、ペルソナごとに説明段落を4つ並べない。**5段階を列、上記4点を行にした横向きの1表**へまとめ、各セルは原則1文・40字程度までとする。ペルソナの概要は直前の「顧客像の整理」の比較表で一度だけ示し、カスタマージャーニーでは再掲しない。表の前後に置く文章は「推定である旨」と「根拠」を各1〜2文までにする。

本文に書く段階の順番は、必ず定義順（**日常業務 → 課題の発生 → 調査 → 検討 → 購入**）に揃える。ペルソナごとに順不同で書くと、態度変容の流れを見せるという成果物の目的が成立しない。

障壁・刺激仮説には根拠の種類（`evidence_type`）を必ず5値のいずれかで設定し、01の
`customer-understanding.yaml` に保存する。利用者向けレポートではこの英字の内部値を出さず、
必要な場合だけ「顧客の声で確認」「公開事例から推定」「未検証の仮説」のような日本語で示す：

- `service_derived`：自社のサービスページ・料金ページ等、**自社が書いた**公式情報から「こういう人の、
  こういう状態に向けて売っている」と読み取れる場合。出典（ページ名・該当箇所の引用）を添える。
- `customer_voice`：**自社**に関するレビュー・Q&A・SNS等で「何がきっかけで検討を始めたか」
  「何が決め手だったか」を語っている発言が根拠として存在する場合、または利用者が問い合わせ・
  商談で直接聞いている顧客の声。発言の引用元（子スキル成果物名、または「利用者ヒアリング」）を添える。
- `competitor_customer_voice`：**競合**の公式導入事例に登場する実在の顧客の発言・行動が根拠。
  「その属性の顧客が実在すること」は確認できるが、「その人が自社を選ぶか」までは確認できない
  （`customer_voice` より一段弱い）。障壁の裏付けには使ってよいが、刺激に使う場合は会社を
  問わない一般的な機序であることを確認する。出典（子スキル成果物名）を添える。
- `desk_research`：**第三者**を調べて確認した客観的な事実が根拠。誰かの発言そのものではなく、
  調べた結果自体（レビューサイトの件数・傾向、Q&Aサイトで観測した言及、業界データ、公開情報）が
  根拠になる点で `customer_voice` / `competitor_customer_voice` と異なり、自社発信ではない点で
  `service_derived` と異なる。**「調べた範囲で見つからなかった」ことだけを障壁の根拠にしない。**
  不在は検索範囲を限定した調査結果として記録し、顧客が第三者評価を探して困った直接証拠か、
  独立した別根拠がある場合だけ障壁へ接続する。`competitor-review-research` / `competitor-qa-research` / `competitor-desk-research`
  が実際に調べた結果を出典として添える。**`service_derived` との境目に迷ったら「誰が書いたか」で
  判断する**：自社のページなら `service_derived`、第三者のサイト・データを自分で調べた結果なら
  `desk_research`。
- `hypothesis`：上記いずれの裏付けも無い仮説。**「〇〇な訴求が効く」と書くのは簡単だが、根拠が
  無ければただの思いつき。埋めたくなる項目だからこそ、ここは厳しく区別する。** `hypothesis`
  のまま書くときは、仮説を書いて終わりにせず、**「何を確認すれば裏付けになるか」を1文添える**
  （例：「competitor-qa-researchでこの障壁への言及有無を追加調査すれば裏付けになる」「利用者
  ヒアリングでこの刺激への反応を確認すれば裏付けになる」）。読み手が次に何をすればよいか分かる
  形にする。

`service_derived` / `customer_voice` / `competitor_customer_voice` / `desk_research` は
`evidence`（出典）が必須。`hypothesis` だけ `evidence: null` を許す。

**`persona_basis`（ペルソナ全体の構築経路）に `desk_research` は無い。** ペルソナの実在を
主張できる経路は「① サービスから逆算」「② 自社の顧客の声」「③ 競合事例」の3つのみ（次項）。
`desk_research` はどれかのペルソナが既に存在する前提で、その障壁・刺激を裏付ける根拠として
journey内でのみ使う（デスクリサーチだけでペルソナそのものを立てることはしない）。

段階・障壁・刺激には識別子を振る（`stage_id` は5固定値、`barrier_id` / `stimulus_id` は
`{persona_id}_{stage_id}_b1` / `_s1` 形式）。06（CVR改善）が「どの段階の、どの障壁に対する
施策か」を引けるようにするため。**この識別子は06連携用の内部の目印であり、読み手の手がかりには
ならない。** 本文（Step 4cのカスタマージャーニー本体、状況・行動／認識状態／障壁／刺激仮説の
各記述）には `barrier_id` / `stimulus_id` をそのまま書き出さない。段階名（例：「検討」段階の
障壁）で言及すれば足りる。識別子は01の `customer-understanding.yaml` にだけ保存し、利用者向けの
統合レポートには付録を含めて出さない。06（CVR改善）はレポートではなく09から識別子を引く。

##### 最終段階（`purchase`）の表示名を決める

`stage_id: purchase` は06が段階を参照するための識別子なので変えない。表示名（`stage_name`）だけ、
01の `kpis.yaml` に登録されたCVの実態に合わせて上書きする。手順：

1. 01の `kpis.yaml`（Step 0で読み込み済み）の `key_events` に紐づく `kpis[].name` / `.description`
   を確認する。
2. **GA4イベント名（`generate_lead` `contact_service_thanks` 等）から日本語の段階名を機械的に
   推測しない**。イベント名だけでは業務上の意味が自明でないことが多い（例：`contact_service_thanks`
   →「相談」と決められる根拠は名前自体には無い）。`kpis.yaml` の `name` / `description` に業務上の
   意味が書かれていれば、そこから該当事業のCVの実態を表す名称（「購入」「相談」「契約」「資料請求」等）
   を導く。
3. `kpis.yaml` に業務上の意味が書かれていない、または `kpis.yaml` 自体が未登録の場合は、**推測で
   決めない**。既定値「購入」を暫定値として使い、成果物・01保存の両方に「要確認（01のkpis.yamlに
   業務上の意味が無いため暫定）」と明記する。対話可能なら利用者に確認して確定する。
4. 日常業務／課題の発生／調査／検討の4段階（`stage_name`）は業種で大きく変わらないため、原則
   既定名（「日常業務」「課題の発生」「調査」「検討」）のままでよい。

利用者向けの統合レポートは次の表示ルールを守る。

- 作成前に `docs/report-writing-style.md`、`common/report_export/design_system/visualization-guidelines.md`、`common/report_export/design_system/design-system.md` を読み、文章・図表・デザインの正本に従う
- 表紙情報の直後に、`market-report-template.md` の `<!-- pictograms: insight,analysis,target -->` 付き3列表を必ず置く。顧客・市場の要点／競合・代替との違い／次の判断を各1〜2文でまとめ、HTML/PDFではピクトグラム要約として表示する
- HTMLの閲覧用目次は `report_export` が生成する。Markdown本文に手作業の目次を置かない
- 各章は対象と結論が分かる見出しで始め、前置きは原則1〜3文で止める。根拠は直後の表・図解または本文内リンクで示す
- 市場の異単位の数値はKPI、3Cは同色の3列か比較表と交点、複数ペルソナは同じ比較軸の表または平らなブロック、カスタマージャーニーは横向きのフロー図を既定とする
- 定性情報を棒・円・レーダーチャートへ変換しない。数が無い場合は比較表・カード・フロー図を使い、疑似スコアを作らない
- 1面の主メッセージは1つ、主要な表または図は原則1つにする。同じ内容を文章と表で繰り返さない
- 色は「良い結果」の緑と「悪い結果・要対応」の赤に意味を固定する。それ以外は白黒グレー、強調はゴールドにする。3Cの区分や根拠状態を別色にしない
- 1段落1論点、原則1〜3文とし、内部の実行メモやスキル名を利用者向け本文へ混ぜない
- 固定8章を文章だけで埋めない。各章に最低1つの比較表またはジャーニー表を置き、表の言い換えを複数段落で繰り返さない。顧客像は1つの比較表、カスタマージャーニーは顧客像ごとの5段階表を正とする
- 文体は専門家の監査報告ではなく、事業担当者がそのまま説明できる平易な言葉にする。`service_derived` 等の内部分類は利用者向け本文に出さず、社内用の根拠台帳に置く
- 利用者向け統合レポートの本文・注記・カスタマージャーニーの説明文は「です・ます調」に統一する。表内の名詞句はそのままでよいが、本文へ常体を混在させない
- `会社側仮説`、`利用者未確認`、`persona_basis` 等の内部ラベルを、本文・表・見出しへ出さない。顧客像は「立上げ補完型」のような通常の名称だけを使う。根拠の弱さを判断上残す必要がある場合は、表の直後に `<small>※ ...</small>` で1〜2文にまとめるか、「調査方法と限界」へ置く
- 対象名には `client_id` ではなく、確認済みのサイト名・企業名・製品名を使う
- 利用者が会議を明示していない限り、「次の打ち合わせで決めること」「MTGで握る論点」を作らない。判断に必要な未確認事項は、該当結論の直後に「要確認」として置く
- 利用者向け統合レポートに付録を作らない。公開出典は本文の該当箇所に直接リンクし、全量の根拠は `data/` に社内用として残す

ファイル名は固定で `00_3c_persona_journey_report.md`（`report_index` が本体レポートとして拾う基準名。変えない）。

固定構成は `../market-report-contract.md`、執筆テンプレートは `../market-report-template.md` を全文読んで使用する。以前の自由見出しテンプレートは廃止した。作成前に固定8項目の対象・根拠・不足を整理し、完成後は `python tools/validate_market_report.py <report.md>` を実行する。章を案件固有の結論で置き換えず、結論は各章の本文・H3以下に書く。示唆の件数合わせはしない。本契約は本書の旧章名・件数指定より優先する。
### Step 5. 人レビュー観点を内部で確認する

**このチェックリストは成果物の確定前に自分で確認する。** 確認した結果「怪しい」と分かった項目を
チェック無しのまま提示するだけで終わらせない。**該当する本文の記述を直してから**（例：出典が
薄いのに言い切っている一文を「〜と考えられる」「〜の可能性がある」のように和らげる、埋まって
いない `unresolved` を追加する）、チェックリストを完成させる。チェックリストは「本文の粗さを
検知する」ためだけの飾りにしない。

次の観点を内部で確認する。利用者向け統合レポートにチェックリスト自体は掲載しない。

## やってはいけないこと

* **全子スキルを盲目的に全部呼ぶ**：案件タイプとデータ有無に応じて選ぶ
* **子スキルの内容を本スキルで重複させる**：本スキルはオーケストレーションと統合に徹する
* **インプット 5 項目を埋めずに走り出す**：最低限テーマと対象は確定してから動く
* **競合・選ばれる理由・失注理由・提供限界を聞かず、公開情報だけで最終版を作る**：候補探索は進めてよいが、`data/research-intake.json` の確認完了までは最終版として配布しない
* **`会社側仮説`・`利用者未確認`・内部IDを利用者向け本文や見出しに出す**：通常の顧客表現へ直し、必要な留保は表下の小さな注記または「調査方法と限界」へ集約する
* **対象が決まらないとき、リポジトリの `README.md` / `CLAUDE.md` 等から発行元・運営会社名を読み取って対象に使う**：これらの文書はツール自体（配布元）についての記述であり、分析対象のクライアントとは無関係。対象は「ユーザーの明示指定」または「01の登録情報」だけを根拠にする（「対象の決め方」節）。どちらも無く、対話でも確認できない無人実行なら、推測せずに中断する
* **個別子スキルのレポートを丸ごと消す**：`data/child_reports/` に保存する（追加深掘り時に再利用するため）。ただし利用者に提示するのは統合レポート1本だけで、個別成果物をトップレベルには置かない
* **利用者が求めていない付録を作る**：利用者向け統合レポートは本文だけで判断できる形にする。全量の根拠は `data/` に社内用として残す
* **クローンの外にあるファイルを材料に使ったのに内部記録を残さない**：利用者向け本文にローカルパスを出さず、`data/` 配下の根拠台帳にファイルのパス・読んだ日・採った内容を残す
* **同じ対象を再実行したのに、日付や `_v2` のような接尾辞を付けた新しいテーマフォルダを作る**：同じ対象の再実行は既存のテーマフォルダに書き、既存の統合レポートは `_past/` へ退避してから上書きする（「出力フォルダの決め方」節）
* **人レビュー観点のチェックリストを省略する**：これは本スキルの成果物の必須要素
* **取得日付・期間情報を統合レポートから落とす**：個別レポートにあっても統合に転記しないと意味がない
* **Ahrefs未契約なのに『データが無いのでレポートが作れない』と止める**：`competitor-ahrefs-analysis` は任意の子スキル。契約が無ければその章を省いて、残りの子スキルだけでレポートを成立させる
* **ペルソナに年齢・職業・家族構成・趣味のような一般的な属性を書く**：態度変容の説明に効かない属性は書かない。書くのは態度変容を左右する属性（決裁権の有無等）だけ
* **属性の違いでペルソナを分ける**：分ける基準は態度変容フロー（障壁・刺激）が違うことだけ。フローが同じなら1人にまとめる
* **人数合わせで2〜3人のペルソナを作る**：材料が足りなければ人数を減らす。根拠の無いペルソナを作らない
* **5人を超えるペルソナを切り捨てて減らす**：態度変容フロー（障壁・刺激）が近いペルソナ同士を統合する。フローが違うのに人数のためだけに合わせない
* **顧客の声（レビュー・Q&A・SNS・競合事例・利用者ヒアリング）が無いことを理由にペルソナ作成そのものを諦める**：サービスから逆算した会社側の想定を仮説として出せる。ただし、実利用者に確認済みとは書かない
* **競合事例（`competitor_customer_voice`）を「自社を選ぶ」根拠として使う**：競合事例が確認できるのは顧客層の実在だけ。「その人が自社を選ぶか」までは`customer_voice`（自社の顧客の声）でなければ言えない
* **利用者ヒアリングを「ペルソナを教えてください」のような抽象的な聞き方で行う**：相手が具体的に思い出せる聞き方にする（「利用者ヒアリングの聞き方」節）。答えられなくても質問を重ねて止まらない
* **サービスメニューを「デジタルマーケティング支援」のような事業ドメイン単位の粗い粒度でしか見ない**：想定顧客が逆算できない。サービスページ・料金ページをメニュー単位まで分解する
* **障壁・刺激に根拠が無いのに `service_derived` / `customer_voice` / `competitor_customer_voice` / `desk_research` と書く**：根拠が無ければ `hypothesis` と明示する。埋めたくなる項目だからこそ厳しくする
* **第三者を調べて確認した客観的事実（レビュー・Q&Aサイトの件数、業界データ等）を `service_derived`（自社発信）や `hypothesis`（根拠なし）として書く**：材料が自社発信でも顧客の発言でもなく「第三者を調べた結果」なら `desk_research`。「調べたが見つからなかった」も事実として使ってよい
* **`desk_research` をペルソナの `persona_basis`（実在を主張する経路）に使う**：デスクリサーチはあくまで既存ペルソナの障壁・刺激を裏付ける根拠。ペルソナの実在自体は①サービスから逆算／②自社の顧客の声／③競合事例のいずれかで立てる
* **GA4イベント名だけから最終段階（`purchase`）の表示名を機械的に決める**：業務上の意味は名前からは自明でないことが多い。01の `kpis.yaml` に意味が書かれているか確認し、無ければ推測せず要確認と明記する
* **GA4データが無いのに実際の流入経路・ページ遷移を書く**：03はGA4を使わない。CJは外部公開情報から組み立てた仮説であることを明示する
* **公開出典を社内用の識別子だけで示す**：読み手がその場で開ける資料名つきリンクを該当記述に置く
* **`barrier_id` / `stimulus_id` を利用者向けレポートに書き出す**：内部の目印であり読み手の手がかりにならない。段階名で言及し、識別子は01の `customer-understanding.yaml` にだけ置く
* **`hypothesis` の刺激仮説を書きっぱなしにする**：「何を確認すれば裏付けになるか」を必ず添える
* **内部レビューで根拠の薄さを検知したのに、本文の言い切りをそのままにする**：検知したら該当箇所を書き直してから成果物を確定する
* **統合示唆（5章）に同じ論点の言い換えを複数個並べる**：候補を見比べて統合してから5〜8個に絞る

```
    └── {YYYY-MM-DD_HHMMSS}_00_3c_persona_journey_report.md
```

- 置き場所は実行フォルダ（セッション開始時のカレントディレクトリ。通常はリポジトリルート。docs/standard-run-order.md §4）直下の `outputs/{client_id}/` 配下に置く。client_id は 01 コンテキストストアの登録名を使う。出力先はユーザーに尋ねない（明示指定があった場合のみ上書き）。テーマフォルダ名（日付を含まない）と再実行時の `_past/` 退避は「出力フォルダの決め方」節（Step 1）の手順に従う。
- **個別の中間成果物は捨てず `data/child_reports/` に保存する**（追加深掘り時に再利用するため。以前と同じ理由だが、置き場所をトップレベルから移した）。ただし利用者への提示は統合レポート1本のみ。
- 統合Markdownの完成後は `python tools/validate_market_report.py <report.md>` と `python tools/report_quality_check.py <report.md>` を通してから、`docs/standard-run-order.md` §4-2 に従って成果物変換を実行する。HTML/PDFが指定されている場合は `common/report_export` で生成し、変換後のHTMLにも `pictogram-grid` があることを確認する。可視化契約を満たさない場合は変換処理自体が失敗するため、そのまま完成扱いにしない。
- **完了時の案内は「どれが最終か」を明示する**（`docs/standard-run-order.md` §4 規約4。パスを並べるだけでは、どれを見ればいいか伝わらない）。統合レポート（HTMLに変換した場合はそのHTML、無ければ `00_3c_persona_journey_report.md`）だけを「最終成果物」として案内する。`data/child_reports/` 配下の個別成果物は社内用の中間ファイル（再利用材料）であることを一言添えるだけにし、個別のファイルパスを並べて表示しない。案内は数行に収める。
- クライアントに紐づかない汎用調査（業界研究等）の場合のみ、従来の `research/YYYYMMDD_トピック/` を使ってよい
