# 05 数値改善（CVR改善）｜分析・施策作成（する側）

CVR改善を **2レイヤー（全体施策／施策）** で進める。05は各レイヤーで
**分析（GA4＋外部データ）と施策作成**を担う「する側」。その**レビューは [06_effect_verification](../06_effect_verification/) 側**が担う（作る人と検証する人を分けてバイアスを避ける）。

自然文で「サイト改善案を作って」「CVRを改善したい」と依頼されたときのチェーン制御、現在地判定、自動レビュー往復、停止条件は [run.md](./run.md) を正本とする。

## 2レイヤーと出力スコープ

| レイヤー | やること | 出力のゴール |
|---|---|---|
| **① 全体施策** `1_overall_strategy/` | どの改善タイプ（LPO/コンテンツ/サイト/EFO）に着手すべきか＋優先順位 | **方針まで** |
| **② 施策** `2_target_page_plan/` | 方針の中でどのページを対象にするか精査し、そのページの改善案と実施方法まで作る | **対象ページの決定＋実行可能な改善計画まで**（検出力不足なら計測整備または単独リリースへ切り替える） |

**旧構成では②「個別施策（対象ページ選定）」と③「ABテスト（改善案）」に段が分かれていたが、
統合した。** 理由は3つ: (1) 対象ページを選ぶだけの段は軽いはずが実運用で8ステップかかっていた、
(2) 段をまたぐたびに同じ内容が書き写され、そのたびに壊れる機会が増える（実際に到達率の定義
混在が段をまたいで再発した）、(3) 「どう変えられるか」を考えずにページは選べない（改善案作りの
段で初めて分かる制約があり、選定を先に確定すると手戻りになる）。詳細は `2_target_page_plan/README.md`。

①②とも `analysis/`（分析）と `creation/`（施策作成）の2エージェント、それぞれのレビュー
（`analysis_review` / `creation_review`）が06側にある。②の `creation/` は対象ページ選定と
改善案の両方を担い、出力の中で選定と改善案を別セクションに分けて書く（06が別々に判定できる
ようにするため）。

## 横断・支援エージェント
- `page_profile/` … 各ページの目的/ターゲット判定（②の前提を作る専用エージェント＝インプット元②）

CVR改善ではエンゲージ率を判断材料・成果物に使わない。セッション、キーイベント、定義済みの導線イベント、同一LP×流入元、ページ目的で判断する。

## 動くタイミング
①は最初に1回、②はぐるぐる回る（継続。対象ページ・改善案とも見直しが入りうる）。

## インプット元
1. 他エージェント（03外部探索・04基本分析 等）のアウトプットを利用
2. 専用エージェント（`page_profile`）で作成
3. 他エージェント＋②のエージェント＋担当者からの入力（対象施策の情報。主に改善案づくり）を利用
