# 実行手順: サイト改善チェーン

ユーザーは「サイト改善案を作って」「CVRを改善したい」などと自然文で依頼する。現在のAIエージェントが、この文書を入口として①全体施策→②施策（対象ページ選定＋改善案）を進行する。各段は05の作成→06の検証を通し、作成→検証は1往復まで自動で行う。①から②へ進む境界では、①の確定後に**チャットで方針を要約して続行確認を取り**、利用者の了承を待つ。レポート本文に確認待ちの章を置くだけでは、この確認を行ったことにならない。

**単一エージェントだけの手順ではない。** `outputs/{client_id}/05_cvr/_past/` に残る連番成果物（ファイル名は固定。日付を付けない）から「いまどの段まで済んでいるか」を判断し、そこから**実行できるところまで自動で続けて実行する**（1ステップ実行して止まり、利用者が毎回依頼し直す必要がある動きはしない）。段を飛ばさない。止まる条件は「## 実行の単位」を参照。チェーンの共通規約は `docs/standard-run-order.md §2`。各入口ファイルの手順も読んで実行し、このファイルに書き写さない。

**成果物の置き場所**: クライアントが見るのは `outputs/{client_id}/05_cvr/cvr-improvement-plan.md` 1本だけ。段ごとの個別確定版（`1_overall-strategy` / `2_target-pages` / `3_abtest-plan`）は作らない。確定した段だけを束ねた内容を、段が確定するたびにこの確定版へ直接反映する（作り方は `docs/standard-run-order.md §4-5`）。分析・レビュー・差し戻し前の途中成果物（この実行手順が現在地判定に使う連番ファイル）はすべて `05_cvr/_past/` に置く（`docs/standard-run-order.md §4` 規約2・3）。

## 実行前チェック（必ず最初に）

「無いと動かない」と「あると精度が上がる」の区別、質問のまとめ方は docs/standard-run-order.md §2-1 を正本とする（内容をここに書き写さない）。

1. **client_id の確定**。依頼文に指定があれば 01 に登録済みか確認する。無ければ登録済み一覧を提示して選んでもらう。チェーン全体で同一の正規 ID を使う（表記揺れを作らない）。
2. **01 の前提を読む**。`load_context(client_id)` を実行する。
   - **未登録**なら、重い01登録フロー（`01_context_management/prompts/context-manager.md`）には進まず、`docs/standard-run-order.md` §2-1 のURL先行受付を使う。最初に対象サイトURLを確認し、サイト表示名と client_id はURL・サイト・GA4情報から候補を作る。曖昧・矛盾・重複がある場合だけ利用者へ確認し、`writeback.ensure_client_registered()` と `writeback.save_business_profile(site_url=...)` で最小登録する。フル登録を望む利用者には、自然文で「サイト情報を一通り登録して」と依頼できることを案内する。
3. **KPI・CV の確定**（このチェーンの「無いと動かない」項目）。対応する GA4 イベント名が 01 に登録されているか確認する。無ければ、一括依頼でもここで止めて確認する（分からなければ GA4 キーイベント設定から候補提示）。確定したら `writeback.save_kpi_info(client_id, key_events=[...])` で01に保存する（次回から聞かれない）。CV が確定しないまま進めない。
4. **出力先**。`outputs/{client_id}/`（尋ねない。明示指定時のみ優先）。
5. **成果物の出力形式の確定**。依頼文に形式の指定があればそれを今回だけ優先する。無ければ01の既定（`profile.yaml` の `preferences.output_formats`）を使う。01にも無ければ、上記3の質問とまとめて1回で「MDのみでよいか、HTML/PDF/Word/Excelへの変換が要るか」を聞き、`writeback.save_output_format_preference(client_id, output_formats=[...])` で保存する（次回から聞かれない。チェーン全体で1回聞けば以後の各段では聞き直さない）。**対話で応答を待てない無人実行のときは、仮の形式を自分で選ばずMDのみで進め、`save_output_format_preference` も呼ばない**（§4-2）。優先順位・保存方法の詳細は docs/standard-run-order.md §4-2。

### 成果物契約チェック

作成側・是正反映側が `01-analysis.md`、`03-strategy.md`、`04-strategy-final.md`、`page-profile.md`、`05-page-analysis.md`、`07-target-page-plan.md`、`08-target-page-plan-final.md`、`cvr-improvement-plan.md` のいずれかを書いた直後は、次を単独で実行する。

```bash
uv run python tools/validate_cvr_artifact.py "<書いたMarkdownのパス>"
```

内部成果物とクライアント向け確定版では検査条件が異なる。`docs/standard-run-order.md` の「CVR改善チェーンの判断・成果物契約」に従う。確定版は結論から始め、内部前提の見出しや内部IDを載せない。NGのまま次工程・確定版反映へ進まない。

**なぜこの形で判定が成立するか**: 出力規約（`docs/standard-run-order.md §4`）はファイル名から日付を外し、上書き前に旧版を `_past/` へ退避する方式に変えた。この現在地判定は元々「連番ファイルの存在」だけを見ていたので、**退避先の `05_cvr/_past/` を「常に最新の連番ファイルが並ぶ場所」として使う**ことで判定方法自体は変えずに済んでいる。退避される旧版はファイル名の先頭に時刻が付くため、上表の完全一致のファイル名とは重ならず、誤判定しない。段の確定版（①②）は判定に使わず、`05_cvr/_past/` の連番ファイルだけを見る。

## 実行の単位（05→06 自動往復・1往復まで）

このチェーンを実行するたびに、開始点から**実行できるところまで自動で続けて実行する**。05 のステップが完了したら、人の追加依頼を待たずに**続けて同じ番号の 06 レビューを実行**し、06 が「妥当（軽微な指摘つきを含む）」なら**続けて次のステップを実行**する。止まるのは次のいずれかのときだけ。

1. **段の境界（①→②）**。前段の確定版ができた直後は、次段の最初のステップ（②の `page_profile`）を実行せずに止める。その場で下記「ゲートと範囲」の形式に従ってチャットで方針を要約し、続行してよいかを明示的に聞く。
2. **同じ 05→06 のペアで 06 が2回目の要修正判定を出した**（1往復までの自動修正枠を使い切った）。このときは差し戻しをせず、その場で実行を止めて人に報告する。②の場合は「選定」「改善案」のどちらが（または両方が）2回目でも解決していないかを含めて報告する。
3. 実行前チェック（01未登録・CV未確定など）で止める既存の条件に当てはまったとき。

### 06が「要修正」を返したときの往復（1回だけ自動）

- **1回目の要修正**: 自動で対応する 05 のステップに差し戻し、指摘を踏まえて 05 が出力を作り直す → 続けて同じ 06 レビューを再実行する。**再実行時は「これは2巡目のレビューである」と司令塔のAIエージェントから06に明記して伝える。**
- **2回目の要修正（＝2巡目のレビューでも要修正）**: **ここで止める。3巡目は自動実行しない。** 差し戻しは行わず、次を人に報告する。
  - どのステップで止まったか（クライアント向けの呼び方。例:「全体施策の方針チェック」）
  - 何周したか（2周）
  - まだ解決していない指摘（06の出力の「結論を変える指摘」欄をそのまま引用する）
  - このあとどうするか（人が指摘を見て05への追加指示を出す、または方針・対象・案を変える）

**何巡目かは、司令塔となる現在のAIエージェントが管理し、06を呼び出すたびに明記して伝える。** 1回のチェーン実行の中で、あるステップの06を最初に呼ぶときは「1巡目」、要修正で05に差し戻した後にもう一度そのステップの06を呼ぶときは「2巡目」と伝える。司令塔は同じ実行の中で06を何回呼んだかを把握できるので、これで足りる。**`05_cvr/_past/` に残る退避ファイルの件数や退避時刻からは判定しない。** 退避ファイル名の先頭に付く時刻は「退避した時刻」であり「その内容が作られた時刻」ではないため、数か月前の内容を今日たまたま退避しただけでも新しく見えてしまい、件数や時刻だけで判定すると初回のレビューを2巡目以降と誤判定する（数か月後に同じクライアントを①から回し直すケースで実際に発生した）。**06がこのチェーン制御を経由せず単体で呼ばれた場合（回数が伝えられていない場合）は1巡目として扱う**（各06レビューの入口ファイルの「ラウンド判定」参照）。伝えられた回数が2巡目を超えてなお差し戻そうとしている場合は、上限を超えた運用逸脱として実行前に止める。

### ②（07-target-page-plan.md ↔ 08-target-page-plan-final.md）は選定と改善案を別々に往復させる

`06_effect_verification/2_target_page_plan/creation_review/prompts/review.md` は「選定」「改善案」を独立に「妥当／要修正」判定し、判定記録として`08-target-page-plan-final.md`を常に書く。**両方が妥当のときだけ**②の確定版として扱う。06から返る総合判定は次の4通りのいずれかなので、司令塔はその内容をそのまま05に伝えて差し戻す。

| 06の総合判定 | 司令塔が05に伝える差し戻し指示 |
|---|---|
| 選定:妥当／改善案:妥当 | （差し戻しなし。②確定として次へ進む） |
| 選定:要修正／改善案:妥当（保留） | 「選定のみ要修正」→ 05は「## 対象ページ選定」だけ作り直す（対象外になったページの改善案は削り、新規対象ページの改善案は追加するが、対象が変わらないページの改善案は作り直さない） |
| 選定:妥当／改善案:要修正 | 「改善案のみ要修正」→ 05は「## 改善案（ページごと）」だけ作り直す（選定はそのまま） |
| 選定:要修正／改善案:要修正 | 「両方要修正」→ 05は両セクションとも作り直す |

**巡目のカウントは選定・改善案を分けず、この05→06ペア全体で1つ数える**（例: 1巡目「選定のみ要修正」で差し戻し、2巡目のレビューで選定が妥当になったが新たに改善案が要修正になった場合も、これで2巡目の要修正が確定したとみなし、3巡目には進まず止める。選定と改善案で別々にラウンド数を数え出すと、往復の上限（1往復まで）が実質的に増えてしまうため）。

## ゲートと範囲

- **段の間（①→②）は、人が結果を確認してから次の段へ進む。** ①の内容が確定版（`05_cvr/cvr-improvement-plan.md`）に反映された直後は、そこで一度実行を止め、チャットで次の4点を簡潔に示す。
  - 全体方針がまとまったこと
  - 優先する改善方向（1〜2点。確定方針の内容を要約し、新しい事実を足さない）
  - 判断の主な根拠または重要な留意点（1〜2点）
  - 次に行うこと（対象ページを選び、ページごとの改善案を作ること）
- 上記の直後に、**「この方針で、対象ページの選定とページ別の改善案作成まで進めてよいですか？」** と明示的に聞く。利用者向けには内部の工程番号・ファイル名・`page_profile` 等を出さない。単に成果物のパスを示す、レポート内に「個別ページ改善へ進む前の確認」を置く、または「確認してください」とだけ書く対応ではゲートを満たさない。
- 利用者が「OK」「進めて」等と了承したら、次の呼び出しでは `page_profile` から開始し、②の確定まで同じ段の処理を自動で続ける。方針変更の希望や判断できない返答の場合は②へ進まず、指示を①へ反映する。②の途中に同趣旨の追加承認ゲートは設けない。
- チャットでの確認文は次を基本形とする。値は確定方針から埋め、空欄や例文のまま出さない。
  ```text
  全体方針がまとまりました。
  - 優先する方向: <方針の要約>
  - 主な根拠・留意点: <根拠または制約の要約>
  - 次に行うこと: 対象ページを選び、ページごとの改善案を作成します

  この方針で、対象ページの選定とページ別の改善案作成まで進めてよいですか？
  ```
- **段の途中（同じ段の中の 05→06）は自動で連続実行する。** 呼び出しを分ける必要はない（上記「実行の単位」参照）。
- GA4 の取得生データは `outputs/{client_id}/_data/ga4/` に取得日プレフィックス付きで保存する（06 が検算材料に読む。材料が無ければ 06 はレビューを中断して 05 に差し戻す）。
- ②は対象ページ選定と改善案の確定（`08-target-page-plan-final.md` → `05_cvr/cvr-improvement-plan.md` へ直接反映）までを扱う。テスト実行後の効果測定は初版の対象外。

## 完了時

- **この回の呼び出しで実行した全ステップ**を、それぞれの入口ファイルの手順どおり成果物をファイルに書き出しながら順に実行する（上記「実行の単位」）。①②の確定版を書いた段（`04-strategy-final` / `08-target-page-plan-final`）は、続けてその内容を確定版 `05_cvr/cvr-improvement-plan.md` に**直接**反映する（既存の確定版があれば `_past/` へ退避してから上書き。段ごとの個別確定版は作らない）。確定版は、その時点で確定している段をすべて束ねて毎回作り直す（各06レビューの入口ファイルが行う。単純な連結にしない基準は `docs/standard-run-order.md §4-5`）。
- **完了時の案内は数行で、最終成果物と中間ファイルを区別する**（docs/standard-run-order.md §4 規約4）。確定版に反映した段は、その `05_cvr/cvr-improvement-plan.md` のパスを**最終成果物**として示す。それ以外の段（分析・レビュー・作成の途中）は、書き出した `_past/` 配下のファイルのパスを途中経過（社内用）として示し、最終成果物とは呼ばない。
- **この回で実行したステップの一覧と、06レビューが何巡したかを完了報告に書く。** ①の確定で止まる場合は、内部の工程番号やファイル名を並べる代わりに、上記のチャット用確認文で方針と次の作業を伝え、続行可否を聞く。**2回目の要修正で止まった場合は、上記「06が要修正を返したときの往復」の報告内容（止まった段・周回数・未解決の指摘・次にどうするか）をそのまま案内し、それ以降のステップは実行しない。**
- `python common/report_index/build_index.py "outputs/{client_id}"` で `outputs/{client_id}/index.html` を再生成し、そのパスもあわせて示す。途中の段でも、index.html にはチェーンの現在地（進行中の表示）が反映される。
- **HTML/PDF等への自動変換の対象は、クライアント向け確定版（`05_cvr/cvr-improvement-plan.md`）だけ。** 01に既定の出力形式が設定されていれば、確定版がこの回で更新された場合に `common/report_export` で変換し、変換後のファイルのパスもあわせて表示する。**`05_cvr/_past/` 配下の分析・レビューの中間ファイル（`0X-...-review.md` や `04-strategy-final.md` 等の`-final`ファイルを含む）は変換しない（常にMDのみ。docs/standard-run-order.md §4-2）**。設定が無い・MDのみの場合は従来どおりMDのパスだけを表示する。単発で別形式が要るときは「このレポートをPDFにして」などと自然文で依頼し、`common/report_export` を使う。
- 01 への書き戻しは、実行した各段の入口ファイルの手順（それぞれの `append_finding()`）に従う。**1回の呼び出しで複数ステップを実行した場合は、実行したステップの数だけ `append_finding()` を呼ぶ**（まとめて1回にしない）。
