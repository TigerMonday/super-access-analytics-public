# 改善事例の情報源と都度調査

共通の事例データベースは作らない。レポートの課題・施策に合わせて、その都度公開事例を調べる。全件収集、件数目標、定期蓄積は行わない。

## 情報源

情報源への掲載は品質保証ではない。**個別記事で数値・調査方法を確認できるものだけを、レポートの根拠として採用する。** 有名な会社、成功事例という見出し、改善率の大きさだけで選ばない。

## 調査と記録

### 根拠としての採用条件

- 一次資料の個別本文に、調査対象、対象数（人数・サイト数・セッション数等）、実施時期・期間、指標の定義、調査・比較方法、結果の数値があるかを確認する。欠けた条件は推測で補わない。
- 「CVRが2倍」だけで、何のCVか、分母、比較対象が分からないものは効果の根拠に採用しない。実施内容が具体的なら内部の発想材料にはできるが、根拠付きの成功例として本文へ載せない。
- A/Bテストは割付・対象数・期間・不確実性を確認する。前後比較は季節性・流入変化・同時施策を確認し、施策単独の因果を断定しない。
- UX調査は対象ユーザー・課題・観察方法と、失敗率・達成率等の結果を確認する。定性観察は操作上の仮説の根拠であり、CVR上昇の証拠とは区別する。
- クリック率、カート投入率、購入率、問い合わせ率を混ぜない。相対増とポイント差、最大値と平均値も区別する。
- 必要な根拠が公開されていない場合は別の資料を探す。見つからなければ、外部の効果根拠は未確認とし、自社データからの検証候補に留める。件数のために条件を緩めない。
- 案件側の採用記録には上記項目と「実験／前後比較／横断調査／定性観察」の区分、適用限界を残す。根拠の妥当性はエージェントが本文と照合する。既存の構造検査で自動保証されるものではない。

1. 自社の数値・UI観察から改善目的を定め、顧客の検討段階・業態・対象UIで事例を探す。
2. 一覧の見出しだけで採用せず、個別本文の変更内容と成果の定義・分母・期間・比較方法を確認する。未記載は未確認とする。
3. 掲載企業と支援対象企業を区別する。同案件の別媒体掲載を独立した成功例として扱わない。数値に矛盾があれば成果値を採用しない。
4. 採用した事例だけを `outputs/{client_id}/05_cvr/_data/adopted-cases.md` に記録する。URL、確認日、要点、成果の定義と制約、対応施策、応用する点を残す。本文には判断に必要な要点と出典だけを掲載する。
5. 再利用時も個別原典を確認する。既存の案件記録を最新情報とはみなさない。合う事例がなければ無理に掲載しない。

検索順：改善目的→顧客の検討段階→業態→対象UI。企業の業種が同じという理由だけで採用しない。ベンダー掲載の成功事例には選択バイアスがある。成果数値を自社施策のICEの確信度や期待改善率へ直接転用しない。

全文・画像の一括複製は行わない。共通領域には情報源と調査ルールのみを維持し、案件固有の事例を追加しない。
