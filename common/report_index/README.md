# report_index

`outputs/{client_id}/` を走査して `index.html`（成果物一覧の入口ページ）を作るツール。
特定のエージェント専用ではない。実在するフォルダ・ファイルだけを見て一覧を作るので、
テーマ側がまだ最新の出力規約（`docs/standard-run-order.md` §4）に追いついていなくても、
あるものを拾って動く。

外部依存パッケージは無い（標準ライブラリのみ）。`uv sync` 等の準備は不要。

## 使い方

リポジトリルートから実行する。

```bash
python common/report_index/build_index.py "outputs/{client_id}"
```

`outputs/{client_id}/index.html` を（無ければ作り、あれば上書きで）生成し、生成した
ファイルの絶対パスを標準出力に表示する。通常は `common/report_export` が
`outputs/{client_id}/` 配下へHTMLを書き出した直後に自動実行する。HTMLを直接作成して
`report_export` を通さない場合や、入口を修復・明示的に再構築したい場合は、このコマンドを手動で実行する
（`docs/standard-run-order.md` §4 規約3）。

一覧の更新時には、見つかった各HTMLのサイドバーも同時に更新する。全レポートを横断して移動できる
目次を入れ、レポート名ごとに開閉できるアコーディオンにする。いま開いているレポートだけを既定で
展開し、ほかのレポートは閉じる。PDFでは従来どおりサイドバーを印刷しない。

`--client-id` でサイト識別名を明示できる（省略時はフォルダ名をそのまま使う）。一覧の表示と前提情報へのリンクの両方に使うため、日本語の表示名ではなく登録済みの識別名を指定する。保存先とフォルダ構成は `docs/standard-run-order.md` の「閲覧先とフォルダ構成」を参照。

```bash
python common/report_index/build_index.py "outputs/my-site" --client-id "my-site"
```

## 何を一覧に出すか

入口ページ自体とブラウザ向けの最終成果物はHTMLを正とする。既存テーマの移行中でも成果物を
見失わないよう、一覧生成だけはHTMLが無い場合にMarkdownへフォールバックする。同じフォルダに
同じbasenameのPDFがあれば、同じカード内に「PDFを開く」副リンクを表示する。

- `outputs/{client_id}/` 直下の `NN_なまえ` 形式のフォルダ（テーマフォルダ）を走査する。
- テーマごとに「本体のレポート」として見せるファイル名（拡張子抜き）を `build_index.py`
  内の `_THEME_REGISTRY` に登録している（例: `02_measurement` なら `check-report`、
  `03_research` の各トピックフォルダなら `00_3c_persona_journey_report`）。
  登録済みのテーマは、フォルダの深さを問わずそのファイル名を再帰的に探す
  （`.html` があれば `.html` を優先、無ければ `.md`）。選ばれた主ファイルの隣にある同名PDFだけを
  副リンクにするため、別フォルダのPDFを誤って紐付けない。
- `03_research` のように調査テーマごとにサブフォルダ（`YYYYMMDD_トピック/`）を持つ
  テーマは、サブフォルダ単位で1件ずつ一覧に出す。タイトルはレジストリの表示名
  （例:「市場顧客分析」）を基本にし、対象違いの調査で
  トピックフォルダが複数あるときだけ、フォルダ名から推測した対象名を
  「表示名（対象名）」の形で添えて区別する（1件だけのときは表示名のみ）。
  レジストリの基準ファイルが見つからない場合はフォルダ名をそのまま出す
  （何のレポートか判断できないため）。
- レジストリに無いテーマフォルダ、または登録済みでも該当ファイルが見つからない場合は、
  フォルダ内で見つかった Markdown/HTML ファイルをそのまま一覧に出すフォールバックで拾う。
- `_` または `.` で始まるフォルダ（`_data`・`_past` など）はスキャン対象から除外する
  （生成物ではない・内部の作業領域という共通の合図）。フォールバック時は、ファイル名に
  `-notes`・`.draft`・`-draft` を含むもの（人が書き込む途中のファイルの典型例）も除外する。

## 利用者向けの表示名

成果物トップには内部フォルダ番号（`02`・`03`など）や内部保存先の説明を表示しない。
テーマ名とレポート名は利用者が内容を判断できる名称にし、市場・競合・顧客を扱う統合レポートは
「市場顧客分析」に統一する。内部フォルダ名やファイル名は変更せず、表示だけを分かりやすくする。

## チェーンの「進行中」表示（05 CVR改善など）

06のCVR改善チェーンは、**クライアント向け確定版が `cvr-improvement-plan` 1本だけ**
（段ごとの個別確定版は持たない。正本は `docs/standard-run-order.md §4-5`）。この確定版がまだ無い
状態と、一度も実行していない状態を区別できないと「何もしていない」ように見えてしまう
（進行中の途中成果物は `_past/` にあるため、確定版だけを見るとゼロ件になる）。

これを避けるため、`_THEME_REGISTRY` の各テーマに任意で `chain` 設定を持たせられる。対応する
`chain` の手順（`_past/` 配下の固定名ファイル・時系列順）のうちどこまで実在するかを見て、
「進行中」として確定版とは別枠（`section.progress`）に出す。判定表の正本は
`05_campaign_optimization/run.md`（ファイル名を変えたらそちらも直す）。

06は確定版が複数段（①②）を束ねた1本しか無いため、**確定版が既にあっても進行中の
判定は独立して行う**（例: ①が確定して確定版ができた後、②の分析が進行中というケースがある）。
ただし、ある段の是正反映が完了した合図（`-final.md`）が_past/の最新到達点になっている場合は
「進行中」として出さない。`-final.md` はそのレビュー実行の中で確定版へ直接反映されるため、
これが最新の到達点ということは確定版側がすでに反映済みのはずで、二重表示を避けるため。
判定ロジックは `build_index.py` の `_find_chain_progress` を参照。

「進行中」は確定版のカードと混ざらないよう見た目を控えめにし（ゴールドの小さいラベルのみ・
枠や強い装飾は使わない）、途中成果物へのリンクは辿れるようにしつつ前面には出さない。
`chain` を持たないテーマ（02・03など単発のエージェント）には影響しない。将来別のチェーンが
できた場合も、同じ `chain` 設定を追加するだけで同じ表示が動く。

## デザイン

見た目は `common/report_export/design_system/design-system.md` のコアCSS・共通部品
（`.section-label`・`.section-title`・`.card` 等）をそのまま使う。別のデザインは持ち込まない。
コアCSSは `build_index.py` 内に埋め込んでいる（配布先で1ファイルで開ける必要があるため。
`report_export` 側と同じ理由の意図的な二重管理。デザインを変えるときは design-system.md を
直してから、ここにも反映する）。

## テスト

pytest等の追加インストールは不要（標準ライブラリの `unittest` のみで書いている）。

```bash
python -m unittest discover -s common/report_index/tests
```
